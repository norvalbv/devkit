# consumer-extra-gates

## Target · 2026-10-08 — A repo declares extra deterministic gates in guard.config.json as extraGates, a label-to-command map

**Context:** Overlay and package consumers had no way to add a repo-specific deterministic gate. Only self-host could, by baking --extra into its generated hook. A consumer that moved from a hand-written pre-commit to an overlay lost commands such as knip, its structure lint and its typecheck, so devkit ship passed and the repo's main went red on CI three times in two weeks.
**Ruling:** A repo declares extra deterministic gates in guard.config.json as extraGates, a label-to-command map. guard-deterministic reads them at run time and runs them after any --extra gates, under the same contract: each command's argv is split on whitespace, runs without a shell, and any non-zero exit blocks. A malformed entry, a non-object block or an unreadable guard.config.json blocks as unrunnable instead of being dropped. The value is a resolved GuardConfig field, so the prefix-cache config fingerprint changes when the declared set changes.
**Consequences:**
- Positive: Any install mode gets the repo's own checks on commit, ship and --dry-gates with no hook regeneration, and a cached green tree can never skip a newly declared gate.
- Negative: Gates are whole-command, not diff-scoped: pre-existing debt on the base branch blocks every commit until it is fixed. Commands run without a shell, so anything compound has to live in a package script.
**Vision-fit:** n/a — internal tooling
**Researched:** gate-engine/deterministic/run.mts (--extra contract, prefix scope), gate-engine/prefix-cache/config-fingerprint.mts (fingerprint hashes the resolved GuardConfig), cli/lib/husky/self-host.mts (SELF_HOST_EXTRAS), devkit PR #663 (deferred consumer --extra gates), frink-oss CI history.
**Rejected:** (a) Let overlay or package init write consumer --extra flags into the generated hook: every config change needs a hook regeneration, and the hook text is the only cache input. (b) Ship a built-in knip gate: covers one tool and leaves typecheck, structure lint and generated-content checks out. (c) Read extraGates outside GuardConfig: the cache fingerprint would miss it and a cached green tree would skip a newly declared gate.
**Scope:** gate-engine/deterministic/run.mts,gate-engine/deterministic/command-gates.mts,gate-engine/config.mts,guard.config.example.json
**Source:** manual

## Target · 2026-10-24 — An extraGates command may take the commit's staged paths as a {staged} argument

**Context:** devkit's self-host related-tests gate blocks a broken test before the AI reviewers, saving an escalated reviewer round of about 7 minutes, but no consumer could build one. Under git commit -a or git commit -- <path> the commit index is an alternate file that only devkit reads, through commitIndexEnv. Every off-the-shelf staged reader saw the wrong set, and a monorepo package gate runs from the package dir while git prints root-relative paths.
**Ruling:** A repo declares extra deterministic gates in guard.config.json as extraGates, a label-to-command map, run after any --extra gates; each command's argv is split on whitespace, runs without a shell, and any non-zero exit blocks. A malformed entry, a non-object block or an unreadable guard.config.json blocks as unrunnable. One whole argument {staged}, at most once, expands to the commit index's ACMR staged set (stagedSet, MERGE_HEAD-intersected), sorted and made relative to the gate's cwd, so a sibling package stays ../x. An empty set prints '<label>: no staged paths, not run' and passes without spawning; an unreadable set or one over 256 KiB blocks as unrunnable. A {staged} inside a larger argument, or twice, blocks as unrunnable. devkit ships no runner-specific related-tests gate: the consumer names its own runner.
**Consequences:**
- Positive: Any repo, in any install mode and in a monorepo package, can block a commit on its related tests before any AI judge, with vitest related --run {staged}, jest --findRelatedTests --passWithNoTests {staged} or its own script, with no hook regeneration. devkit's self-host related-tests reads its paths the same way, so the consumer path is dogfooded.
- Negative: The tests read the working tree, which equals the staged content only under devkit ship. Deleted paths are not passed, so an importer of a deleted module is not selected. A staged package.json or vitest config still makes vitest run its whole suite unless the consumer narrows forceRerunTriggers. The prefix cache keys on the staged tree, not HEAD, so an identical tree re-shipped on another parent replays the earlier selection. A huge staged set blocks rather than batching.
**Vision-fit:** n/a — internal tooling
**Researched:** gate-engine/deterministic/{run,command-gates}.mts, gate-engine/ratchets/git-index.mts stagedSet/gitPrefix, cli/lib/husky/husky-block.mts (package cd), cli/lib/ship/evidence/config.mts {files} placeholder; vitest 5.0.3 dist (related defaults passWithNoTests, forceRerunTriggers, resolve against root), vitest #280, #5739, PR #9928; lint-staged lib/gitWorkflow.js; test-staged; jest CLI docs and kcd-scripts#245 on --passWithNoTests.
**Rejected:** (a) A vitest-only built-in related-tests guard in the registry: the shape of this axis's earlier rejected built-in knip gate, covering one tool, while two of five local consumers use node --test and one a custom runner. (b) lint-staged or test-staged as an extraGate: both read git diff --cached from the inherited env, which devkit scrubs, and lint-staged also stashes and rewrites the working tree. (c) vitest --changed: it adds unstaged and untracked files. (d) A vitest experimental.vcsProvider module: experimental, vitest-only, and needs a consumer config edit.
**Scope:** gate-engine/deterministic/run.mts,gate-engine/deterministic/report.mts,gate-engine/deterministic/selection.mts,gate-engine/deterministic/command-gates.mts,gate-engine/config.mts,guard.config.example.json
**Source:** shortcut · sc-5114
**Evidence-change:** A consumer wanting related tests at commit had no working road: devkit scrubs GIT_INDEX_FILE for gate children, so lint-staged, test-staged and vitest --changed read the default index or the working tree, and extraGates passed no staged list. Only devkit can read the commit index, so it must hand the paths down.
- 2026-10-24 — The {staged} check runs per command in expandStaged, not in the extraGates schema, so the hook's --extra and --structure flags and guard-structure commands get the same expansion and check. A malformed placeholder blocks as '<label>(unrunnable: {staged} must be one whole argument)'. A {staged} gate prints no re-check line, because the expanded path list goes stale once the fix is staged. devkit's own related-tests wrapper blocks when given no paths, since devkit never spawns a {staged} gate with nothing staged.
- 2026-10-25 — parseJsonObject (gate-engine/config-json.mts) rejects a key that one object declares twice, at any depth, naming the key path and both lines. JSON.parse keeps only the last copy, so a second extraGates block silently dropped the first; this was the one malformation the blocking path never saw. The scan uses jsonc-parser's visit() after JSON.parse succeeds, so values and syntax errors are unchanged. Keys starting with // may repeat because the loader ignores them. devkit migrate and the doctor judge-family bind read through the same function, so neither rewrites a duplicated file and erases the first block.
