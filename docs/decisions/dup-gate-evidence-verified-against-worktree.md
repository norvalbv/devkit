# dup-gate-evidence-verified-against-worktree

## Target · 2026-07-25 — Dup-gate findings must be backed by working-tree evidence

**Context:** guard-dup reported duplication pairs purely from the search-code index and never opened a file on disk. That index is shared — devkit ship symlinks the primary checkout's copy into every gate worktree, this repo sets no indexCommand, and any concurrent writer can revert it — so it routinely holds a PRE-change version of a file. The reported incident (sc-1237, twice in one session, ~8 min lost each): StopRunButton was extracted out of FlowRunStrip/index.tsx into its own file and the gate blocked on a drifted pair between the two at range-b 79-142, the symbol's location on the BASE branch; the parent no longer defined it at all. Blast radius is the whole mandated commit path for exactly the refactor the gate reasons about worst — moving a symbol between files — and the only remedy it printed was guard-dup-allowlist add, which would have written a permanent approval for a pair that does not co-exist. Re-indexing was named nowhere in the failure output.
**Ruling:** Every pair the scan gate reports must be backed by code in the working tree. For each side, the indexed chunk BODY — the tail of raw_code after search-code's import prelude, which must be stripped: measured over 898 chunks with the symbol's lines deleted, a prelude-inclusive comparison still called 17% of them fresh, the body 0.2% — is looked up by rowid and checked for presence ANYWHERE in the file on disk: verbatim first, then, as formatting tolerance only, the best ALIGNED window of significant lines scoring >= 0.8. Alignment (not set membership) is load-bearing in both directions: it rejects a deleted symbol whose generic guard clauses live on scattered through sibling functions, and it means a symbol whose CONTENT changed since the last index reads as stale — correctly, since its embedding describes text that is no longer there. Presence anywhere, never at the recorded range: line drift must stay invisible or the gate goes quiet on ordinary commits. A side whose body is absent, or whose file cannot be read, drops the pair. The layer is strictly DROP-ONLY and lives only in runScan — never reconcile or baseline, where over-dropping deletes real human approvals — and it disables itself wholesale on an index carrying no raw_code/id, on GUARD_DUP_VERIFY_TREE=0, on any DB error, and on the root-mismatch fuse (every probed path missing, i.e. an index rooted elsewhere). Every drop is named in the output with a re-index hint, and a block decided on unverified evidence says so.
**Consequences:**
- Positive: An extract refactor can no longer be blocked by code that is not on disk, and no false approval can be written into the allowlist by following the gate's own printed remedy. Because the filter can only turn a block into a pass, no cached deterministic-prefix PASS is invalidated by it, and no verification failure can ever surface as a block. What the gate withholds is printed rather than silently swallowed, so a quiet run is never mistaken for a clean one.
- Negative: Recall, knowingly. Any symbol whose body changed since the last index — and, in a ship worktree, every non-shipped file, which sits at BASE while the shared index reflects a dirty primary checkout — is dropped rather than judged on text that is no longer there. The gate is therefore quieter than the index alone would make it, and quietest exactly where editing is heaviest; the loss is printed on every run instead of hidden, and re-indexing restores it. Verification also costs one file read per distinct path in a reported pair (cached), and the upstream cause is untouched: search-code's incremental indexer skips a changed file on an mtime stamp, so 'touch <file> && search-code index --seed-files' remains the manual refresh.
**Vision-fit:** n/a — internal tooling
**Revisit-when:** search-code exposes a per-chunk verified-fresh flag or content hash (making body re-derivation unnecessary), or devkit ship stops sharing one index across concurrent worktrees
