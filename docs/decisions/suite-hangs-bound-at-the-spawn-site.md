# suite-hangs-bound-at-the-spawn-site

## Target · 2026-09-04 — A wedged suite is bounded at the spawn site, not by a global run killer

**Context:** sc-2393: a full 'bun run test:run' stayed alive 30-50 minutes in the single-worker git-integration project without emitting a final pass/fail aggregate, and the configured testTimeout (150s) and hookTimeout (120s) neither stopped it nor named a test. Repository-wide validation could not produce a trustworthy completion result, so a story's verification was blocked on a run nobody could attribute. The mechanism is upstream and documented: vitest cannot service testTimeout while a SYNCHRONOUS spawn blocks the worker thread (vitest#8164), so a wedged command yields no failure, no file name and no aggregate — indistinguishable from a slow run. devkit already owned the remedy one layer down (the supervised test helpers own a command's process tree and report 124), yet 15 of the 24 files in that project bypassed it with raw node:child_process calls, none passing a timeout. The neighbouring axis had already been patched four times by raising ceilings, which never closes an unbounded spawn.
**Ruling:** Bound the SPAWN SITE, not the run — and bound it where a wedge is actually unattributable: the single-worker git-integration project named in vitest.config.mjs, whose trailing sequential group is what stalls an aggregate. Inside that project, a command that runs devkit's own CLI, a gate, or a shipped shell script, or a real git commit that DISPATCHES A HOOK, goes through the supervised helpers in cli/__tests__/_helpers.mts, which own the process tree and surface a wedge as an ordinary named test failure at exit 124. Leaf verbs (git add/init/config, mkdir, command -v, sh -n) stay raw. TWO carve-outs stay raw and only these: a test whose SUBJECT is the supervisor, and a test asserting a command's OWN 124 ceiling sentinel — supervising the latter gives its assertion two indistinguishable sources of 124, so it could pass while the behaviour under test had regressed. A carve-out passes a native timeout instead and names itself at the call site. The only run-level bound is a step-level timeout-minutes in CI, sized as a hang detector and nothing else.
**Consequences:**
- Positive: A wedged command now names the file that caused it, so a stalled validation run is an ordinary red test rather than an unattributable 50-minute mystery, and an agent can tell 'my change broke this' from 'the box is loaded'. CI can no longer burn GitHub's 6-hour default on one wedged run while still publishing its per-file artifacts. Cross-references [[test-deadlines-are-hang-detectors]]: that axis's own prescribed AST deadline rule has NOT shipped, and this record does not discharge it.
- Negative: A supervised call costs ~2.2x per invocation (measured 61.9ms to 136.8ms, because each boots an extra Node process), which is why the rule is scoped to one project and to hook-dispatching or devkit-machinery commands rather than to every spawn. The PARALLEL project is deliberately NOT converted: its raw CLI spawns can wedge a worker too, and only the CI backstop bounds them. The two carve-outs are unbounded by the supervisor by construction, buying sentinel clarity at the cost of the tree reap. A worker that stalls with NO live child process (vitest#9494's leaked-stdio shape) is likewise bounded only in CI. The step timeout is a hand-picked number that must be raised, never lowered, as the suite grows.
**Vision-fit:** n/a — internal tooling; devkit's own suite is the gate every consumer change passes through.
**Researched:** prior-art and feature-critique panels. Upstream: vitest#8164 (testTimeout not respected while a sync execSync blocks the runner thread), #9494 (leaked stdio needs a TREE kill, not child.kill), #10590 with the #10564 v4 backport (worker-crash stranding, already fixed in the pinned 4.1.10), #9751 (upstream has no run-level timeout and no open request for one; the de-facto answer is an external timeout-minutes). Measured locally: the git-integration project alone runs 39m16s GREEN solo on an idle box (24 files, 700 passed, exit 0), so the report's 30-50 minutes with no aggregate describes a HEALTHY run — vitest emits the aggregate only at the very end, which is why forward progress and a wedge look identical from outside. On CI the Tests step measured 24m40s-31m56s across the six runs preceding this change.
**Rejected:** (a) A global no-progress watchdog over the run — DEFERRED: it would be the fifth patch on this axis and still could not name a blocked sync spawn any better than the spawn-site bound does. (b) A fixed wall-clock cap on the whole run — REJECTED: the sequential project legitimately runs 39 minutes solo, so any cap tight enough to be useful kills healthy runs, the false-redness class [[test-deadlines-are-hang-detectors]] exists to end. (c) Supervising EVERY raw child_process call in the test suite — REJECTED: measured 2.2x per call across hundreds of sites, which would lengthen the very run this ticket complains about; the scoping above is the deliberate alternative. (d) A job-level CI timeout — REJECTED: it cancels the job and puts the if-always per-file artifact uploads at risk, destroying the attribution [[ci-emits-per-file-test-results]] depends on. (e) An absolute ruling with no carve-outs or scope — REJECTED after the ship gates blocked two drafts of it: a reviewer read the deliberate-124 carve-out as a violation, then the completeness judge read an unsupervised hook-dispatching commit as one. Both were right about the RECORD, not the code.
**Revisit-when:** A full-suite run stalls with no live child process in the worker (vitest#9494 shape), the parallel project produces an unattributable wedge, or upstream vitest ships a run-level deadline
**Scope:** cli/__tests__/**,.github/workflows/gate.yml
**Source:** shortcut · sc-2393

## Target · 2026-09-29 — Wedges stay bounded at the spawn site; the git-integration files share the suite's worker pool

**Context:** The single-worker git-integration project, introduced so git-heavy files would not manufacture load, ran as a trailing sequential group after the whole parallel project. It dominated wall time: CI Tests took 44 min (run 36632570982, ~27 min in the 1-worker tail) and local full runs sat 30+ min in it, stalling pre-push, ship and every story's validation on the one worker. The serialisation bought nothing the spawn-site bound did not already provide: no file shares state (mkdtemp fixtures, sandboxed git config/XDG, locks keyed on the temp repo), and ~30 equally git-heavy ship/review files already ran concurrently in the parallel project.
**Ruling:** Bound the SPAWN SITE, not the run. The files named in GIT_INTEGRATION_TESTS (vitest.config.mjs) run in the SAME worker pool as the parallel project — both projects read one SUITE_WORKERS constant, so they form a single task group and no groupOrder is set. Inside those files, a command that runs devkit's own CLI, a gate, or a shipped shell script, or a real git commit that DISPATCHES A HOOK, goes through the supervised helpers in cli/__tests__/_helpers.mts, which own the process tree and surface a wedge as an ordinary named test failure at exit 124. Leaf verbs (git add/init/config, mkdir, command -v, sh -n) stay raw. TWO carve-outs stay raw and only these: a test whose SUBJECT is the supervisor, and a test asserting a command's OWN 124 ceiling sentinel; a carve-out passes a native timeout instead and names itself at the call site. A load-sensitive test whose product ceiling can fire before setup completes is fixed by RAISING that ceiling, never by serialising. The only run-level bound is a step-level timeout-minutes in CI, sized as a hang detector.
**Consequences:**
- Positive: A wedged command still names the file that caused it, and the suite no longer spends most of its wall time on one worker: local full runs went from 30+ min to 18.2 min (0 failures), and CI's projected Tests step drops from 44 to ~32 min at the same 2-worker concurrency it already ran.
- Negative: Up to SUITE_WORKERS git-heavy files now run at once (5 on a 10-core box), so a test whose correctness depends on setup finishing before a product ceiling is exposed to more intra-run load; review.test.mts's asset-wedge ceiling was raised 30s to 90s for this, adding ~60s of idle wait that overlaps other files. Both projects must share one maxWorkers value — vitest throws when one groupOrder mixes them — so the git files cannot be capped separately. The PARALLEL-only files remain unsupervised, bounded only by the CI backstop, as before.
**Vision-fit:** n/a — internal tooling; devkit's own suite is the gate every consumer change passes through.
**Researched:** prior-art and feature-critique panels. vitest 4.1.10 installed source: cli-api executeTests awaits task groups sequentially; groupSpecs sends an isolated order-0 maxWorkers===1 project to a trailing sequential group and throws when one groupOrder mixes maxWorkers; VITEST_MAX_WORKERS overrides fileParallelism:false. vitest.dev/config/sequence claims projects run in parallel by default — the doc/source mismatch that misled sc-1263. PR #508 (sc-2288) found the trailing group but only fixed a comment. CI run 36632570982 report.json per-file timings.
**Rejected:** (a) git-integration at maxWorkers:3 with an explicit groupOrder:1 — LOSES on wall time: keeps a trailing group (~9-12 min on CI) and runs 3 git-heavy files at a concurrency CI never exercised. (b) Moving the ceiling tests into a trailing 1-worker serial project — LOSES: ~2.6 min of idle serial tail, shields only from its own run not machine load, resurfaces an anti-slop baseline entry and invites a double-run via TEST_INCLUDE. (c) Raising 'parallel' above 50% in config — LOSES locally: three queued runs already put 15 workers on 10 cores; raise per-run via VITEST_MAX_WORKERS instead. (d) Lowering timeouts or product ceilings — REJECTED: the dev box genuinely overloads, and test-deadlines-are-hang-detectors permits raises only.
**Revisit-when:** A git-integration file fails only when pooled (never solo), a full-suite run stalls with no live child process in the worker (vitest#9494 shape), or vitest ships per-project worker caps within one task group
**Scope:** cli/__tests__/**,.github/workflows/gate.yml,vitest.config.mjs
**Source:** collab
**Evidence-change:** The prior Target's scoping premise was false: vitest 4.1.10 source (cli-api groupSpecs/executeTests) shows a maxWorkers:1 project is awaited as a separate TRAILING group, not run beside 'parallel' as abb73aef assumed; measured on CI run 36632570982 that tail was ~27 of 44 min. A collision scan of all 31 files found no shared state, and a full local run with them pooled was green (18.2 min, 0 failures, up to 5 concurrent git files).

## Target · 2026-09-30 — Wedges stay bounded at the spawn site; git-integration files share the pool except named pooled-only failures

**Context:** Pooling the git-integration files cut CI's Tests step from 44 to 25-34 min, but turned main red: review-gate-supervisor.test.mts's pending-trap signal cases fail on every pooled Linux run. Each failure spends the full drain bound in run-gates-with-capture.sh and still sees tee running after TERM and KILL, i.e. a scheduling-dependent race in the signal/drain path, not a slow setup a raised ceiling would absorb. The tests are skipped on macOS (no bash >= 4), so local runs cannot see it.
**Ruling:** Bound the SPAWN SITE, not the run. The files named in GIT_INTEGRATION_TESTS (vitest.config.mjs) run in the SAME worker pool as the parallel project via one SUITE_WORKERS constant, EXCEPT files listed in POOLED_FAILURES, which run in a trailing git-serial project (maxWorkers 1, explicit sequence.groupOrder 1 so VITEST_MAX_WORKERS cannot fold them back into the pool). A file enters POOLED_FAILURES only on evidence that it fails when pooled and passes solo, and a failure that a raised ceiling would absorb is fixed by raising instead. Inside every GIT_INTEGRATION_TESTS file, a command that runs devkit's own CLI, a gate, or a shipped shell script, or a real git commit that DISPATCHES A HOOK, goes through the supervised helpers in cli/__tests__/_helpers.mts, which own the process tree and surface a wedge as a named test failure at exit 124. Leaf verbs stay raw. TWO carve-outs stay raw and only these: a test whose SUBJECT is the supervisor, and a test asserting a command's OWN 124 ceiling sentinel. The only run-level bound is a step-level timeout-minutes in CI, sized as a hang detector.
**Consequences:**
- Positive: Main returns to green while keeping the pooled wall-time win (CI Tests ~25-34 min instead of 44), and a wedged command still names its file.
- Negative: POOLED_FAILURES runs after the pool, adding ~1 min of serial tail on CI (review-gate-supervisor: 54-70s). Serialising hides the underlying signal/drain race from the suite instead of fixing it; it is tracked as a product defect and the file leaves POOLED_FAILURES once that race is root-caused. The list is a second place a git file can be named, so GIT_INTEGRATION_TESTS stays the supervision source of truth.
**Vision-fit:** n/a — internal tooling; devkit's own suite is the gate every consumer change passes through.
**Researched:** CI logs of runs 36644089373, 36644541122, 36645862444, 36645866590 (post-pooling) vs 36632570982, 36631016409, 36630886009 (pre-pooling: the same cases pass in ~0.6-1.2s). Local verification that git-serial starts only after the pool drains, including under VITEST_MAX_WORKERS=4.
**Rejected:** (a) Reverting the pooling — LOSES ~10-19 min per CI run to protect one 70s file. (b) Raising run-gates-with-capture.sh's 5s drain bound — INEFFECTIVE: the failing runs reach the KILL stage with tee still listed running, so more time does not change the outcome. (c) An order-0 maxWorkers:1 project without explicit groupOrder — REJECTED: VITEST_MAX_WORKERS lifts it above 1 and silently folds it back into the pool.
**Revisit-when:** The signal/drain race in run-gates-with-capture.sh is root-caused and fixed (then empty POOLED_FAILURES), a POOLED_FAILURES file also fails solo, or a second file fails only when pooled
**Scope:** cli/__tests__/**,.github/workflows/gate.yml,vitest.config.mjs
**Source:** collab
**Evidence-change:** The prior Target's Revisit-when fired: cli/__tests__/review-gate-supervisor.test.mts failed in 4 of 4 Linux CI runs once pooled (36644089373, 36644541122, 36645862444, 36645866590; varying pending-trap tests) after passing every prior run at 1 worker in ~1.1s per case. The failing cases take ~7s: the 5s drain, then TERM and KILL stages, with the job still listed running, so raising a ceiling cannot fix it.
