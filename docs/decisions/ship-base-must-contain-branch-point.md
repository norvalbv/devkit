# ship-base-must-contain-branch-point

## Target · 2026-09-04 — ship refuses a --base that does not contain the work's branch point, before any gate runs

**Context:** devkit ship proved only that --base named a branch on origin, then cut the ephemeral gate worktree from that base tip (ship-branch.sh:1122), so every gate judged a foreign base tree plus the briefed patch. An autonomous report (aaccc36d -> sc-2357, severity medium) recorded a worktree whose branch point sat on origin/0.0.11 while the harness environment block named main as the PR base; origin/main was 80 commits behind on that line and did not contain the branch point. Three consecutive ship attempts died on gates unrelated to the change. guard-size reported 42 files over ceiling, none of them the agent's, because the shipped .devkit/baselines/size-lines.json carried ceilings ratcheted on the other line. assertBaselineTrackable then threw a hard stop recommending devkit init/upgrade, because the base commit predated the tracked .gitignore negations that un-ignore .devkit/baselines/ -- a remedy that would have pulled a repo-wide config change into an unrelated PR. guard-clone reported 12 new clones that exist only across the two lines. Every failure was internally consistent, so the agent fixed them: it wrote 12 guard-dup-allowlist add-clone entries with full justifications and reverted all 12 on finding the real cause. The cost was three gate chains plus up to six LLM reviewers each, and shared gate configuration one un-reverted commit away from permanently suppressing clone detection for pairs that were never duplicated.
**Ruling:** ship refuses a --base that does not contain the commit this checkout is built on, before the drift advisory, before staging and before the gate worktree. The predicate is CONTAINMENT: ship_origin_ancestor_branch -- tier 1 of ship_origin_base_candidate, split out so it answers an oid and is allowed to answer nothing -- names the nearest branch on origin that HEAD sits on top of, and the refusal fires only when merge-base --is-ancestor of that oid against the PINNED base oid answers no. The commit distance, the branches that do contain the branch point, and a copyable --base are narrated in the message; none of them is the trigger. Every cannot-tell fails open: a shallow clone skips the check entirely, a git exit other than 0 or 1 prints one line and proceeds, and no origin ancestor means the check has no input and stays silent. GUARD_SHIP_BASE_OK=1 overrides for one run and states what the override costs. Two adjacent surfaces are corrected with it: ship_suggest_base offers the ancestor branch before origin's default, in wording distinct per tier so a candidate is never announced as the default; and assertBaselineTrackable names base selection and the overlay exclude as causes only inside a ship gate.
**Consequences:**
- Positive: A wrong base costs one attributed message instead of a gate chain. The failure this ends is not slowness but MISATTRIBUTION: every symptom pointed away from the cause, so the correct-looking response was to suppress real gates, and the incident's twelve clone-allowlist entries would have survived as permanent holes in duplicate detection had the agent not found the cause. The refusal names the branch point, the branches that carry it and the base to pass instead, which is the fact the reporter had to reconstruct by hand. Fixing ship_suggest_base removes devkit's own contribution: the hint printed when a checkout's branch is not on origin -- the shape of every provisioned worktree -- recommended origin's default branch, which is how work cut from a release line gets told to ship into main.
- Negative: Four costs are paid knowingly. (1) Detection reads refs/remotes/origin, so a narrow remote.origin.fetch that never mirrored the work's line leaves nothing to compare against and the incident reproduces undetected; there is no name-free substitute, because distance is symmetric with a long-lived branch and a count trigger is barred on the sibling axis. (2) reship.sh takes the same --base, pins it the same way and cuts the same worktree, and is NOT covered. (3) A deliberate cross-line PR -- a release merge-up, a stacked PR onto a topic branch already on origin -- must now pass the hatch. (4) The nearest-ancestor scan moves onto every --base ship; it was rewritten as one for-each-ref --merged plus rev-list over the ancestors, replacing a merge-base spawn per origin ref, which is the cost base-drift/resolve-base.mts declined to port.
**Vision-fit:** n/a -- internal devkit tooling (ship pipeline correctness), not a product surface. Stays inside devkit-gates-repo-not-harness: the subject is the consumer repository's own base, diff and staged set, and no carve-out is consumed or widened.
**Researched:** Verified against real git and against the reported evidence rather than reasoned about. A prior-art pass reached its github and web legs and returned no solution to adopt: gh validates only that a base EXISTS (cli/cli#12996 and #8979 are both open, and #12996 describes this repository shape verbatim -- parallel release branches, temporary feature branches, no single base), and git's own merge-base --fork-point is disqualified twice by its man page for this environment, being reflog-dependent and documented not to find the fork point when the branch was cut from an older commit than the tip. Peer tools attack the base's PROVENANCE instead: git-machete's github create-pr uses the inferred parent branch and never accepts a base, and Gerrit's git-review reads defaultbranch from a committed .gitreview. The local reference-checkout leg could not run at all -- guard.config.json declares no research.referenceCheckouts -- which is recorded here rather than laundered. In-repo, the sc-2451 payload fix was confirmed NOT to cover this: it changed the staging anchor, while the worktree is still cut from the base at ship-branch.sh:1122 and both ratchet baselines are tracked files, so the cascade still reproduces. A feature-critique panel returned PROCEED_WITH_CHANGES and supplied three corrections that are now part of the ruling: the two-tier resolver had to be split, the probe had to run against the pinned base oid rather than the remote-tracking cache, and a shallow clone had to skip rather than refuse.
**Rejected:** (a) Reusing the ancestry predicate devkit already has twice -- merge-base --is-ancestor BASE HEAD at ship-branch.sh:483 and reship.sh:435 -- REJECTED: it demands the base be CONTAINED IN HEAD, and a base that has advanced past the fork point is the normal case on this arm, so it would refuse nearly every legitimate ship. The converse is the correct question. (b) Triggering on the commit distance or on sha inequality -- REJECTED per base-drift-surfaced-at-read-time Rejected(b): in a shared parallel-agent checkout HEAD never advances as PRs merge, so a count-keyed signal is permanently red and gets tuned out. The distance is narrated and never fires. (c) Promoting the base-drift path-overlap advisory to a block -- REJECTED for the fourth time, and not re-litigated here: that advisory answers a different question and is correctly silent in this incident, since silent=no-overlap is set when nothing briefed moved on the base. (d) Reading ratchet baselines from the caller's tree instead of the gate tree, which would have muted the guard-size half -- REJECTED: the gate tree IS the base tree by design, and sourcing baselines from elsewhere would mask a genuinely wrong PR target instead of reporting it. (e) Covering reship.sh in the same change -- REJECTED as scope, deliberately and not by oversight; the precedent is ship-patch-anchored-at-fork-point Rejected(e). (f) The ticket's fourth acceptance criterion, warning when the base diff touches files outside the briefed paths -- REJECTED: that is the path-overlap signal (c) refuses, and the refusal removes the case it was meant to explain. (g) Deriving the base outright instead of validating a supplied one, as git-machete and Gerrit do -- NOT TAKEN NOW: it is a larger change to ship's contract, and the hatch's usage rate is the evidence that would justify it.
**Revisit-when:** A consumer reports the narrow-fetch-refspec blind spot allowing a wrong-base ship through, OR a wrong --base reaches reship.sh and reproduces the cascade there, OR GUARD_SHIP_BASE_OK shows up routinely in real runs -- which would mean cross-line PRs are common enough that DERIVING the base (Rejected (g)) beats validating a supplied one.
**Scope:** cli/lib/ship/origin-base.sh,cli/lib/ship/ship-branch.sh,gate-engine/ratchets/git-index.mts
**Source:** shortcut · sc-2357
- 2026-09-04 — An edge-case pass found three defects in the first implementation, two of which would have silently disarmed the check. (1) The hatch was read with a bare non-empty test, so GUARD_SHIP_BASE_OK=0 -- which envFlag/envBool in gate-engine/config.mts, and therefore every other devkit surface, reads as OFF -- DISABLED the refusal. A guard that vanishes when an operator or a CI profile spells "off" the way the rest of the tool spells it is worse than no guard, because the run still looks guarded. origin-base.sh gains ship_truthy, the shell mirror of envFlag, and it is the predicate any future GUARD_* read in these scripts should use: this was the first one in the ship shell, so there was no local precedent to copy. (2) The contained-by list was enumerated with %(refname:short), which renders refs/remotes/origin/HEAD as the bare string `origin` -- so the skip written against "origin/HEAD" never matched, the symref was listed as though it were a branch, and it consumed one of the four slots a real branch needed. It now enumerates %(refname) and shortens for display, the same predicate ship_origin_ancestor_branch already used. (3) A slashed candidate and a slashed base were untested end to end; they work, and are now pinned. Also pinned: the refusal fires from a DETACHED checkout, which is not incidental -- --base is the one arm that accepts one, since the branch-name probe only runs when no base was given, so every provisioned worktree cut detached and handed a base by its harness reaches this check.
- 2026-09-04 — Ship's own correctness reviewer found three holes in this Target's first implementation, and two of them let the refusal be bypassed. (1) The predicate short-circuited on NAME equality -- `cand = base_ref` returned success without probing. That looks like proof the base is right and is not: the candidate oid comes from the local tracking ref and the base oid from this run's fetch, so a force-push between them leaves the two names equal while the pinned base no longer contains the branch point. The shortcut waved through the one case that needed the probe most. It is gone; every ship pays one extra spawn, and a base that merely advanced answers 0 immediately. When the candidate IS the requested base the message drops its "pass --base X" line -- that would name the base the caller already passed -- and says the base moved off the branch point instead. (2) Unrelated histories are no longer waved through. Sharing NO ancestor is the strongest possible answer of "this base does not contain the branch point", and letting it pass meant an unrelated base bypassed the very refusal this Target exists to make. The earlier reading -- that an unrelated tree fails obviously rather than plausibly, so shipping onto an orphan base should stay free -- does not survive the consistency argument, and the deliberate case is what GUARD_SHIP_BASE_OK is for: ship-base-preserves-base-changes' unrelated-base fixture now sets it, which also documents that path as an override rather than an accident. (3) ship_origin_head_branch read the caller's cwd instead of the repo it was handed, so ship_suggest_base with a repo path could recommend a DIFFERENT repository's default branch as this one's base; it now takes the repo like its siblings. All three came from the reviewer fleet rather than from the edge-case pass, and the second one also corrected a test of mine that had been passing only because the name shortcut masked a base oid the fixture never made an ancestor.
- 2026-09-04 — A second reviewer round found two more, and recorded one design consequence worth stating rather than discovering later. (1) The check re-read HEAD while ship had already PINNED CALLER_HEAD before staging. In the shared parallel-agent checkout this whole feature is about, a sibling can switch or reset the checkout mid-run, so the refusal could describe a line the rest of the ship never touched. ship_origin_ancestor_branch and ship_base_contains_branch_point now both take the head to reason about, and ship-branch.sh passes CALLER_HEAD. (2) A test helper wrapped the resolver in ` true`, which converts every nonzero exit into the valid empty-result case -- so the "answers NOTHING" test would have passed had the function crashed. It asserts the exit code beside the output now: no answer is exit 1 with empty stdout, and anything else is a defect wearing the same clothes. (3) The completeness judge recorded, without blocking, that a ship from an already-pushed feature branch reads as a cross-line ship: HEAD sits on origin/<feature>, which origin/main does not contain, so the check refuses. That is accepted rather than fixed. The refusal names origin/<feature> and suggests it as the base, which for a stacked PR is the correct target -- GitHub stacks target the parent branch -- and a caller who genuinely wants the mixed diff against main has GUARD_SHIP_BASE_OK. Narrowing the predicate to exempt "my own pushed branch" is not possible without a notion of ownership the tool does not have, and the incident's origin/0.0.11 is structurally identical to a stack parent.
- 2026-09-04 — A third reviewer round closed the pinned-head fix properly and produced one verified FALSE finding worth recording so nobody re-opens it. (1) CALLER_HEAD is now pinned BEFORE the default-arm base probe rather than after it, because ship_suggest_base reasons about HEAD too and a sibling reset between the probe and that hint would retarget the caller's PR; both consumers take the pin as an argument. (2) An unreadable pin no longer falls back to a live read on the BLOCKING path -- `${CALLER_HEAD:-HEAD}` would have decided the ship on a commit nobody in the run reasoned about, so the check is skipped instead, like every other cannot-tell. The advisory hint keeps the live fallback deliberately: it runs on a path that is already refusing, where a slightly stale name beats no name. (3) REJECTED, measured rather than argued: the reviewer held that `--merged "$head"` parses its argument as a ref pattern and leaves the filter on live HEAD. On git 2.50.1 the detached and attached spellings return byte-identical results, and both differ from a live-HEAD filter -- so the claim is false and the code was never broken. The attached `--merged=<oid>` form is adopted anyway: it costs nothing, it is unambiguous under any parser, and the alternative was arguing with a reviewer about git's option grammar on every future run.
- 2026-09-04 — The advisory hint's live-HEAD fallback is withdrawn, correcting the previous note on this axis. An empty pin now skips the ancestor tier outright instead of re-reading HEAD. The earlier reasoning -- advisory path, already refusing, a stale name beats no name -- optimised for a richer message over the cannot-tell contract, and it was wrong on its own terms: naming a base derived from a commit this run never reasoned about is, in a shared checkout, naming a SIBLING's branch, which is exactly the unusable remedy sc-2261 built this file to end. The "no name at all" worry was unfounded too: the origin-default tier does not depend on HEAD, so a caller with an unreadable pin still gets an answer, just an honest one.
