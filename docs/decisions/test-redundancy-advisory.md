# test-redundancy-advisory

## Target · 2026-11-16 — devkit test-redundancy reports changed lines no test catches and fallow's per-test kill evidence, advisory only

**Context:** Agent-written PRs added tests whose every detectable failure another test already caught. benord-labs/frink#441 shipped 12 tests for a 15-line deletion and 4 were later removed by hand. The only control was a self-attested prompt rule (every extra test must name the distinct failure it catches), which the agent satisfied in prose for each redundant test. Every pipeline signal rewards adding tests: the diff-coverage gate, the evidence line's count of red-failing tests, and the critique schema's not-covered edge cases. Nothing measured whether a new test catches anything another test does not, or whether the changed lines are caught at all. Owner decision 2026-11-16: a new test is redundant when any existing test, unit or integration, already catches the same failures.
**Ruling:** devkit test-redundancy runs one fallow mutation --kill-matrix-for on the test files a change touches, against the production files it touches (or the paths named after --), with the repo's own full runner config and --allow-dirty, uncapped. From that run it prints two things. First, not caught: mutants that survived or that no test reaches, only on lines the change added or modified, the first 10 then a count, always with how many changed-line mutants ran out of how many were planned, and a statement when the time budget left some unrun. Second, fallow's candidates as redundant and its coverage_without_kills as kills nothing, only for targets whose evidence fallow marks complete; it lists every flagged test in those files and does not say which tests the change added. A target with incomplete evidence, a fallow older than 3.40.0, a missing fallow, a fallow refusal, a wrong argument, an unresolvable base or a git failure prints not judged with the reason. The command always exits 0. fallow owns the verdict vocabulary; devkit never re-derives redundancy from raw kill counts, and redundant is a review prompt, never a deletion instruction.
**Consequences:**
- Positive: An agent or reviewer can measure, before shipping, whether changed lines are caught and whether a test protects anything, instead of asserting it. A test written to kill an uncaught mutant cannot be redundant, so the stronger signal does not reintroduce pressure to add tests for their own sake. A cut-short or partial run reads not judged and names how many changed-line mutants ran, never a pass.
- Negative: Comparing against the full suite is slow on a large consumer: on benord-labs/frink at d5b2236e, 242 mutants over 4 files did not finish in 15 minutes with fallow 3.41.0 and no test was judged, while a 3-test project finished in 1 second. The run is not capped or scoped to changed lines, because either removes the redundancy verdict. Some surviving mutants are equivalent and cannot be killed. Tests that guard data or a removal kill no mutant and need a human reason. fallow does not compute subsumers in target mode, so the report cannot name which test makes another redundant. A change that touches no test file stops before fallow runs, so its uncaught lines are not reported. Until the pinned fallow reaches 3.40.0 every devkit-installed consumer reads not judged.

Measured with fallow 3.41.0: --max-mutants makes the run partial and empties candidates while survivors are still reported; --changed-since with no paths planned no mutant for a change whose tests exercise unchanged code; uncapped whole-file runs give both candidates and survivors. **Rejected:** (a) A prompt rule alone: it existed and was satisfied in prose. (b) Restricting the run to unit test files: minutes instead of an hour, but it contradicts the owner decision and fallow marks the run partial and names no candidates. (c) Marking the tests a change added by matching titles to added lines: three review rounds each found another way to mislabel a pre-existing test, and fallow reports no test line numbers. (d) A blocking gate: incomplete evidence is common under load, so a block would flake. (e) Re-deriving redundancy from unique_kills when fallow withholds candidates: equal kill sets would be misread. (f) Capping mutants or scoping the run to changed lines, as the industrial deployments do: measured, a cap removes every redundancy verdict and changed-line scope leaves the tests unjudged. (g) A second, capped fallow run for uncaught lines only: it doubles the suite warm-up on the consumers where time is the problem.

Counts only: no test id, path, planted-bug text, fallow message, base sha or time budget is recorded, because they are consumer content and no reader needs them. The row runs under its own test-redundancy-<uuid> agent run id, set after fallow ran so the consumer's suite never inherits it, instead of the commit fallback's git write-tree and run_mode commit. A DEVKIT_SHIP_ID or DEVKIT_REVIEW_ID already in the environment still wins, as it does for every envelope, so a run started inside a ship carries the ship's id and no run_mode, and one started inside a review carries the review's id with run_mode review.
