# ship-machine-wide-queue

## Target · 2026-09-30 — devkit ship waits for one machine-wide FIFO slot

**Context:** sc-3785: two devkit ship runs at once exhaust memory on the owner's machine, and ship had no machine-wide concurrency control. Every agent session wrapped its ship in a hand-written launcher polling pgrep -f 'devkit ship' every 20s. That gave no order (on 2026-09-24 one ship waited over an hour while later launchers took the slot), false waits (pgrep matches any shell whose text mentions devkit ship), double starts (two launchers see 'nothing running' in the same window), and no way to tell who is next.
**Ruling:** devkit ship itself takes ONE machine-wide slot before its first gate, in every mode (new, --resume, --pr, --dry-gates), served FIFO. The arrival number is allocated AND the waiting ticket published under one lock. The slot is an mkdir claim under ~/.devkit/ship-queue (DEVKIT_SHIP_QUEUE_DIR overrides), and EVERY slot mutation (claim plus ticket drop, dead-holder reap, release, process-group registration, guest join/leave, gate-log note, and the --queue read) runs under one shared queue lock (queue/queue-lock.mts). That lock is a directory renamed into place already holding one file NAMED by the holder's nonce: it is never ownerless, nothing can be renamed onto it while held, and a dead holder (pid + start identity) is reaped by renaming exactly <lock>/<nonce> away and then rmdir, an atomic compare-and-delete. Slot liveness: the dispatcher's pid + pinned OS start-time identity, OR any live member of the ship's process group, OR any live nested guest. The group is registered by the acquirer's bash as its FIRST action (queue/slot.sh); if the claim no longer carries its token, or the group cannot be read, that bash refuses to run, so no gate ever runs untracked. The dispatcher's release leaves a still-live group or guest holding the slot; the acquirer's bash hands the slot on before --wait-ci polls unless a nested guest still runs, and announces whichever outcome happened. A nested ship skips the queue only while, under the lock, its inherited token names a live ancestor holder or holder-group member, and it then joins as a guest until it exits. The queue is default-on and env-controlled: DEVKIT_SHIP_NO_QUEUE=1 and an uncreatable queue root are the ONLY unqueued paths, each behind a banner and a telemetry row. A contended lock inside the wait loop retries at the next poll, and any other acquisition failure stops the ship. devkit ship --queue is the status view.
**Consequences:**
- Positive: Every QUEUED devkit ship is safe to run alongside the others: queued ships never overlap, start in arrival order, and a waiting ship says where it is and what it waits behind. Agents need no launcher, and a killed ship or killed lock holder cannot strand the queue or overlap its successor. The two unqueued paths (DEVKIT_SHIP_NO_QUEUE=1, an uncreatable queue root) CAN overlap other ships by design; each is announced with a banner and a telemetry row rather than left silent.
- Negative: Every ship on the machine now serialises, including ships of unrelated repos and light --dry-gates rehearsals. The slot is held through the reviewer fleet even if only part of a ship is memory-heavy, which nobody has measured. Liveness is an approximation: pid+start-time identity, plus kill(-pgid, 0), which a recycled process-group id could keep falsely alive until that group exits. Each ship pays extra node starts (~50ms each) to register its group and note its gate log; a ship whose dispatcher dies in that instant, or whose ps is broken, is refused and must be re-run. Every waiter's 2s poll and every --queue read take the queue lock briefly, and a crashed acquirer can leave a stray <lock>.new-* directory behind (harmless garbage). Windows has no process groups, so there the slot lives only as long as the dispatcher or a guest.
**Vision-fit:** n/a — internal tooling
**Researched:** The owner's ~/.config/vitest-queue/preload.mjs (lockf slots plus waiting tickets). docs/decisions/ship-artifact-and-process-lifetime.md (sc-2159 detached-group survival; the sc-2476 note rejecting a mutex that fails open silently). reship.sh rewrite_publish_lock_acquire and cli/lib/atomic-write.mts withLock for the mkdir-claim idiom. A feature-critique panel returned PROCEED_WITH_CHANGES. Successive rounds of the ship reviewer fleet then found: unfenced check-then-act windows and a fail-open on lock timeout; a spawn-to-registration window and a silent failed hand-off; withLock's unfenced reap between two reapers; a paused acquirer's unstamped lock and a rename-hand-back reap; a killed reaper wedging a reap lock; mixed-moment --queue snapshots; a dispatcher release under a live gate group; a nested ship overlapped after the outer ship's CI hand-off; a ps-failure pgid fallback. Each is closed by the design above. Measured: macOS ps -E hides the environment of platform binaries (/bin/bash showed no env, node did), so environment-token liveness cannot cover a bash-only tree.
**Rejected:** (a) A kernel lock held by a lockf/flock helper, as the vitest queue does: macOS ships only lockf(1), Linux only flock(1), Windows neither, and a helper-held lock dies with the node dispatcher while the detached gate group keeps running. (b) A per-repo guard.config.json knob: the slot is a machine property, so a repo that opts out still overlaps everyone else. (c) Timestamp-ordered tickets: Date.now collides at ms resolution and steps with NTP. (d) A bare DEVKIT_SHIP_SLOT=held marker: leaked into any shell, it is a silent bypass. (e) Token re-reads without a lock. (f) The dispatcher recording the group after spawn: a SIGKILL between spawn and record leaves an untracked tree. (g) Liveness via the token in process environments: macOS ps -E cannot see a platform binary's environment. (h) withLock (mkdir then stamp, age/pid reap): two reapers can delete a fresh lock, and a paused acquirer's unstamped lock is reapable. (i) A serializing reap lock: a reaper killed while holding it wedges all recovery. (j) Falling back to $$ when ps fails: it may not be a process-group id, so a live tree could read as dead.
**Revisit-when:** Someone measures which ship phase actually exhausts memory and it is narrow enough to slot alone, or the machine gains headroom for two concurrent ships.
