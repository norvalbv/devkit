# deterministic-gate-deadline

## Target · 2026-10-13 — Every deterministic gate runs under a hang-detector deadline; expiry blocks as could-not-run

**Context:** guard-deterministic spawned each gate with a blocking execFileSync and no timeout. On 2026-10-13 a consumer extra gate (bun run knip in frink-oss) stalled before exec on macOS (every sample in _dyld_start, 0s CPU) under load average ~35 and the chain waited 30+ minutes in silence; after a manual kill the gate was recorded as a verdict fail. Under devkit ship the chain was capped only by the 3600s SHIP_COMMIT_TIMEOUT, whose banner cannot name an extra gate. A plain git commit had no bound at all: one frink commit-mode chain in telemetry lasted 24,934s.
**Ruling:** runArgv passes a per-gate timeout to the one spawn site. Expiry is its own outcome, read from ETIMEDOUT before the exit status: the gate is accumulated as <label>(timed-out:Ns), it blocks in every mode, and telemetry records could_not_run, never fail. It is not an opt-out, so failOpen2, rcLabels and GUARD_DETERMINISTIC_STRICT do not apply and the (could-not-run) suffix stays reserved for a rejected opt-out. Later gates still run and aggregate. The deadline is GUARD_GATE_TIMEOUT_MS, then guard.config.json gateTimeoutMs, then 1800000 ms; only a positive integer is accepted. It is a hang detector, sized above the slowest legitimate gate and raised, never lowered, when a legitimate gate approaches it. The kill is Node's native timeout: one SIGTERM to the direct child. No retry.
**Consequences:**
- Positive: A hung gate is stopped and named instead of holding a commit forever or a ship for an hour, the remaining gates still report, and a stall is no longer counted as a code finding in the fail rate. The remedy printed under the label says it is not a finding and names both knobs.
- Negative: The bound is not total. A child that handles SIGTERM without exiting still holds the synchronous call, exactly as before. A wrapper that does not forward the signal (sh -c, a node script using spawnSync, such as devkit's own related-tests) leaves its children running: the ship supervisor reaps them, a plain commit does not. At the 1800s default the originating stall would still take 30 minutes to surface; a repo with fast gates must lower its own gateTimeoutMs. A legitimately slow gate that crosses the deadline is blocked and must have the deadline raised.
**Vision-fit:** n/a — internal tooling; a gate that hangs a consumer's commit costs the trust every other gate depends on.
**Researched:** prior-art and feature-critique panels. Node docs and src/spawn_sync.cc: the sync timeout signals the direct child once with no SIGKILL escalation, and a fractional timeout throws ERR_OUT_OF_RANGE. Scratch runs on node 22.20 / bun 1.3.1: bun run takes its script down on SIGTERM and orphans it on SIGKILL; a child that exits 0 from its SIGTERM handler yields code ETIMEDOUT with status 0. Peers: lefthook per-job timeout (opt-in, group SIGKILL), nextest slow-timeout (group SIGTERM, grace, SIGKILL), GitHub Actions timeout-minutes; none uses a CPU-time watchdog. execa's sync mode has no force-kill, cleanup or detached. openai/codex#26795 reports the same _dyld_start stall from a syspolicyd/trustd loop. Telemetry, 30 days, 4735 whole-chain deterministic runs: 18 over 600s, 3 over 1800s; one devkit ship spent 1448s in the chain and passed, and devkit's related-tests ran about 32 minutes before reporting a real failure, which is why devkit's own guard.config.json sets 3000000.
**Rejected:** (a) A 600s default, as the report proposed — false-blocks legitimately slow gates under the same load that causes stalls, and a re-run under that load times out again. (b) killSignal SIGKILL — always returns, but cannot be forwarded, so every wrapped gate (bun run, npm run) orphans its script. (c) detached plus a group kill — reaps the tree, but takes the gate out of the terminal's foreground group so Ctrl-C on a plain commit leaves it running, and relies on an option undocumented for the sync API. (d) Nesting gate-supervisor per gate — adds a node boot per gate, remaps natural exit codes 124/129/130/131/143 to 1, turns a clean exit with a lingering child into 124 and overwrites the outer supervisor's ownership token. (e) A per-gate timeout schema in extraGates — the spread is between repos, not gates, and it would widen the label-to-command contract. (f) Fail-open on expiry — a gate that did not finish proved nothing. (g) Retry once — doubles the wait at a hang-detector deadline, and no peer tool auto-retries.
