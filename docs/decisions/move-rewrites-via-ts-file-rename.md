# move-rewrites-via-ts-file-rename

## Target · 2026-09-28 — devkit move decides each import rewrite at write time with TypeScript's resolver

**Context:** devkit move (sc-1133) computed new module specifiers itself: it matched importers on extensionless file paths and forced every rewrite into @/ alias form, and it always joined the destination with the source basename. A folder rename therefore nested (dest/<dir>; a/index.tsx -> b/index.tsx/index.tsx), importers that reached a moved folder through its implicit index (export * from './Dir') were never rewritten and dangled, barrels lost their sibling-relative style, and the command printed success over a tree that failed typecheck. Severity high: the codemod exists to make moves safe for agents, and it silently corrupted consumer repos.
**Ruling:** Rewrites are decided per file at write time, from the file's live contents. Every module specifier (import/export, import-equals, import() types, dynamic import(), vi.mock / vi.doMock / jest.mock / require and kin, recognised from the AST rather than text) is resolved with TypeScript's own resolver against the PRE-move tree and the compiler options of the file's own project; one whose importer or target moved is respelled only if it no longer reaches that target, keeping the written style: relative stays relative, an alias keeps its own prefix or falls back to relative, an implicit index stays implicit, a written extension or index stays written. sc-3016's alias wall holds: an alias is never written from outside its root (never `@/../`), and a relative path that was relative only because its target sat outside every root becomes an alias once the target moves in. Config (extends, references, every fallback target of a paths entry) is read and validated before anything moves, and any diagnostic but 'no inputs' is fatal; in a references build every project keeps its own compiler options and aliases, and each file is resolved and respelled with the options of the project that type-checks it (a file no project claims uses the first project that has files), so projects that resolve differently need no reconciling. The rewrite runs after git mv and reads each file right before writing it, so any spelling of a moved path, any import added during the move, and any source file added mid-move (inside a moved directory or anywhere tsconfig includes, found by re-walking it after git mv) is covered. CONCURRENCY CONTRACT: devkit move is a codemod in the class of prettier --write and eslint --fix, not a transactional editor. It takes no lock over the worktree, so it does not promise to see or preserve changes other processes make while it runs: a file written, renamed or deleted between devkit move reading and writing it, or a file created after its last scan of the tree, may be lost or left unrewritten. This is accepted deliberately and applies to every such interleaving, not one window: POSIX offers no compare-and-swap on file contents or atomic snapshot of a tree, so every guard tried (hash compare, rename-aside + link-in + rollback, descriptor compare-then-truncate, a second scan) only moved the window, and refusing to write would leave the moved tree with dangling imports. Reviewers should treat findings of that shape as this ruling, not as defects. What devkit move does guarantee: it writes only text derived from the bytes it just read, it re-walks tsconfig after git mv so files created during the move are normally covered, and it re-resolves every specifier it rewrote, exiting 1 on any that misses its target. Destination rule: a single file onto a destination with a source extension renames; a single directory renames only under --rename; everything else moves INTO the destination, as before. A tsconfig without paths is no longer an error.
**Consequences:**
- Positive: Agents can rename files and folders through devkit move and get a tree whose imports resolve, in the style the consumer already wrote, or a loud named failure instead of a false success.
- Negative: Changes other processes make while devkit move runs are not guaranteed to be seen or preserved (see the concurrency contract). Every specifier of every file in the tsconfig is resolved once per move, which costs more on large consumers than matching strings did. Imports that did not resolve before the move cannot be rewritten or checked and are only counted in a warning. A tsconfig option newer than the TypeScript bundled with ts-morph is refused as unknown, because it cannot be told apart from a typo. A failure after git mv leaves the moved files in place with imports unrewritten, as the pre-sc-1133 command did. Case-only renames on case-insensitive filesystems still stop at 'destination already exists'.
**Vision-fit:** n/a — internal tooling: keeps devkit's agent-facing codemod from corrupting the consumer repositories it runs in.
**Researched:** Prior-art subagent: TS getEditsForFileRename (typescript.d.ts; microsoft/TypeScript#24904, #25132) verified in scratch projects for implicit index, style preservation and dynamic import(); git-mv(1) two-form semantics. Feature-critique subagent: independently computed per-move edits collide on a file and its colocated test (scratch-confirmed).
**Rejected:** Hand-rolled resolution with forced @/ aliases: the failure itself. ts-morph SourceFile.move / Directory.move: leaves alias importers stale and layers its own reference update over TypeScript's. TypeScript's getEditsForFileRename (adopted first, then dropped in review): its edits describe a snapshot of the tree, so they either overwrite later edits or need a compare-then-write guard, and every such guard (hash check, rename-aside + link-in + rollback, descriptor compare) leaves its own window, since no POSIX API offers compare-and-swap on file contents; per-literal substitution maps applied later miss equivalent spellings. Deciding from the live text with TypeScript's resolver needs neither. git mv's rename rule for every single-source move: silently reverses the documented 'file into a new directory' form existing callers use. Requiring every project in a references build to share one resolution setup (tried in review): comparing raw options misjudges TypeScript's defaults, and computing effective ones needs internal TypeScript APIs; resolving per project needs neither.
