# gate-inputs-single-registry

## Target · 2026-09-30 — One registry for gate-input paths; ship, review and overlay derive from it

**Context:** The gate-input path list (every repo path a gate reads that a clean checkout can lack: untracked guard.config.json, overlay's git-excluded lint configs and baselines, ignored caches) was hand-maintained in about ten places: the GATE_PROJECTION_FIXED/CACHE_CANDIDATES bash arrays and a structure-baseline glob in link-gate-configs.sh, MUTABLE_ROOTS and SOURCE_VOLATILE_CACHES in the review projection runtime, FALLOW_CONFIG_FILES in the review baseline gate, and a separate 7-entry PACKAGE_ENTRIES/COPIED list in the overlay worktree projector against 21+ in ship. The copies drifted (G2/G4): an overlay linked worktree received a different gate-input set from ship and review, so the same commit ran against different inputs depending on which path built its worktree, and nothing failed loudly because a missing input makes a gate fall to defaults and pass.
**Ruling:** Gate inputs are declared once, in gate-engine/deterministic/gate-inputs.mts (gate-engine, so both gate-engine and cli/ can import it). Each entry is {path, kind: file|dir, share: branch|clone|checkout, mutable?, cache?, sourceVolatile?, overlayWrites?, eachFile?, field?}. gateInputs(root) yields the fixed entries first (eachFile dirs expanded per file, so a tracked file cannot hide an untracked sibling), then the config-driven indexPath/allowlistPath/decisionsDir resolved from guard.config.json through resolveFromCwd, skipping unset and out-of-repo paths. gate-config-paths.mts is the single shell emitter (all entries, one field, --cache, --each-file); link-gate-configs.sh keeps no path list, and ship fails when the emitter prints nothing (the registry did not load) rather than gating on defaults; the review projection's mutable/sourceVolatile flags derive from the registry, except the indexPath SQLite family (db, -wal, -shm), which the projection runtime flags through sqliteFamilyPath. A path another gate-engine module already owns (CONFIG_FILENAME, the ratchet baseline constants) is imported, never re-typed; the registry is itself the owner of CORRECTNESS_OVERRIDES_FILE and QAVIS_RECEIPT, which the correctness override valve and the qavis-advisory gate import from it; the cli-owned anti-slop and oxlint names cannot be imported into gate-engine, so a cli test asserts the registry contains them. The fallow config names are written once, in gate-engine/review/baseline-fallow-paths.mts, and the registry imports them: the review baseline gate runs from a frozen package runtime that cannot load guard.config.json, so the names live in a module that runtime already carries. Ship, review, overlay worktree projection, overlay excludes and clean all derive from this table (the overlay projector, excludes and clean move onto it next). share governs overlay linked-worktree projection only: branch is copied per worktree (ratchet baselines, fallow-baselines, eslint.config.devkit.mjs, the anti-slop baseline, and allowlistPath, because a tracked allowlist is branch-local in package mode and an entry lands with the code it covers), clone is linked to the home (configs, caches, decisionsDir since records are append-only, indexPath), checkout is never projected (the qavis receipt attests one checkout's HEAD). Ship keeps linking and review keeps copying into its private tree regardless of share. cache means content-addressed (a committed copy is stale and loses to the live one) and is only the qavis receipt. The anti-slop baseline stays immutable: only explicit create/prune/adopt commands write it, never a gate run. .devkit children outside the table (config.json, hooks, biome, tsconfig) are carried by overlay's .devkit merge rule, not listed as entries.
**Consequences:**
- Positive: One edit adds, removes or re-flags a gate input for every consumer at once, so ship, review and overlay cannot disagree about what a gate reads. A pinned registry test fails loudly when an entry is dropped, and an equality test ties the emitter output to gateInputs(). The config-driven locations still come from the consumer's guard.config.json (synced-assets-layout-agnostic holds), and the ship and review projected sets are unchanged.
- Negative: The shell callers spawn node for lists they used to read from an array (a few extra short node runs per ship). The review snapshot's candidate list gains the per-file structure baselines it previously omitted (inert unless one is a symlink). The registry is a coupling point: gate-engine owns a table that cli/ projection, excludes and clean depend on, so changing it is a cross-cutting change.
**Vision-fit:** n/a — internal dev tooling; gate parity across commit, ship, review and overlay worktrees is what makes a green gate mean the same thing everywhere.
**Researched:** Traced every hand-written list: link-gate-configs.sh:36-65 and its structure loop, runtime.mts:40-49, baseline-gate.mts:60-65, overlay-home.mts:30-43; the frozen review runtime module set (gate-engine/review/runtime.mts PACKAGED_REVIEW_RUNTIME_MODULE_STEMS); frink-oss overlay install (.devkit/config.json, .git/info/exclude) with 26 hand-made docs/decisions symlinks and linked worktrees holding a linked .devkit but no guard.config.json.
**Rejected:** (a) keep the bash arrays and pin them with a regex test — REJECTED: that pinned one copy while the overlay projector drifted. (b) put the registry in cli/lib — REJECTED: gate-engine has no production import from cli/, and cli/lib is at its fan-out cap. (c) make the anti-slop baseline mutable in review — REJECTED: no gate run writes it, so relaxing the drift check on a ratchet baseline would only weaken a guard. (d) list every .devkit child as an entry — REJECTED for now: the overlay .devkit merge rule already carries them, and ship/review do not read them. (e) have the baseline gate import the registry — REJECTED: that pulls config loading into the frozen review runtime.
