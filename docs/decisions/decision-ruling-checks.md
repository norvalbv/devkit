# decision-ruling-checks

## Target · 2026-10-11 — a Target may link one deterministic Check that runs at commit for its Scope

**Context:** Rulings reached agents only as advice. A 2026-10 study of devkit's own delivery found a briefed record opened in at most 8% of cases and the detect judge flipping on 22% of reruns, so a scoped ruling that a test already pinned was enforced only when that test happened to run before push or CI, and its failure never named the ruling. Feasibility was borderline and is restated as measured: of 8 violated-clause clusters, pre-existing tests caught 4; two narrow predicates written after seeing the violation brought it to 6 of 8 (the pre-registered floor); a third, crude identifier ban is not counted; one cluster cannot be checked. 15 of 83 scoped rulings (18.1%, Wilson 95% [11.3, 27.7]) are already pinned by a test and linkable today, under the 30% bar set beforehand. The gate therefore shipped on its own proof run, made through the real guard-deterministic on the built branch: the 3 canonical violations of the dogfood axes blocked with the ruling printed; 6 laundering commits (an unlink or a re-Target in the violating commit, on each axis) blocked through HEAD's Check; a replay of the 20 newest first-parent main commits touching each linked Scope (60 commits, the Check ran on 55; the other 5 fell outside that axis's Scope as recorded at the time) gave 0 blocks; each Check passed 10 of 10 runs under load (medians 0.32 to 0.56 s); the lexical query rank of the 3 axes did not move.
**Ruling:** A Target may link one deterministic Check: a command the repository already runs, recorded as a `**Check:**` note under the live Target by `guard-decisions enforce link`. Linking is refused when the axis has no Target or no Scope, or when the command fails on the current tree; `--check none` unlinks. When the decisions guard is selected, guard-deterministic's opt-in decision-checks gate runs the Check of every link whose Scope matches a staged file, or whose command names one, argv-split with no shell, no stdin and a 120 s bound, and prints the ruling when it fails. The link set is the union of HEAD and the commit index, so a commit cannot unlink, re-Target, rescope or re-link its way past its own violation: a ruling reversal lands as its own commit first. A new Target drops the link. This narrows alignment-judge-on-demand: a Scope alone still arms no gate, but a Scope plus an explicitly linked deterministic Check arms decision-checks. devkit adds no rule language; the brief and the judges are unchanged.
**Consequences:**
- Positive: A ruling a test already pins fails at commit, for its own Scope only, with the ruling text beside the failure, earlier than pre-push or CI; `guard-decisions enforce` reports which scoped axes are enforced and which are prose-only, and flags links a re-Target dropped or that can never run; the cheapest way to weaken a check, unlinking it in the violating commit, no longer passes.
- Negative: Checks execute commands written in markdown notes: the same trust boundary as package.json scripts and extraGates, with the command printed before it runs, and `devkit review` of a branch runs the links that branch added. Every decisions-guard commit pays one more node process (median +100 ms with no Checks, +161 ms with 3 links and a commit outside every Scope, measured at a load average of 11 to 15 on 10 cores), and a commit inside a linked Scope pays the Check's own run. A ruling reversal costs two commits. Checks judge the working tree, not the index; an advisory prints when unstaged edits sit in the Scope. Hooks of decisions-only selections gain the deterministic block on `devkit upgrade`. Whether printing the ruling changes agent behaviour, beyond a bare test failure, is unmeasured.
**Vision-fit:** n/a — internal devkit tooling. It stays inside devkit-gates-repo-not-harness: the gate judges the consumer's commit against the consumer's own command, never the agent's tooling.
**Researched:** archgate's rule API (https://cli.archgate.dev/reference/rule-api/): a rule that throws or exceeds its 30 s timeout exits 2, apart from 1 for a violation, and changedFiles is staged-only under --staged; this shaped the timeout reported as could-not-run and the staged-scoped run. A practitioner post on harness engineering (https://nyosegawa.com/en/posts/harness-engineering-best-practices-2026/) reports agents editing linter config to clear an error rather than fixing the code; this is the reason the link set includes HEAD and the remedy says not to weaken the check. The feasibility classification and the proof run are restated in Context.
**Rejected:** (a) A rule language inside the record: loses on precision, since 9.1% of rulings were fully static and prose-derived rules false-fired on 3 of 9. (b) extraGates-only opt-in: a Check named in a record would silently never run unless the repository also wired it in guard.config.json, and its failure could not name the ruling. (c) Running Checks inside detect --gate: ties a deterministic check to an LLM gate that fails open. (d) A Check field on the Target itself: changing it would force a re-Target, which buries the notes. (e) Reading links from the working tree only: a commit could unlink and violate at once. (f) The brief skipping linked axes: unmeasured, left to a follow-up.
