# gates-judge-commit-index

## Target · 2026-09-27 — Gates judge the index git is committing, not the default index

**Context:** The hook runs every gate under __dk_no_git_env, which unsets GIT_INDEX_FILE so a gate or a tool it spawns can never write a foreign repository's index over the commit's (the 896db20e ship index-clobber). Git hands commit hooks a non-default index in ordinary workflows: git commit -a / -i commit from <gitdir>/index.lock, git commit -- <path> from a temporary next-index-<pid>.lock, and GIT_INDEX_FILE=<alt> git commit from <alt>. With the variable scrubbed every gate read the default index: under commit -a a modified tracked file was invisible to size, structure, decisions and review, under a partial commit gates saw nothing, and git write-tree on the default index failed outright because git holds index.lock, so the prefix cache, run-context telemetry and the anti-slop snapshot could not form a tree at all. sc-2463.
**Ruling:** The hook exports a devkit-owned carrier before any gate runs: DK_COMMIT_INDEX_CAPTURE (cli/lib/husky/review-fragments.mts) sets DEVKIT_COMMIT_INDEX_FILE and DEVKIT_COMMIT_GIT_DIR only when the commit's index differs from the default one, compared as canonical paths (git exports .git/index relative on a plain commit, and /tmp/... where rev-parse reports /private/tmp/...). It is emitted in every hook flavour and the commit-msg block, before any monorepo cd, clears an inherited carrier first, and fails open. GIT_INDEX_FILE itself stays scrubbed for every child. devkit's own git calls opt back in through commitIndexEnv(root) in gate-engine/ratchets/commit-index.mts, which injects GIT_INDEX_FILE (plus GIT_OPTIONAL_LOCKS=0) only when root's canonical absolute git dir equals the carrier's, and never overrides a GIT_INDEX_FILE the caller chose. Ratchet baseline writes go to the carrier under commit -a and alternate indexes; under a partial commit best-effort staging leaves the baseline unstaged and strict migration staging throws with a remedy, because a write into next-index lands in the commit but reads as deleted from the real index afterwards. cli/__tests__/commit-index-hook.test.mts scans gate-engine and anti-slop for index reads that bypass commitIndexEnv.
**Consequences:**
- Positive: commit -am, commit -i, commit -- <path> and alternate-index commits are judged on the content they commit, and write-tree-based snapshots work while git holds index.lock. The ship clobber protection is intact because only devkit's own git calls against the exporting repository see the index; judges, fallow, qavis and every other child still run scrubbed. A plain commit and the ship linked-worktree path export no carrier, so their behaviour is unchanged. Negative: a lowered ratchet baseline is left unstaged during a partial commit and rides the next commit; external tools that read the index themselves (qavis --staged, fallow audit) still see the default index under commit -a, and LLM judges told to run git diff --cached do too — the staged evidence they are handed is correct, their own investigation commands are not.
- Negative: Opt-in per git call over restoring GIT_INDEX_FILE for the whole chain: more call sites to route, kept honest by a source-scan test, in exchange for never re-opening the foreign-repo index clobber.
**Vision-fit:** Gates judge the consumer repository's commit; a gate that passes content it never read is a silent fail-open, which devkit treats as worse than a loud failure.
**Researched:** pre-commit reads staged files with the inherited environment and applies no_git_env only when cloning into foreign directories (store.py; maintainer rejects a blanket scrub in pre-commit#1849); lint-staged deletes only GIT_DIR/GIT_WORK_TREE and handles index.lock and next-index pathspec commits explicitly (resolveGitRepo.js, gitWorkflow.js). Probed on git 2.50: hook GIT_INDEX_FILE per commit shape, write-tree failing under a held index.lock, partial-commit hook writes leaving D/?? in the real index.
**Rejected:** Removing GIT_INDEX_FILE from the scrub list: re-opens the 896db20e clobber for every child. Passing it to a subset of gates: sibling ratchets would read different indexes for the same commit. Failing closed on every non-default index: blocks git commit -am, the most common agent commit shape. Comparing index paths as strings: exports a carrier on every macOS commit made through a symlinked path.
**Revisit-when:** Git changes the GIT_INDEX_FILE it exports to hooks, a gate needs to write a partial-commit index, or qavis/fallow grow a way to be handed the commit index.
**Scope:** cli/lib/husky/**,gate-engine/ratchets/commit-index.mts,gate-engine/ratchets/git-index.mts,cli/lib/install/anti-slop/git-index-lock.mts

- 2026-09-30 — Every commit-message judge now runs with git's per-repo env scrubbed, in every install mode: the sentry ship prewarm at pre-commit, and completeness and sentry at commit-msg. The index rides DEVKIT_COMMIT_INDEX_FILE, which both hooks capture. Before, only overlay's commit-msg was scrubbed, and the overlay-self-heal 2026-09-28 note declined the overlay prewarm because the unscrubbed prewarm and the scrubbed replay could key different indexes. Scrubbing both sides removes that split. Cache keys still match, because check-sentry and completeness read the staged diff through commitIndexEnv. The parallel completeness start already relied on this: it ran scrubbed while package commit-msg did not, and its verdict is designed to be replayed from the cache. The package commit-msg block's bytes change. Doctor's commit-msg check compares sentinels only, so the new bytes arrive with the next init or upgrade.
- 2026-10-01 — sc-2759 brings the self-host skill-projection advisory (cli/lib/husky/skill-projection-integrity.mts) under this ruling. It read working-tree bytes, so inside a ship worktree, whose .claude/ prepare-gate-worktree.sh refreshes from the running package on disk only, it judged the package's copy and kept reporting .claude/skills stale after the corrective commit. It now freezes the commit index once (indexTreeRef), reads skills/, dist/skills, every provider dir, the skills manifest and config from that one tree via the new treeBlobsAtRef (one ls-tree plus one cat-file --batch, byte-exact, all through commitIndexEnv), and stands down with an unchecked finding when the index cannot form a tree. Working-tree reads remain only outside git; the two sources are never mixed in one run. The repair hint no longer tells agents to stage rebuilt tracked dist (sc-2467).
