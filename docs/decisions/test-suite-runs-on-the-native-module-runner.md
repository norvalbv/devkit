# test-suite-runs-on-the-native-module-runner

## Target · 2026-10-13 — devkit's tests load modules the way Node does, so in-process and subprocess coverage of one file add up

**Context:** With coverage.autoAttachSubprocess on, a module that one test imports in-process and another reaches through a spawned `node x.mts` child read wrong coverage in both directions. Measured: writeIfAbsent in cli/lib/fs-helpers.mts had 7 hits from its own suite, 564 from a suite that spawns `devkit init`, and 0 when both ran together; gate-engine/decisions/amend.mts read 104/145 statements against a true 130/145; depth/depth-pass.mts read 11/48 against a true 2/48. The trigger is any module a spawned process loads transitively. Cause: vitest's worker ran Vite-transformed text while the child ran Node's type-stripped text, and @vitest/coverage-v8 merges V8 profiles by script URL before converting them, so offsets into two different texts were merged as one. Agents reading coverage-diff saw executed added lines as uncovered and wrote redundant tests. Upstream calls the by-URL merge a known, accepted limitation (vitest #11541 open, #11476 closed), so waiting for a fix had no end date.
**Ruling:** devkit's own tests run on Node's module loading, not Vite's module runner. SHARED_TEST_CONFIG in vitest.config.mjs sets experimental.viteModuleRunner to false, and because that object is spread into every inline project each project carries the flag itself: a value set only at the root does not reach an `extends: false` project (measured: root-only placement left writeIfAbsent at 0). The worker then loads the same module text a spawned child and production load, so one script URL has one coordinate system and the provider's merge is correct. No coverage provider is patched, subclassed or replaced. cli/__tests__/vitest-config.test.mts pins the flag on every project and asserts, through a nested run of the real coverage block, that the hits of an imported-and-spawned fixture add up.
**Consequences:**
- Positive: Coverage of an imported-and-spawned module is additive and matches the per-context ground truth: writeIfAbsent 571 (7 + 564), amend.mts 130/145, depth-pass.mts 2/48, skills/_devkit/review-roots.mjs 169/207 paired against 168/207 alone (142/207 before). coverage-diff and test:run:coverage:changed can be believed for devkit's own diffs, and the tests execute the text that ships rather than a transformed copy.
- Negative: The fix rests on a flag vitest marks experimental. Tests lose what only the Vite runner provided: vi.resetModules (behaviour fixed at module load is tested in a spawned child instead), vi.spyOn on an ESM namespace and vi.doMock of Node builtins (pass a stand-in through a parameter of the code under test, or patch the builtin inside a spawned child), injected __dirname, .mjs-to-.mts resolution, plugins, alias and import.meta.env. A vi.mock factory that awaits importOriginal exposes its exports as undefined while importers evaluate, so code must not read a mockable module's export at import time (cli/lib/doctor/pin/pin-checks.mts now builds its lockfile patterns on use). Six test files were migrated to land this.
**Vision-fit:** n/a - internal tooling. devkit's own test harness, not a surface any consumer installs.
**Researched:** A prior-art pass and a feature critique. vitest docs config/experimental.md recommends disabling the module runner when tests run in the same environment as the code. Installed @vitest/coverage-v8 5.0.3 and 5.0.4 provider source (generateCoverage keys mergedScripts by script.url; unchanged on vitest main). Upstream issues #11541, #11476, #11533 (fixed in 5.0.4, needed for the native runner). A public consumer pairs this flag with autoAttachSubprocess under 100% per-file thresholds (BeOnAuto/runtime). Mocked modules were measured on both runners and read identically (cli/commands/update.mts 21/97, gate-engine/decisions/decisions.mts 4/134).
**Rejected:** (a) A bun-patched provider that converts each context separately and merges by index: proven in a scratch copy, but it carries provider internals across every vitest bump and was already declined on the coverage-gate axis. (b) A coverage.customProviderModule subclass: the same internals under another name. (c) Turning autoAttachSubprocess off: CLI modules driven only through spawned children fall back to near 0%. (d) Waiting for an upstream fix: the maintainers treat the merge as an accepted limitation. (e) Documenting the caveat only, the prior state: agents still chased gaps that were not there.
**Anchored-bet:** [BET]
**Revisit-when:** vitest removes or renames experimental.viteModuleRunner; OR vitest converts each context's profile separately so the Vite runner yields correct merged coverage; OR a devkit test needs a Vite transform that Node's loader cannot supply.
