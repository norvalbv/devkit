# overlay-self-heal

## Target · 2026-06-26 — overlay survives husky reclaim via a per-clone git ci alias; init freezes once

**Context:** Overlay sets core.hooksPath (local, uncommitted) to .devkit/hooks, but the repo's committed husky prepare resets it to .husky/_ on every bun install — silently unwiring devkit's gates with no error. The documented fix, re-running devkit init --overlay, made it worse: runFreezes re-snapshotted the size and fanout baselines unconditionally, so every re-apply grandfathered all accumulated debt and the ratchets quietly stopped catching new violations. Two silent failures in the one mode meant for shared repos a team won't modify.
**Ruling:** Overlay installs a per-clone LOCAL git alias (alias.ci, in .git/config, uncommitted, dies with the clone) that re-points core.hooksPath back to .devkit/hooks and then commits — it never re-runs init. And runFreezes is now freeze-if-absent: it freezes a baseline only when that baseline file is missing, so re-applying the overlay never re-snapshots an existing one. The explicit guard-size/guard-fanout freeze CLI still re-snapshots on demand.
**Consequences:**
- Positive: Gates stay wired across bun installs through a single git ci with zero committed footprint; the size and fanout ratchets keep catching new debt because the baseline is frozen once at bootstrap, not moved up on every re-apply.
- Negative: The alias only heals on a CLI git ci — a GUI client or plain git commit in the window between an install and the next git ci runs the repo's own hooks ungated; and a user who already has a ci alias (commonly a global commit -v) gets no auto-heal by design (skip-on-collision) and must re-point with git config core.hooksPath .devkit/hooks.
**Vision-fit:** n/a — internal tooling; overlay is how devkit runs guardrails on a shared repo a team would reject a PR for.
**Researched:** cli/lib/overlay.mjs (LOCAL_HOOKS, installOverlayHook); gate-engine/ratchets/size-disable.mjs and folder-fanout.mjs (freeze overwrites the baseline from the current tree); git shell-alias arg-append + top-level run semantics, validated empirically in throwaway repos; feature-critique pass recorded at .cursor/.feature-critique.md.
**Rejected:** (a) a shell precmd or package-manager wrapper hook — REJECTED: global to every repo and lives in dotfiles, not per-clone, breaking overlay's git-invisible local-only ethos; (b) the naive alias that re-runs devkit init --overlay before commit — REJECTED: re-running init re-freezes size/fanout every commit (grandfathering new debt) and resets the guard selection to all five via selectionFromFlags; (c) clobbering any existing ci alias — REJECTED: ci is a common global alias for commit -v, and shadowing it silently breaks muscle memory.
**Anchored-bet:** [VALIDATED]
**Scope:** cli/lib/overlay.mjs,cli/commands/init.mjs
**Source:** collab

## Target · 2026-06-29 — Plain git commit gap closable via an opt-in, uninstallable global husky init.sh shim

**Context:** Overlay's accepted gap bit in practice: the per-clone git ci alias heals only a CLI git ci, so a plain git commit or a GUI-client commit ran UNGATED after husky reclaimed core.hooksPath on a bun install. On frink this silently skipped devkit's gates — the exact silent-unwiring the original ruling set out to bound.
**Ruling:** Keep the per-clone git ci alias + freeze-if-absent as the invisible DEFAULT. ADD an OPT-IN machine-global husky init.sh shim (one marker block, via devkit init --overlay --global-commit-gate) that runs the overlay's pre-commit gates GATES-ONLY (a gates-only env flag makes the overlay hook stop before chaining, so husky's own _/h still runs the committed hook — no double-run) for any repo that has .devkit/hooks, resolving the repo root via git rev-parse (not cwd). It is a guarded no-op in package-mode / non-devkit / non-husky repos, honors HUSKY=0, and is removed by devkit clean --global (a per-repo clean LEAVES it, since one shim is shared across all overlaid repos).
**Consequences:**
- Positive: A plain git commit and GUI-client commits stay gated in every overlaid repo on a machine that opted in, surviving husky's reclaim across bun installs — no more silent un-gating and no reliance on remembering git ci.
- Negative: One opt-in machine-global file (~/.config/husky/init.sh) — a guarded no-op outside overlaid repos and uninstallable, but still the single piece of global state the per-clone ethos avoided. Two residual holes, both documented + doctor-warned: a husky repo with NO committed .husky/pre-commit cannot be covered (husky's _/h exits before sourcing init.sh), and the shim runs a repo-local .devkit/hooks/pre-commit (only in repos the user themselves overlaid, so no wider trust surface than husky's existing init.sh).
**Vision-fit:** n/a — internal dev tooling (overlay runs guardrails on a shared repo a team would reject a PR for).
**Researched:** Verified against husky 9.1.7: index.js sets core.hooksPath unconditionally on every prepare; .husky/_/h sources the XDG-aware ~/.config/husky/init.sh BEFORE running the committed hook, with an early exit when no committed hook exists and a HUSKY=0 exit AFTER the source. A feature-critique pass (PROCEED) confirmed the flow, the hook-name detection, abort propagation, and drove the cwd / no-committed-hook / HUSKY=0 fixes.
**Rejected:** (a) auto-install the shim on every devkit init --overlay — REJECTED: machine-global state without explicit consent resurrects the original global-to-every-repo objection; kept opt-in. (b) a PER-REPO seam that survives the reclaim — IMPOSSIBLE: the committed .husky/pre-commit is git-visible (overlay must stay invisible), .husky/_/h is husky-regenerated, and core.hooksPath is the very thing reclaimed; husky exposes only the GLOBAL init.sh. (c) close the no-committed-pre-commit hole with a git-ignored .husky/pre-commit stub — REJECTED for v1: more .husky/ footprint than overlay's invisibility budget allows; documented + doctor-warned instead.
**Anchored-bet:** [VALIDATED]
**Scope:** cli/lib/overlay.mjs,cli/lib/overlay-global-hook.mjs,cli/lib/husky/**,cli/commands/clean.mjs,cli/commands/doctor.mjs
**Source:** collab · overlay-global-commit-gate
**Evidence-change:** husky's native ~/.config/husky/init.sh hook is a newly-recognized seam, narrower than the rejected generic shell-precmd: it fires ONLY inside husky's own hook chain and is a guarded no-op outside overlaid repos. Made opt-in and uninstallable, so the per-clone/invisible default is preserved while the knowingly-accepted plain-commit gap becomes closable on demand.

## Target · 2026-07-07 — the "already-frozen" sentinel moves from the empty baseline file to .devkit/config.json; empty baselines are no longer written

**Context:** freeze-if-absent keyed "already frozen" off the baseline FILE existing, so an empty baseline (`fanout.json` = `{cap,dirs:{}}`, `size.json` = `{0,0}`, empty `<tree>.mjs`) had to be written and KEPT as a sentinel — litter the user reasonably wanted gone. But deleting empty files to satisfy that would collapse "never frozen" and "frozen-and-clean" into one `absent` state, re-arming exactly the re-snapshot laundering this decision's first Target closed (a `--no-verify`/GUI-committed violation would be grandfathered on the next overlay re-apply / `devkit upgrade`). The gate additionally FAILED OPEN (exit 2) on a missing baseline, so simply not writing the empty file would silently disarm the ratchet — including in devkit's own repo, which has NO `.devkit/config.json` (it dogfoods via sync, see devkit-self-dogfood) and where the committed empty `fanout.json`/`size.json` were the only enforce signal.
**Ruling:** Baselining is **init-only** and the sentinel is split by execution context. (1) The freeze-if-absent guards (`repoAdopted`, replacing `baselineFrozen`/`structureBaselinesExist`) key off `existsSync(.devkit/config.json)` — the durable per-clone adoption marker, written AFTER the freezes on first init, present wherever init/upgrade/overlay run — so an adopted repo NEVER re-snapshots, regardless of whether debt files exist. (2) Every baseline writer skips writing when there is zero debt and deletes a stale empty file; the ratchet `gate` self-deletes a baseline the moment its last entry heals in a real staged commit (`git diff --cached` non-empty, incl. deletions). (3) The gate's enforce-vs-fail-open decision keys off **`guard.config.json`** (committed, present in every commit/CI/dogfood context — NOT `.devkit/config.json`): a governed repo with a missing baseline ENFORCES the cap from config with empty grandfathering; only an ungoverned repo fails open. A later cap (e.g. turning on `maxLines`) is grandfathered by an EXPLICIT `guard-size freeze`, never an implicit re-apply.
**Consequences:**
- Positive: No empty baseline files anywhere; an absent baseline is the standing proof of a clean wall and still enforces from config. No-laundering guarantee is preserved (strengthened: an adopted repo skips freeze entirely, not just "if the file exists"). Dogfood + CI enforcement survives deleting the committed empty baselines because the gate keys off guard.config.json, not the missing file.
- Negative: A deliberate behavior change — the overlay re-apply no longer auto-first-freezes a NEWLY-enabled cap's baseline (`overlay.test.mts` "size-lines when maxLines later" repointed); that grandfathering now requires an explicit `guard-* freeze`. Residual wedge: if init's freeze silently fails (init.mts catch) on an adopted repo with pre-existing legacy debt, the governed gate enforces and blocks until an explicit freeze — narrow and loud (init surfaced the failure), accepted like the existing `--no-verify` gap.
**Vision-fit:** n/a — internal dev tooling (structure-governance ratchets on a shared/overlaid repo).
**Researched:** gate-engine/ratchets/{folder-fanout,size-disable}.mts (freeze/gate + the new git-index.mts stageBaseline/stagedSet/hasStagedFiles); cli/commands/init.mts ordering (runFreezes :951 / runStructureBaselines before the .devkit/config.json write :965/:1245); load-baseline.mts:20 (the .mjs loader already returns [] on absence); verified on disk that devkit's own repo has no .devkit/config.json and committed empty fanout.json/size.json/cli.mjs/gate-engine.mjs. Two adversarial feature-critique passes drove the split-by-context fix (the first RETHINK caught that a single `.devkit/config.json` marker would fail-open the gate in devkit's own repo).
**Rejected:** (a) key BOTH guards and the gate off `.devkit/config.json` — REJECTED: absent in devkit's sync-dogfooded repo and in CI, so the gate would silently fail-open (ratchet off) exactly where enforcement matters. (b) per-baseline `frozenBaselines[]` in `.devkit/config.json` with an existsSync migration fallback to preserve auto-first-freeze of a later cap — REJECTED as overbuilt once baselining was declared init-only: a later cap is an explicit `guard-* freeze`, so no per-baseline granularity or migration logic is needed. (c) keep writing empty files as sentinels — REJECTED: that is the litter the change removes, and the marker makes them redundant.
**Anchored-bet:** [VALIDATED]
**Scope:** gate-engine/ratchets/**,cli/commands/init.mjs,cli/commands/doctor.mjs,cli/lib/generate/**
**Source:** collab · no-empty-baselines
**Evidence-change:** `.devkit/config.json` is a durable adoption marker that survives deleting a debt file, and `guard.config.json` is present in every context the gate runs — so the "already frozen" bit (freeze-context-only) and the "enforce vs fail-open" bit (every-context) are separable, which the empty-file sentinel had conflated. This supersedes the first Target's "freeze a baseline only when that baseline FILE is missing" with "freeze only when the repo is not yet adopted"; the no-laundering intent is unchanged.

## Target · 2026-07-14 — `devkit upgrade` re-syncs an overlay in place (pin = config.json `devkitRef`); no more "re-run init --overlay"

**Context:** `devkit upgrade` bailed on an overlay repo (`overlay (local-only) repo — re-run devkit init --overlay to re-sync`, exit 1, doing nothing). Two things made that bail stale. (1) Its original justification — re-running `init --overlay` re-froze the size/fanout baselines every time (debt laundering) — was removed by the 2026-07-07 Target above: baselining is now init-only, guarded by `repoAdopted`, so the re-sync is idempotent and safe. (2) The framing that an overlay is pin-less / has nothing to reconcile was wrong — overlay records its version pin in `.devkit/config.json`'s `devkitRef` (init.mts writes it), exactly as package mode records its pin in `package.json`. So `upgrade` was refusing to do a safe, well-defined thing and telling the user to type a different command that does it.

**Ruling:** `devkit upgrade` handles overlay in a self-contained branch mirroring the self-host branch. It resolves the pin install-agnostically from config.json's `devkitRef` (falling back to the running CLI version), chases a newer PUBLISHED tag exactly like package mode (`fetchLatestTag` → `update` → `needsRerun`/`NEEDS_RERUN`) — where the "install" for overlay is `bun add -g` (the global CLI is node_modules' analog) — then re-syncs via `applyInit({ overlay:true, devkitRef:'v'+target, globalCommitGate: cfg.globalCommitGate })` and runs `doctor`. `globalCommitGate` is threaded from the recorded config so a re-sync never un-wires an opted-in machine-global shim (applyOverlay reads `plan.globalCommitGate`, NOT the file). Deliberately omitted vs package upgrade: the gate-reconcile multiselect and `computeMigration` — overlay's `guard.config.json`/lint configs are `writeIfAbsent` extend-configs, and the load-bearing refresh is the regenerated `.devkit/hooks/pre-commit`.

**Consequences:**
- Positive: one command reconciles an overlay to its pinned/latest devkit (hook + configs + skills/agents + verify), consistent with package/standalone/self-host; the version source is install-agnostic (config.json), so overlay is no longer special-cased as pin-less. `devkit update`'s overlay hint now points at `devkit upgrade`.
- Negative: overlay upgrade updates the machine-global devkit install (`bun add -g`) — a heavier side effect than package mode's local `bun install`, but it IS the sanctioned overlay version mechanism (identical to `devkit update`) and the analog of node_modules. A newly-bundled gate is still not auto-added to an overlay's `guard.config.json` (writeIfAbsent); overlay gate-reconcile is a documented follow-up.

**Vision-fit:** n/a — internal dev tooling; overlay runs guardrails on a shared repo a team would reject a PR for.
**Researched:** cli/commands/upgrade.mts (self-host branch as the shape; the version/pin step reused inline); cli/commands/init.mts applyOverlay (globalCommitGate read from `plan`:970, devkitRef write:984); cli/commands/update.mts overlay `bun add -g` (:192-194); the `repoAdopted` freeze-if-adopted guard (2026-07-07 Target). Confirmed `applyOverlayConstraints` is re-applied so a hand-edited config can't re-enable structure/tsconfig on re-sync.
**Rejected:** (a) keep the bail / keep pointing at `devkit init --overlay` — REJECTED: the re-sync is now safe (repoAdopted) and the config.json pin makes `upgrade` well-defined; the extra command is pure friction. (b) treat overlay as pin-less (current = running global CLI) — REJECTED: config.json's `devkitRef` IS the pin, so upgrade reconciles against it install-agnostically, not against whatever global binary is on PATH. (c) re-sync only, never touch the global install — REJECTED: then `upgrade` couldn't move an overlay to a newer devkit (inconsistent with every other mode); a warn-only middle was considered and dropped for parity.
**Anchored-bet:** [VALIDATED]
**Scope:** cli/commands/upgrade.mts,cli/commands/update.mts
**Source:** collab · overlay-upgrade-resync

## Target · 2026-08-05 — review accepts a husky-reclaimed hooksPath when the overlay is provably still gated; doctor --fix owns the re-point

**Context:** The 2026-06-29 Target closed the plain-commit gap with the global husky init.sh shim, but nothing re-pointed core.hooksPath itself, and devkit review asserted the literal '.devkit/hooks'. So on owners-web a single pnpm install (husky's prepare resets core.hooksPath to .husky/_ on EVERY install) broke devkit review outright while commits stayed fully gated through the shim — review refused to run on a repo it had no reason to distrust. The remedy it printed, 'devkit doctor --fix', could not repair core.hooksPath at all: doctor only warned. So the failure was unfixable by the command the failure named, and recurred after every install.
**Ruling:** The hooksPath literal is an ASSERTION in overlay mode, not an input — review-target.sh hardcodes -c core.hooksPath=.devkit/hooks for its private gate run — so widen the assertion rather than drop it. Review freezes the canonical .devkit/hooks and validates the LIVE value through an acceptance predicate: .devkit/hooks outright, .husky/_ only when every link of the surviving chain is proven by content (devkit block complete in the resolved init.sh, _/h sourcing husky/init.sh, an executable _/pre-commit sourcing _/h, a committed .husky/pre-commit, and a chain resolving through .husky). devkit doctor --fix additionally re-points core.hooksPath, refusing inside a linked worktree.
**Consequences:**
- Positive: devkit review keeps working across the pnpm installs that a shared repo runs constantly, instead of failing on a proxy that says nothing about whether the repo is gated; and the remedy devkit prints is now a remedy that works. A genuinely unwired overlay still fails review loudly, and the failure names the first broken link plus the resolved init.sh path, so a HOME/XDG mismatch is distinguishable from an uninstalled shim.
- Negative: Review's gating claim now depends on a machine-owned file outside both manifest roots (~/.config/husky/init.sh), which is checked but never fingerprinted — removing it mid-review is caught only at the next verify, not by the frozen-path set. The predicate encodes husky 9's runner shape (the _/h early-exit, the _/pre-commit source line), so a husky major that restructures its runner turns acceptance into a false rejection. And doctor --fix now writes a consumer's git config, a wider blast radius than the file-content-only rule it previously held to.
**Vision-fit:** n/a — internal dev tooling; overlay runs guardrails on a shared repo a team would reject a PR for.
**Researched:** Verified against husky 9.1.7 on disk: .husky/_/h line 6 '[ ! -f "$s" ] && exit 0' precedes the XDG init.sh source at lines 11-12, so a repo with no committed .husky/pre-commit is genuinely ungated and must still be rejected. Traced the frozen value to its three consumers (setup-manifest-parse.mts, review-target.sh field guard, setup-runtime.mts verifySource) and confirmed review-target.sh:646 hardcodes .devkit/hooks for the overlay gate run while $HOOKS_PATH reaches git only in the non-overlay branch at :651. Precedent: sc-1329 (devkit ship unconditionally required .husky/_ and rejected a valid standalone install) and prepare-gate-worktree.sh's 'resolved, never hardcoded' hook-dir projection. A feature-critique pass returned PROCEED_WITH_CHANGES and drove the canonicalisation and the linked-worktree refusal.
**Rejected:** (a) drop the overlay hooksPath check entirely and rely on the hook-content drift check — REJECTED: review would then greenlight a repo where husky reclaimed the path and no shim exists, i.e. commits genuinely ungated, which is the one thing the check exists to prevent. (b) freeze the raw reclaimed '.husky/_' and thread a second accepted literal through the parser and the shell field guard — REJECTED: the frozen value is re-compared against the live one throughout a review, and the live value is transient (both git ci and doctor --fix re-point it), so a concurrent re-point in another terminal would abort an in-flight review. (c) fix only the misleading remedy string and leave the check fatal — REJECTED: review stays broken after every pnpm install, which is the actual recurrence. (d) accept on presence of _/h and _/pre-commit rather than their content — REJECTED: that reinstates a weaker proxy, and the whole point is that acceptance must be proof.
**Anchored-bet:** [VALIDATED]
**Revisit-when:** husky changes its runner contract — either _/h stops sourcing $XDG_CONFIG_HOME/husky/init.sh, or it stops exiting before that source when no committed hook exists — or husky's prepare stops setting core.hooksPath unconditionally, at which point the reclaim this works around disappears.
**Scope:** cli/lib/ship/review/**,cli/lib/ship/review-target.sh,cli/commands/doctor.mts,cli/lib/overlay-global-hook.mts
**Source:** collab · sc-1329
**Evidence-change:** The 2026-07-22 devkit-owned-hook-runner-delivery Target rejected re-pointing core.hooksPath partly BECAUSE it broke review's exact string equality against '.husky/_' — this change removes that coupling, so the reason no longer holds. That record's '--fix is file-content-only' rule was drawn around a git INDEX write (git add -f), which stages files the caller never asked to stage; a core.hooksPath write is local, reversible, already performed by init and clean, and is the exact repair the failing command advertises. The narrower rule that survives: --fix never mutates the git index, and never moves the pointer ahead of the hook it points at.

## Target · 2026-08-26 — a skewed runner hands off to the repo's pinned devkit; it never refuses with a remedy it could have performed

**Context:** sc-2100. `.devkit/oxc/*` is version-coupled: `syncOxcCapabilityUnlocked` writes the managed base from `baseContent()` — a template bundled in the RUNNING binary — and stamps its digest, while `oxcBaseCapabilityIssue` recomputes that digest from the RUNNING binary. Two devkit versions therefore rewrite each other's managed bytes, each declaring the other's stale. A global devkit 0.55.1 on a repo pinned at v0.55.3 followed the printed `run devkit doctor --fix` and rewrote the base without 0.55.3's probe global, so the pinned gate kept refusing and a second global `--fix` cycled between two drift messages; only the pinned binary converged. `checkVersion` was warn-only and, by its own comment, config.json-only — it never compared against the repo's actual dep pin — and `applyFix` had no runner check at all, nor did the six other callers of `syncOxcCapability`/`syncAntiSlopCapability`.
**Ruling:** An older runner never publishes managed state. The guard lives at the WRITER: every managed-state path funnels through `syncOxcCapability` (anti-slop calls it internally), so doctor, init, ship and the anti-slop lifecycle are covered by one check rather than one per caller. `ship` additionally asserts against the CALLER's root before projecting, since it refreshes an ephemeral worktree from the running package by design. `devkit doctor --fix` under skew HANDS OFF: it re-execs the repo's own `node_modules/.bin/devkit` with a `DEVKIT_SKEW_DELEGATED` recursion marker and returns that binary's exit code, refusing (exit 1, nothing written) only when no pinned binary resolves. Skew is computed once in `run()` ABOVE the overlay and self-host short-circuits so all three modes name it. `selfHost` is always `none` — the source tree IS the binary — and an unresolvable pin is `unknown`, which proceeds rather than refuses. The Oxc manifest gains an optional `devkitRef` stamp so a stale digest can name its writer.
**Consequences:**
- Positive: The skew is named in every mode, the managed bytes stop cycling, and the remedy devkit prints is one devkit performs itself — extending the 2026-08-05 rule rather than narrowing it. A stale digest now distinguishes "content drifted" from "a different devkit wrote this", including in overlay and ship where no node_modules pin exists to compare against.
- Negative: `doctor --fix` can now spawn a different binary than the one the user invoked, so its output is that binary's and its exit code is passed through opaquely. The guard reads the pin on every managed write, adding a `.devkit/config.json` + `package.json` read to init and ship. `DEVKIT_ALLOW_SKEWED_FIX` can still produce older-shaped bytes by design; it announces itself and is recorded in the manifest as `writtenUnderSkew`.
**Vision-fit:** n/a — internal dev tooling.
**Researched:** Traced every writer reachable from a skewed runner (doctor.mts applyFix, self-host-doctor.mts, init.mts, anti-slop/lifecycle.mts, ship's managed-capability-runtime.mts) and confirmed a doctor-only guard leaves four open. Confirmed `packageDir()` resolves to `<pkg>/dist` in a packaged install, so an install-identity predicate against `node_modules/@norvalbv/devkit` can never match; `checkVersion`'s existing `packageDir()/package.json` read works in both layouts and is reused. Mirrored `findLock`'s cwd-then-gitRoot fallback for the hoisted-monorepo shape. A feature-critique pass returned RETHINK on an earlier refuse-only draft and drove the hand-off, the writer-level placement, and the `bunx` finding.
**Rejected:** (a) refuse and print the pinned command — REJECTED: that is exactly the 2026-08-05 pattern, a failure unfixable by the command it names, while every managed-capability check keeps advertising `devkit doctor --fix`. (b) print `bunx devkit doctor --fix` (the reporter's own workaround) — REJECTED: `devkit` is an unrelated public npm package and bunx falls through to the registry precisely when the local install is missing, so devkit would be telling a repo it does not own to execute a stranger's code. (c) bump `OxcManifest.schemaVersion` to 2 for the provenance stamp — REJECTED: `readManifest` collapses every failure into `null`, which callers report as MISSING and then rewrite, so an older devkit would reject and rewrite a newer manifest — injecting a fresh instance of the very skew being fixed. The field is optional and non-validating instead, as `antiSlop` already is. (d) guard only doctor and file a follow-up for init/ship — REJECTED: the acceptance criterion would be met literally while the hazard survived under two other verbs.
**Anchored-bet:** [VALIDATED]
**Revisit-when:** the managed Oxc base stops being derived from a per-binary bundled template (e.g. it becomes content-addressed or is resolved from the pin rather than the runner), at which point writer and reader are no longer version-coupled and the guard has nothing to protect.
**Scope:** cli/lib/doctor/pin/runner-identity.mts,cli/commands/doctor.mts,cli/lib/install/oxc/lifecycle.mts,cli/lib/install/anti-slop/lifecycle.mts,cli/lib/ship/managed-capability-runtime.mts
**Source:** collab · sc-2100
**Evidence-change:** The 2026-08-05 Target established that a remedy devkit prints must be a remedy devkit can perform, and gave `--fix` the power to repair rather than warn. A version-skewed runner is the case where `--fix` genuinely cannot perform the repair itself — the fix requires different code than the one running. Hand-off preserves that rule where a refusal would have reversed it.
- 2026-09-03 — 2026-09-03 — anti-slop becomes installable in overlay (see the oxc-toolchain-migration Target of the same date). Its baseline follows this axis's 2026-07-07 no-laundering rule: create-if-absent at install, never --force, so a re-init or devkit upgrade cannot re-snapshot accumulated debt. Because activation evidence is read from Git TREE objects and an overlay capability is git-excluded, activatedRuleIds is always empty there, which left create --force as the only way to clear a newly activated rule's inherited debt — i.e. laundering through a different door. A scoped 'devkit anti-slop adopt-activation' verb closes that: it adopts only the pending rule IDs and leaves every other fingerprint's count untouched.
- 2026-09-28 — sc-1794 — overlay now owns a local .devkit/hooks/commit-msg. Before this, every non-pre-commit hook was a bare pass-through, which silently dropped the completeness and sentry message judges that package mode wires into .husky/commit-msg. The hook is built from the shared buildCommitMsgBlock in STANDALONE form: global command -v bins, fail-open when devkit is not installed. The package bin dir never resolves in a package-less overlay, so package-bin mode would have blocked every commit. Before exec-chaining to the repo's own commit-msg, the hook clears the pre-commit handoff and drops the EXIT trap, because exec discards the trap. A selected judge is NEVER omitted on the strength of the repo hook's text: parsing shell cannot prove execution, and ship review showed sentinels, comments and echoed strings would silently bypass the gate. A repo hook that appears to call a judge only earns a double-run warning; a cached completeness PASS makes the repeat cheap. The hook is published atomically (temp + rename) because git may exec it mid-write, and any mode other than devkit's exact 0755 (including an owner-unreadable hook) counts as drift. Deselecting both judges reverts the hook to a pass-through, or removes it when the repo has none. syncOverlayHook reports commit-msg drift SEPARATELY from pre-commit: doctor counts it in the exit code and --fix heals it, while devkit review reads only the pre-commit flags (it never runs commit-msg, per the sc-2361 note on review-gate-in-chain). The overlay pre-commit does NOT gain the sentry ship prewarm: the shared fragment keeps the git env (so both runs key one index), which ship review flagged as crossing the commit-index isolation boundary. On an overlay ship, sentry therefore judges at commit-msg, after the qavis advisory; that ordering is a follow-up. Chain targets derived from core.hooksPath are shell-quoted (shQuote), so a path carrying $(...) is data.
