# decision-log-informs-before-work

## Target · 2026-07-27 — The log informs before work, matched on Scope globs not text similarity

**Context:** Every decision surface enforced AFTER the fact: check-alignment flags a contradiction at commit, decision-stop-check nudges to record at turn end, decision-edit-guard denies a hand-write to a record. Nothing told an agent an area was already settled while it could still act on that, so an agent could re-solve a decided problem from the code alone and only learn at commit — and only if the ruling carried a Scope glob matching the staged files. scoped-targets.mts existed for exactly this and was consumed by one review-time agent.
**Ruling:** Two informing surfaces, both matched on the ruling's own Scope globs. (1) A PreToolUse hook (agents-hooks/decision-scope-brief.mjs) briefs the governing rulings before an Edit/Write, at most once per session per file. It emits additionalContext and deliberately NO permissionDecision, so it can neither block a write nor auto-approve one, and degrades to a silent no-op if the platform ignores additionalContext on PreToolUse. (2) The brainstorming skill runs guard-decisions query at the FORK, before options are posed, which its own decisions-skill documentation already claimed but never implemented (it ran list, in the record step).
**Consequences:**
- Positive: An agent sees the settled ruling while it can still act on it. Scope-glob matching needs no threshold, no model and no network (~121ms), and 33 of 34 axes declare a glob. Effectiveness is observable through check-alignment's existing scoped-contradiction flag rate, so no new benchmark is required.
- Negative: Only files a ruling explicitly scopes are briefed: an axis with no Scope glob informs nobody, and a settled problem in an unscoped area is still invisible. The PreToolUse additionalContext contract is documented inconsistently upstream, so the hook may be a silent no-op on some versions — the skill-level fix is the surface that does not depend on it.
**Vision-fit:** n/a — internal developer tooling; the decision log's own consumption path.
**Rejected:** Injecting retrieved rulings on UserPromptSubmit, keyed on a confidence threshold over the lexical top-1 score — REFUTED on measurement. That score tracks query LENGTH (r=0.908 on this corpus), not confidence: all six short-but-governed probes scored below all four long-but-ungoverned ones, so at the oracle threshold four ungoverned prompts inject and 6/6 governed ones are missed. Raising the threshold buys 'only long prompts', not precision. The event is also wrong mechanically: 5.29s cold, ~78s projected at 500 axes (past the 60s hook timeout), and ~4.9k tokens added to every prompt.

- 2026-10-06 — Correction to the Context sentence 'check-alignment flags a contradiction at commit' and to the Positive that effectiveness is observable through its scoped-contradiction flag rate. No devkit-generated hook runs check-alignment (axis alignment-judge-on-demand), so that flag rate only reflects on-demand and hand-wired runs. This makes the pre-edit brief more load-bearing than the record assumed: for an architectural ruling it is the main surface that reaches an agent before the change is committed.
- 2026-10-11 — The pre-edit brief now reports itself. The hook passes `--brief <tool>,<max_axes>,<cap>` to scoped-targets only for a file not yet briefed this session. A later edit skips retrieval, and only the first return to the file is recorded, through `--brief-again <tool>,<secs_since_brief>`. scoped-targets emits brief_shown (shown slugs, each shown ruling's full length, hidden slugs and hidden_count, cap, max_axes), brief_edited_again and brief_unavailable (reason error or unloadable). show and query emit decision_read. Each CLI read runs under its own agent run id (run_mode 'agent', no write-tree) and joins the brief on parent_session_id. Why: the sink held no brief row at all, and RULING_CHARS=320 shipped unmeasured. Behaviour change: the DID-NOT-RUN notice can no longer fire for a file already briefed this session. Limits: a spawn timeout or a missing binary cannot be logged, because the CLI never ran; scoped-targets reads are never logged, including the brief's own 'N more' pointer, so the follow rate covers show only; query rows carry no slugs; Cursor sessions cannot be joined; two concurrent first edits of one file can both write brief_shown while only one prints. A cap change is read by splitting rows on their `cap` field, not by date.
- 2026-10-11 — The brief's effect on what an editing agent writes is measured by the decisions-brief benchmark suite (gate-engine/decisions/eval/brief/). It runs the shipped decision hooks from the tree under test, registered from HOOK_REGISTRATIONS.decisions, with only guard-decisions stubbed from frozen fixtures in docs/benchmarks/decisions-brief/: 8 clause tasks and 9 floor tasks, claude-haiku-5-5, K=5, scored by each task's check script, in two regimes (the agent cannot read on, or it may run the stub through PATH). Metrics carry a 15-point noise floor, equal to the before/after decision threshold, so a change to the brief's text, cap, timing or registration publishes an event against the recorded baseline. Its first event, at the shipped 320 cap on claude 2.1.296, reproduces the cut-at-320 cells of the study that built the tasks within their bands: rule kept 2/40 brief only (study 1/40) and 37/40 when the agent may read on (38/40), floor edits correct 37/45 (41/45), none arm 2/40 and 45/45 (0/40 and 45/45). Rejected: a re-implemented brief formatter, because it can drift from the hook it measures; live rulings as the corpus, because a record edit would move the baseline. This replaces the 2026-07-27 Consequence that no new benchmark is required, which the 2026-10-06 note already undercut. It is not the cap change's evidence: that change's checks hold by construction, and field telemetry is what can fail. A note, not a Target: the ruling is unchanged, and this records how it is measured.
- 2026-10-11 — A third, plan-time informing channel was evaluated on 2026-10-11 and not built: a PostToolUse hook on ExitPlanMode that would brief the Scope-matched rulings for the paths an approved plan names. Its only benefit evidence was a timing bench (claude haiku, 5 runs per arm) in which the whole ruling delivered at session start kept the outage-classifier task's rule 5/5 against 0/5 for the per-edit brief. That gap came from the check, not the behaviour: the rule is that an unrecognised judge failure stays non-permanent, and the check also demanded the literal kind 'transient'. All 110 recorded runs of that task returned permanent: false, which keeps the rule in behaviour; only the label varied. In the 72-run arm comparison, the 64 runs without session-start delivery (no brief, a cut or whole ruling, and name-only or mandate wordings, on haiku and sonnet) returned { kind: 'unknown', permanent: false } and the 8 session-start runs returned kind 'transient'. Of 38 further per-edit runs, 36 returned 'unknown' and 2 returned 'transient', both among the 8 that read the whole axis record through show. Per-edit runs that never edited the governed file again after the brief kept the rule 5/5 on the other task where that happened. No measured failure is left for earlier delivery to fix, and this axis already informs at plan time through ruling (2), the brainstorming query at the fork. Reopen only on field evidence: brief telemetry showing, in at least 3 distinct sessions, a briefed file never edited again after its brief whose change then drew a contradiction or a reviewer finding citing that ruling. A bench offered as reopening evidence must score behaviour rather than labels, reproduce the failure in the per-edit arm under the same plan-mode regime, beat that arm with a 95% lower bound above zero, and also beat a one-line per-edit wording change that tells the agent its edit has already landed.
- 2026-10-11 — `guard-decisions show <slug> --current` was tested as the brief's pointer target and DROPPED on its preregistered bench. The brief keeps 'Full text: `guard-decisions show <slug>`' and plain `show` is unchanged. The tested view printed the newest Target block verbatim (every field and continuation line up to the first note), the effective Scope when a rescope note changed it, and one line counting the other sections and notes and naming the whole-record command. Bench: the edit-time agent bench from the brief-cap study (a real PreToolUse hook delivering the brief, a stub guard-decisions whose `show` returned either this repo's real axis file or the new view over the same bytes, 9 tasks each scored by a deterministic check), claude-haiku-5-5, K=5, one interleaved batch of 180 sessions after a 36-session probe. q2-outage was scored on behaviour (an unrecognised failure stays `permanent: false`), not on its literal kind label. Pass rule, fixed before the batch: in both brief regimes kept(view) >= kept(file) - 2 and refusals(view) <= refusals(file) + 2, and at the 320 cap mean cost(view) <= mean cost(file). At the 320-char cap every clause passed: kept 39/45 against 32/45, refusals 4 against 4, $0.00763 against $0.00877 per run. With the whole ruling in the brief (what a 2000-char cap gives on these tasks) both clauses failed: kept 41/45 against 44/45, refusals 4 against 1. That whole gap is one task, ship-ci-wait-is-observation-not-intent's q2-shipci: the view kept 1/5 with 4 revert-and-stop, the file 4/5, every run having called show. Its two views differ only by two notes (a scope move and an opt-in flag). In the earlier study the same task ranged from 1/5 to 3/5 kept across haiku arms, so the file arm's 4/5 here is itself above every earlier arm. So this run cannot separate a view effect from task noise, and the preregistered rule does not discount it. Agents followed the pointer: the view was read on 45/45 runs at the 320 cap and on 23/45 with the whole ruling, and a plain `show` followed it on 1 run in each regime. Revisit when production stays at the 320 cap, where the view won on every clause, or when a re-registered bench with more tasks in the whole-ruling regime can resolve the single-task loss.
