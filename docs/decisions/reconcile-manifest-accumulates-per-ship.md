# reconcile-manifest-accumulates-per-ship

## Target · 2026-06-28 — Reconcile manifest accumulates across every ship event on a branch

**Context:** devkit ship --pr re-pushed commits to an open PR but never updated .devkit/reconcile-manifest.json — only the initial devkit ship wrote it. A multi-commit PR therefore recorded only the first commit's paths; after merge, devkit reconcile --apply cleaned only those and git pull --ff-only then ABORTED on every path the --pr commits added or renamed (local changes would be overwritten), stranding shipped files dirty in the shared parallel-agent tree until a manual git restore.
**Ruling:** Every ship event on a branch — the initial devkit ship AND each devkit ship --pr re-push — records into the SAME branch entry. A re-push MERGES its paths keyed by path: replace a re-shipped path with its branch-TIP blob, add new paths, and supersede a renamed-away path's stale modify with its delete, keeping the PR metadata. Renames stay delete-old + add-new (the existing reconcile contract), never a new op:rename. No prior entry means an honest best-effort miss, never a partial reconstruct.
**Consequences:**
- Positive: A multi-commit PR's manifest holds every final shipped path at its tip blob, so after merge reconcile --apply restores or stages all of them and the shared tree is fully ff-pullable — zero stranded files, no manual git restore.
- Negative: A rename's old path must be passed to ship --pr for its deletion to be recorded — the same contract as the initial ship, and safe because reship only commits the passed paths so the record cannot desync from what shipped. A lost best-effort INITIAL write leaves the whole branch entry unrecorded; accepted, because reconstructing from a re-push could know only that commit's paths and would prune then falsely report 'all clean' while earlier paths still block ff.
**Vision-fit:** n/a — internal dev tooling (the parallel-agent shared-tree ship and reconcile workflow).
**Researched:** frink manual-lane reconcile spec (workflow-reconcile), whose own 'sub-threshold rename emits add+delete = two independent entries, still correct' sanctions delete+add; git-spice forge-MERGED detection plus git-town per-path empty-diff gate the contract builds on; verified against the shipped reader cli/lib/reconcile.mjs, which has no rename branch (handles only add/modify/delete).
**Rejected:** (a) op:rename + renamedFrom schema, as the spec literally listed — INFEASIBLE without also building an unbuilt rename case in the reconcile reader (reconcile.mjs handles only add|modify|delete), and the spec itself proves delete+add reconciles identically, so the extra schema buys nothing. (b) reconstruct a fresh entry when no prior entry exists — LOSES correctness: a re-push knows only its own commit's paths, so reconcile would clean those, prune, and falsely report success while the unrecorded earlier paths still block git pull --ff-only.
**Anchored-bet:** [VALIDATED]
**Scope:** cli/lib/ship/**,cli/lib/reconcile.mjs

- 2026-07-25 — reconcile no longer ASSERTS ff-pullability from the manifest, it MEASURES it against the tree: upstream-changed paths intersected with locally-dirty ones, minus index==upstream (git's own keep_entry exemption, which is exactly what the restore produces). With a non-empty list it names the blockers and withholds both the ff-pullable claim and the git pull --ff-only instruction — the old unconditional pair steered an agent into git's 'commit your changes or stash them', which destroys the concurrent edits reconcile declined to touch one line earlier. Catches a peer's dirty file that no ship ever recorded, which a warnings-derived check cannot see (sc-1235).
- 2026-08-26 — sc-2071 — the restore reads a commit sha resolved ONCE per branch from refs/remotes/origin/<baseRef>, never the literal FETCH_HEAD ref. .git/FETCH_HEAD is one mutable file in a tree N agents share, so a peer's fetch between the gate probe and the checkout either killed --apply mid-manifest (the reported crash, whose bare 'Command failed' echoed the argv and named neither exit code nor stderr) or, silently, staged a blob from a commit this branch never reconciled against. The base fetch is now refs/heads/<baseRef>, so a same-named remote tag cannot win git's DWIM in a consumer repo. A write git refuses is now a named warning carrying its stderr and exit status plus a per-branch restoreFailures[] in the --json envelope, not a throw: later branches still clear their debt, the entry survives to be retried, and a failed 'git rm --cached' on a shipped deletion no longer prints '✓ restored' and prunes the only record of it. The CLI's advisory exit 0 is unchanged. ffBlockers already refused to read the ref for the measurement (sc-1235); this extends that to the write.
- 2026-08-26 — **Scope:** cli/lib/ship/**,cli/lib/reconcile.mts,cli/commands/reconcile.mts — The recorded glob names cli/lib/reconcile.mjs, a path that stopped existing at the 2026-07-05 TypeScript migration — so the alignment gate has been silently covering nothing on this axis. Point it at the .mts source and the command that renders it.
- 2026-08-26 — CORRECTION to the sc-2071 note above, which named refs/remotes/origin/<baseRef> as the resolution source: that ref is NOT what ships, and reconcile must never read it. A peer's fetch of the same base can advance the tracking ref between our fetch and our read, so it cannot answer 'what did I just fetch?' any better than the shared .git/FETCH_HEAD can. What ships instead: each branch fetches +refs/heads/<baseRef> into a ref this process owns, refs/devkit/reconcile/<pid>/<baseRef>, captures that commit once, and drops the ref in the same run. Naming its own destination also makes resolution independent of the repo's fetch refspec. A test asserts refs/remotes/origin/<baseRef> is neither read nor recreated, and that no pin ref is left behind. Aligning the code back to the superseded wording would reintroduce sc-2071.

## Target · 2026-08-30 — Append reships accumulate; proven full-scope rewrites replace

**Context:** The manifest's merge-only rule assumed an existing PR branch was append-only, so each reship knew only its own delta. Story sc-2323 introduced a different state transition: after the PR base moves and conflicts, a caller can prepare a resolved snapshot on the new base, but publishing it removes the old PR history. Keeping the old accumulated entry would retain paths no longer changed by the rewritten PR, while refusing the rewrite leaves no attested devkit path to update the same PR.
**Ruling:** Ordinary devkit ship --pr remains append-only and merges its paths into the branch entry. An explicit history rewrite may replace that entry only after devkit proves the complete old-PR changed-path set was briefed, gates one replacement commit on the PR's pinned current base, verifies the open PR's pinned head/base identity, and publishes under an exact expected-OID lease. The replacement entry is rebuilt atomically from the final commit while preserving the PR identity. Devkit publishes a caller-prepared resolution; it does not perform the rebase or resolve conflicts.
**Consequences:**
- Positive: A conflicted PR can keep its identity and acquire new-base ancestry through the same strict ship gates, while reconcile describes only the history that still exists and never restores rewritten-away paths.
- Negative: Rewrite mode force-updates the PR to one squashed ship commit, requires the caller to brief every path changed anywhere in the old PR, and refuses on incomplete, sparse, unresolved, retargeted, or concurrently advanced state; ordinary append iteration remains the cheaper default.
**Vision-fit:** n/a — internal dev tooling (safe shared-checkout PR publication and reconcile).
**Researched:** Story sc-2323 and autonomous report 537304eb-d584-42d9-944b-7ad1ea096282; Git merge-tree reproduction; Git push exact expected-OID force-with-lease documentation; git-spice submit implementation; local prior-art and feature-critique agents.
**Rejected:** (a) Build a rebase/conflict/regeneration engine — REJECTED: interactive conflict ownership and generated-artifact policy are broader than publication and duplicate Git/GitHub. (b) Append a merge commit — REJECTED: devkit would own merge staging and re-gate every base change rather than the caller's prepared snapshot. (c) Document raw git push --force-with-lease — REJECTED: it cannot earn devkit's exact-SHA pre-push attestation and repeats the full local suite that caused the report.

**Revisit-when:** GitHub exposes conflict-capable server-side PR updating whose exact resulting head can be gated and attested before publication, or devkit removes same-PR conflict recovery from its supported ship contract.
