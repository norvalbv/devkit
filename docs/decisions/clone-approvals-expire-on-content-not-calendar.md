# clone-approvals-expire-on-content-not-calendar

## Target · 2026-10-14 — A clone approval lasts until the duplicated code changes; a calendar expiry is opt-in

**Context:** A reasoned approval of deliberate duplication lapsed 7 days after it was written, because guard-dup-allowlist add-clone stored no lifetime and an entry with none inherits the 7-day default shared with symbol-pair approvals. The clone gate then blocked the next unrelated commit that touched the file, labelled the lapsed approvals as new clones, and printed the same add-clone command, which re-armed another 7 days. On devkit's own most-edited benchmark file this blocked two ships about two weeks apart, each costing a failed ship attempt and 10 to 15 minutes of source reading, and the second renewal changed nothing but ten date lines. Of 28 hand-written clone approvals none carried a lifetime, and all 28 gave a by-design reason. The 7-day default dated from the first commit and had never been ruled on, and it contradicted the detector's own stated contract that an approval re-surfaces only when the duplicated code changes.
**Ruling:** guard-dup-allowlist add-clone writes an explicit 3650-day lifetime, the same value baseline-clones uses to freeze pre-existing clones, unless the approver passes --decay-days N. A clone entry is keyed on a hash of the duplicated fragment, so an edit to that code already ends the approval; the calendar is therefore an opt-in temporary waiver for clones and not the default. Symbol-pair approvals written by add keep the 7-day default, because a pair is keyed on symbol and file names and nothing else ends it when the code drifts. The shared default in the decay module is unchanged, so clone entries written before this ruling with no lifetime stay expired and are never silently revived. The gate's block output and the CLI usage text state the lifetime each verb buys.
**Consequences:**
- Positive: An approval the gate's printed command produces does what the approver meant: a later commit that leaves the duplicated code alone is not blocked, and a commit that changes it is. A test holds both halves, approving a clone through the default command, then changing one token inside it and expecting the block. Pasting add-clone over a baseline-frozen clone no longer downgrades it to 7 days.
- Negative: The fragment hash is file-agnostic and is taken from jscpd's slice of the first file, so a third paste of an approved fragment can ride the approval when jscpd pairs it at the same extent; a 7-day expiry used to bound that window and a 3650-day one does not. The same exposure already applied to the 60 baseline-frozen entries. Nothing sweeps a clone entry whose fragment no longer exists: prune is calendar-only and reconcile handles pairs only, and 51 of devkit's 88 clone entries were already dead when this was ruled, so durable entries accumulate until someone runs remove-clone. In practice the temporary class will be rarely chosen, since every approver so far claimed by-design structure.
**Vision-fit:** n/a — internal tooling (gate trust: a block must point at something the commit did)
**Researched:** Fingerprint-pinned acceptances carry no calendar in ESLint bulk suppressions (a suppression ends when the violation is resolved), the jscpd baseline (content-hash fingerprint per accepted clone) and the detekt baseline; Snyk keeps ignore-temporarily and ignore-permanently as two explicit classes. A peer repository using this gate had already hand-picked 90 and 365-day lifetimes for by-design clones, and its 90-day tier mixed by-design reasons with debt excuses. A scan of devkit measured 37 live clones against 88 allowlist entries.
**Rejected:** (a) Refuse add-clone unless the approver names a class, by-design or temporary — NO DISCRIMINATION: all 28 existing reasons already claim by-design, so the flag would be answered the same way every time while changing the command the gate prints. (b) Keep 7 days and print a renewal command carrying 90 days — only moves the same false block to a quarterly cycle, and a longer number does not separate by-design from debt. (c) Raise the shared default — would silently revive every lapsed entry, including symbol pairs that have no content pin. (d) Key the match on hash plus file pair to close the third-paste window — FALSE BLOCKS: jscpd re-pairs fragments when a file is split or a sibling appears, and two live entries had already moved to a different partner file than recorded. (e) jscpd ignore markers or a path exclusion — no reason or audit trail, and they hide genuinely new clones in the most-edited file.

**Revisit-when:** A clone reconcile exists that drops entries whose hash the current scan no longer produces (then the lifetime can become truly unbounded and the 3650 stand-in can go), or a third copy of an approved fragment is observed riding an approval past the gate (then the match key needs more than the hash).
