# release-requires-green-base-ci

## Target · 2026-10-10 — devkit release refuses unless the base commit's CI passed

**Context:** v0.68.0 (#858) was released while gate.yml had failed on every push to main since 2026-10-02. devkit release read no CI at all: it ran the local suite and built dist from whatever the local HEAD was, and ship then opened the release PR on origin's current tip, so dist could also be compiled from a commit other than the one the PR lands on. Consumers pin immutable version tags, so a version whose CI never passed reaches every downstream install and cannot be re-cut.
**Ruling:** devkit release refuses unless the local HEAD is GitHub's tip of the release base branch (read again just before the PR opens) and that commit's newest completed run of the configured CI workflow (guard.config.json baselineStatus.workflow, default gate.yml) concluded success. Runs are read by sha with gh run list --commit, never through PR checks. A red run, no run, a cancelled, timed-out or otherwise non-success conclusion, and any gh failure all fail closed; an unfinished run is told to wait. --ci-override "<reason>" waives only a verdict that was actually read (red, missing or still running), never the tip check, gh reachability or a run read gh could not answer, and the reason, sha, verdict and run URL are written into the release PR body. The local test suite still runs after the CI read.
**Consequences:**
- Positive: devkit's own release command can no longer open a release PR from a commit whose CI never passed, or build dist from a commit other than the one the PR lands on. The refusal comes before the roughly 30-minute local suite and build, and an override leaves its reason on the release PR for anyone auditing the tag.
- Negative: Releases are blocked whenever main is red (every push run on main failed when this was recorded), and a release now needs an authenticated gh and the network. It guards a path the last eight releases (#665 to #858) bypassed by hand with --no-verify, so until devkit release can run from a clean worktree it is defence in depth. The tag is still cut by hand on the squash-merge commit, whose own CI this does not read. If origin advances during the release, the run is refused at the end and must be redone.
**Vision-fit:** n/a — internal tooling (devkit's own release path, whose tags every consumer pins)
**Researched:** gh 2.96: gh run list --workflow --commit and gh run view --json url,jobs, checked live on run 38042970754 (job gate, failed step Tests). cli/lib/ship/ship-branch.sh: the --base arm fetches origin's tip at ship time. .github/workflows/gate.yml keeps every push run on main (cancel-in-progress only for pull_request). main's ruleset has no required status check. Bun publishes canary builds only from a green main. arXiv 1907.01602: broken builds commonly stay broken for days, so a hard refusal needs a recorded override.
**Rejected:** (a) Advisory only, as at pre-push. blocking-gates-narrate-attribution-never-depend-on-it Rejected (e) because a red base used as EXCULPATION ('not your fault') licenses --no-verify; here a red base is a REFUSAL, the opposite polarity. Its firing-rate worry is also smaller: while main's Tests step is red the local suite already refused, so this mostly moves that refusal 30 minutes earlier and adds the CI-only steps (format, lint, anti-slop, structure). Its Revisit-when (gate.yml green on main) still governs pre-push. (b) Only a server-side required check on main. None exists today, and a client refusal also saves the 30-minute local run and writes an evidence line into the PR body. (c) Publish from a tag-triggered CI workflow: it would also cover the hand-cut tag, but it is a larger change across release, tagging and consumer pins. (d) Fail open on missing CI, as remoteTagExists does offline: a tag lookup can only add certainty, whereas a missing CI read is exactly the state after a broken push.
**Anchored-bet:** [BET]
**Revisit-when:** releases are published by a CI workflow, or a required status check on main plus a tag ruleset enforce green CI server-side
**Scope:** cli/commands/release.mts
**Category:** self-host-release
**Source:** shortcut · sc-5179

## Target · 2026-10-11 — A green base commit skips devkit release's local suite; an overridden base still runs it

**Context:** The 2026-10-10 Target kept the local test suite after the CI read. Cutting v0.69.0 on 2026-10-11 showed what that costs: CI had passed gate.yml on the exact base commit in 48 minutes, the local re-run of the same suite then took over an hour on a loaded 10-core machine and failed twice on things the commit did not cause (ten timing-bound git-integration tests under load, six tests that break in a checkout path containing a space). Each failure refused the release, and the owner cut v0.69.0 by hand with --no-verify — the bypass path the earlier Target names as the thing to end.
**Ruling:** When the base commit's CI verdict is green, devkit release does not run the local suite: it prints that CI passed it on this commit, and the release PR body says the suite passed in CI and was not re-run. Under --ci-override (a red, missing or pending verdict that was read) the local suite runs exactly as before and a failure refuses the release, because that base has no other proof. Everything else is unchanged: the tip check, the CI read, the build, the dist smoke checks, the re-read of origin's tip before publishing, and ship's own gates on the release PR.
**Consequences:**
- Positive: A release from a green base takes minutes instead of over an hour, so the checked path is cheaper than --no-verify and there is less reason to leave it. The suite that gates a release is the one that ran on the exact commit in a clean CI environment, not one perturbed by the maintainer's machine load or checkout path.
- Negative: A green release no longer exercises the suite on the maintainer's OS, so a macOS-only regression that Linux CI cannot see is not caught at release time; devkit ships platform-neutral .mjs, and commit and ship gates still run on that machine. The local run also used to cover whatever differed between the checkout and the CI'd commit; the tip check already requires HEAD to be origin's tip on a clean tree, so that difference is empty by construction.
**Vision-fit:** n/a — internal tooling (devkit's own release path)
**Researched:** release.mts (baseCiLines, the test step); the v0.69.0 release attempts on 2026-10-11 (CI run 38165008203: 18:43 to 19:31 UTC green on cb955163; local run: 16 of 10624 failed, all environment); cli/__tests__/release.test.mts.
**Rejected:** (a) Keep the local suite always (the 2026-10-10 ruling): it duplicated a verdict already read and pushed the release back to --no-verify within one day. (b) A --skip-tests flag: a second bypass to remember, with no evidence behind it; the green verdict is the evidence. (c) Run only a smoke subset locally: the build, built-bin version check, stdin-body wiring check and dist completeness already are that subset. (d) Skip the suite under --ci-override too: that base has no passing run, so the local suite is the only check left.
**Anchored-bet:** [BET]
**Revisit-when:** A release ships a regression that a local suite run on the maintainer's machine would have caught and CI did not; or releases move to a CI workflow.
**Scope:** cli/commands/release.mts
**Source:** collab
**Evidence-change:** One day of use: the local suite repeated a green CI verdict at over an hour per attempt, failed on environment-only causes twice, and the owner released with --no-verify; the owner then delegated the fix.
- 2026-10-17 — The printed post-merge recipe now reads the squash-merge commit's own CI before tagging: it finds that commit's push run of the configured workflow on the base branch, fetches the base, and waits with gh run watch --exit-status. It is printed as one ( set -e … ) subshell, because a pasted interactive shell has no errexit and would otherwise run git tag and git push after a failed check; exit inside the subshell also no longer closes the maintainer's shell. This closes the 'whose own CI this does not read' Consequence for the printed path; a tag typed by hand still bypasses it. A --ci-override release also prints a one-line fallback that tags the merge commit without reading CI, since the override already waived it and a base the workflow never runs on gets no push run to watch.
