# agent-comment-firewall

## Target · 2026-08-15 — Challenge changed comments before they can justify workarounds

**Context:** Agent-authored implementations sometimes preserve a bug or shortcut and then add a paragraph explaining why the workaround is acceptable. Untouched repository comments are existing debt, while every added or modified source comment is evidence introduced by the current change. A purely syntactic hard gate would also reject legitimate invariants, safety explanations, licenses, and API documentation.
**Ruling:** Add a dedicated hybrid comment firewall after the deterministic guard prefix. It reads staged index blobs, reconstructs every added or modified supported-language comment token, and blocks deterministically when no explicit per-finding rationale exists. A cheap independent judge may only downgrade that existing block after reviewing the exact comment, bounded relevant code and diff, rationale, and optional canonical debt ticket. PASS receipts are content-addressed to all judged evidence and policy identity; relevant changes invalidate them. Untouched comments and deletions are grandfathered. The correctness reviewer and its benchmark are not changed.
**Consequences:**
- Positive: Agents must either remove the comment and fix the underlying implementation, explain why the comment is load-bearing, or link a tracked cleanup ticket for legitimate temporary debt. Fresh installs receive the firewall in the recommended guard set; existing recorded selections are offered the new bundled guard without silent re-enablement. Supported lexer adapters and outage states are reported explicitly.
- Negative: Every changed comment incurs one deliberate challenge and some legitimate documentation incurs a one-time rationale and model cost. Ordinary judge outages remain visible but fail open under the established AI-gate contract; strict ship fails closed. Initial language support is deliberately limited rather than using a misleading universal regex.
**Vision-fit:** Turns a recurring agent failure mode into a changed-only ratchet while preserving consumer-owned configuration, transparent bypass evidence, and independent semantic review.
**Researched:** Bun Comment Cop, Bun adversarial reviewer guidance, Bun self-obsoleting workarounds, source-lint ratchets, and devkit review-gate/verdict-store precedents.
**Rejected:** Rejected a literal two-line Comment Cop hard gate because it is noisy and format-gameable; rejected changing the correctness prompt because it is a distinct classifier with an existing benchmark; rejected rationale-alone authorization because it can launder the same workaround without independent review.
**Anchored-bet:** A changed-comment challenge plus independent judged rationale will expose workaround-shaped implementation bugs earlier without training agents to delete legitimate load-bearing documentation.
**Revisit-when:** The focused corpus misses the hard-gate precision threshold, disable or rejection rates show unacceptable friction, or production evidence supports narrower TODO/suppression/stub detectors instead.

## Target · 2026-08-18 — Challenge paragraph-shaped workaround explanations, not comments generally

**Evidence-change:** The first self-hosted implementation required ten committed rationales for legitimate comments in its own PR, and review showed that a large change could force authors to defend scores of ordinary comments or delete useful documentation. A fresh Bun audit found the same failure mode: current Comment Cop is advisory, PR #39166 retained three useful flagged comments, and RoboBun PR #37948 narrows the trigger after maintainer complaints to a third non-structural text line.
**Context:** Treating every changed comment as suspicious creates pressure to remove useful documentation, grows a repository allowlist, and scales model calls with comment count. The motivating defect is narrower: agents write paragraph-shaped prose to defend an implementation workaround that should instead be fixed.
**Ruling:** Challenge only standalone JS/TS-family comment paragraphs for which the staged change adds or modifies at least three non-structural text lines. Multi-line block explanations may open after code and may end before closing punctuation or JSX closing tags, but comments followed by executable text remain inline. One- and two-line staged comment changes, inline comments, untouched lines, deletions, and pure renames pass deterministically. There are no content-keyword exemptions: long license/generated headers enter the same batched review instead of creating a gameable bypass. Explicit per-finding rationales live in shared Git-local metadata with pre-change-blob migration, per-worktree ownership, and conflict detection; managed review reads shared evidence and redirects mutations into its private data root. All pending exceptions are decided in one bounded Haiku batch with deterministic overflow failure and content-addressed receipts.
**Consequences:**
- Positive: The gate preserves pressure against workaround essays without taxing normal comments, committing an accumulating rationale registry, or issuing one model request per finding.
- Negative: A workaround compressed into one or two lines can evade this detector, and legitimate long-form documentation still requires an explicit reviewed exception.
**Vision-fit:** Keeps devkit's governance proportional to the specific agent failure it addresses while preserving low-friction comments and bounded review cost.
**Researched:** Bun Comment Cop current workflow; Bun PRs #32089, #35534, #37948, #38127, #39166, and #39183; RoboBun discussion responses and the proposed three-text-line rule.
**Rejected:** Rejected retaining the every-comment gate because observed self-host friction confirms its deletion and registry incentives; rejected copying Bun's current two-physical-line threshold because Bun maintainers have already found it noisy; rejected per-finding model calls because one structured batch can return independent decisions at bounded cost.
**Anchored-bet:** Three non-structural lines are a practical deterministic proxy for explanation-shaped workaround prose without making comments suspicious by default.
**Revisit-when:** Production examples show workaround prose routinely compressed below three lines, or accepted long-form documentation produces material false-block friction after batching.

## Target · 2026-08-28 — Bounded chunked review that names why a verdict is missing

**Context:** One batch per run made the reply size a function of the pending count, which grows monotonically on a comment-dense diff because receipt identity is content-addressed. The gate could not distinguish a judge that never ran from one that ran and answered, and the two need opposite remedies.
**Ruling:** Pending exceptions are decided in as many bounded batches as GUARD_COMMENTS_BATCH requires — default 12 findings per call, at most 4 sequential calls, off restoring exactly one call for everything. A batch that fails to parse no longer voids the batches that succeeded: every well-formed batch publishes its PASS receipts after the unchanged whole-set freshness re-read, so a retry reviews only the remainder. judgeComments returns a CommentJudgeOutcome naming which of disabled | timeout | outage | empty | malformed occurred, and the gate prints that cause with its own remedy — strictRemedy('timeout') and strictRemedy('outage', bin) for the causes that seam already owns, a local batch-size remedy for a reply-shaped failure. This supersedes ONLY the one-batch clause of the 2026-08-18 Ruling; deterministic overflow failure survives unchanged, enforced on the TOTAL before any batch is planned (>200 findings, or a plan above 4 batches, exit 4 'split the staged change'). It also amends that Target's Rejected clause: per-finding model calls stay rejected; the bound moves from per-run calls (1) to per-call findings x sequential calls (12 x 4).
**Consequences:**
- Positive: Positive: the operator is never sent to CLI auth/quota for a healthy judge, and a large-but-legitimate diff becomes reviewable instead of unshippable at any retry count. Smaller batches also judge BETTER, since judgeBatchInput divides its 120k evidence budget by items.length — ~9.6k chars per finding at 12 against ~3.1k at 38. The ordinary 1-5-finding commit still makes exactly one call, so routine cost is unchanged.
- Negative: Worst-case wall clock rises to 4 x 120s = 480s (batches run in series because the gate is synchronous), sized to stay inside the 600s foreground agent-tool cap. Declared narrowing: a commit with more than 48 pending findings now blocks deterministically at exit 4 instead of failing open at 2/3 — which is what already happened undiagnosably in the regime that truncated at 38. Declared rotation: the prompt states a 240-character reason budget, so COMMENT_JUDGE_PROMPT_VERSION moves to 2026-08-28.1 and every persisted PASS receipt rotates once (the sc-2077 precedent).
**Vision-fit:** A gate that fails closed must say what would reopen it; a remedy that cannot work is worse than none.
**Researched:** The sc-2195 autonomous report's GUARD_COMMENTS_DEBUG capture; strictRemedy's own sc-1049/sc-1227 history of cause-specific remedies; the correctness-chunking-ships-dark env-kill-switch precedent.
**Rejected:** Rejected extending strictRemedy with a malformed/empty cause — the actionable remedy names GUARD_COMMENTS_BATCH, a gate-local knob that cannot live in a seam shared by review/completeness/decisions, and RESPONSE_CONTRACT_REMEDY already sets the local-remedy precedent for a healthy judge with a contract-failing reply. Rejected extracting resolveChunkCap's env-validation shape into a shared module: both candidate homes sit exactly at fanoutCap 12 and config.mts has one line of headroom, while the shared run falls under both dup-gate floors. Rejected a repack-at-doubled-caps backstop like chunk-tasks' MAX_CHUNKS, because coarsening the batch to fit is precisely the failure being removed. Rejected judging the first 48 of an over-cap set, which makes deterministic overflow non-deterministic. Rejected rejecting an over-budget reason at the parser: reason is display-only and absent from receiptKey, so clamping at 400 chars keeps a complete verdict set usable, while rejecting would trade an output-cap truncation for a parser-cap one. Rejected concurrent batch fan-out — runCommentFirewall and runCommentCli are synchronous, and 480s already fits the cap.
**Anchored-bet:** Naming the cause and splitting the batch converts the one comment-firewall failure the operator can act on from an undiagnosable fail-open into a converging retry.
**Revisit-when:** Production shows a 12-finding batch truncating, the 48-finding ceiling blocks legitimate commits, or the gate becomes async so batches can fan out concurrently.
**Scope:** gate-engine/comment-firewall/**,cli/lib/husky/**

## Target · 2026-09-02 — guard-comments is a purely deterministic budget gate

**Context:** Every new 3+ text-line comment paragraph cost at least one extra ship attempt by construction: the gate blocks first with 'need a decision', the agent writes a rationale, the re-ship runs a batched gpt-5.6-terra judge, and a rejection blocks again. That protocol accounted for 47% of the rise from 2.50 to 9.13 ship attempts per successful ship across v0.56.0, and it still let the paragraphs through. Owner ruling: a paragraph-long comment belongs in docs or a decision record, not in code; there is no waiver and no content exemption.
**Ruling:** guard-comments is a purely deterministic budget gate. The 2026-08-18 detector is unchanged (standalone JS/TS paragraph, 3+ added/modified non-structural text lines; inline and trailing comments, 1-2 line changes, untouched comments, deletions and pure renames pass), with one hardening: comment groups separated only by blank lines merge into one paragraph, so a 4-line paragraph cannot be split 2+2. On any finding the gate prints each finding and one remedy — shorten to at most 2 lines, or move the information into code, types, a test name/assertion, or a decision record — and exits 1. Exit 4 for unreadable evidence or an unsupported language stays. Exits 2 and 3, the rationale store, justify/list/prune, --from-ship-log, --ticket, the judge, batching, PASS receipts and the judge eval corpus are deleted. A CLI usage error exits 4, never 2, because the shared __dk_gate_ai hook helper passes on 2. The block's first line stays byte-identical ('N added/modified comment paragraphs need a decision') because the telemetry collector classifies on it, and commit-with-gate-capture.sh gains a comments arm so blocked_gate names this gate. This supersedes the 2026-08-15 clause that a purely syntactic hard gate would reject legitimate invariants, licenses and API documentation, and the 2026-08-18 Rejected clause on a hard two-line gate: this is that shape, chosen on purpose, keeping the 3-text-line threshold.
**Consequences:**
- Positive: Zero model spend and zero second round-trip on this gate; the remedy is the same for every finding and needs no store, receipt, or reviewer to converge. The readout survives: blocked_gate='comments' is now recorded in the ship envelope inside devkit rather than only mined from log text.
- Negative: The gate forbids devkit's dominant documentation style, the multi-line invariant paragraph (617 per fortnight on devkit, 1326 on frink). Those explanations move to a 1-2 line pointer plus a decision record when they are a ruling, a test name or assertion when they are a behaviour, and a named constant or type when they are a value. Evasion through trailing comments on consecutive code lines or 2-line comments interleaved with statements is never a finding (the inline exemption from 2026-08-18) and is accepted for now; the deferred edit-time PreToolUse hook owns it. The 3-line threshold is inherited untested under the new cost function — a false positive now costs a deleted comment, not a rationale — and the rollback knob is the >= 3 constant in requiresChallenge (raise to 4 if block share does not fall).
**Vision-fit:** A gate whose remedy is always the same needs no waiver machinery; devkit's governance stays proportional to the failure it prevents and never spends a judge on a question a line count answers.
**Researched:** Bun Comment Cop as currently deployed (.github/workflows/comment-cop.yml: advisory, MIN_LINES 2, SAFETY: exempt) and its live behaviour on oven-sh/bun PR 41188 (robobun shortened every flagged paragraph or defended a 2-line cross-reference; no rationale path). sc-2501's SHIP-RATIO-MEASUREMENT.md and the 2026-08-31 bench-validity RESEARCH.md. The dashboard collector's classify.mts regex and commit-with-gate-capture.sh's blocked_gate chain.
**Rejected:** A human-only justify with no judge — the same laundering, cheaper. A stricter judge prompt — the 80% justify rate is structural, not a prompt defect. Raising the threshold or a per-repo allowlist — both re-open a waiver by another name. JSDoc @param or license-header exemptions — empirically moot (none in the fortnight corpus) and gameable; owner ruling. A gate_events telemetry row — the 2026-08-29 declination stands, a deterministic gate has no judge outcome to describe; the in-scope readout fix is the blocked_gate arm.
