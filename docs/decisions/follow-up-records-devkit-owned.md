# follow-up-records-devkit-owned

## Target · 2026-10-21 — devkit owns follow-up records and the only auto-start path

**Context:** Follow-up handling lived only as prompt text in one machine's Frink Flow (frink-work's Track Follow-ups step). An agent classified each deferred item and wrote description lines on a Shortcut story, but nothing validated those lines, nothing bounded follow-up chains, and the depth-1 and wait-in-the-queue rules were policy only. The prompt does not travel to the owner's other machines, so the same discipline could not be used there. About 0.8 follow-ups are filed per PR, about 13% get done, and 25 of the last 40 frink-work trigger stories were themselves follow-ups.
**Ruling:** Classification stays agent judgment. devkit's cli/lib/follow-up/ owns the record schema, parsing and the start decision. The record is the description lines on the child story (**Follow-up of:** sc-N · <PR url>, **Follow-up type:**, **Stack on:**), kept byte-compatible with their existing readers. devkit reaches Shortcut only through the machine's short CLI and holds no token. 'devkit follow-up start --parent <story>' is the only auto-start path: it starts nothing when the parent is itself a follow-up (title starts with [auto-start] or it carries **Follow-up of:**); a child qualifies only as an open builds-on follow-up of that parent that, when the parent had a PR, carries **Stack on:** with that PR's URL; at most one child per parent ever starts, the lowest qualifying id; it renames the child '[auto-start] <title>' and then assigns it, and a rerun either stops (an assigned [auto-start] child exists) or assigns an unassigned [auto-start] child without renaming. blocks-done and discovery follow-ups always wait for a human. Assignment is the start signal; the run then waits in the consumer's own queue.
**Consequences:**
- Positive: One follow-up record any agent on any machine with short can read; depth and breadth enforced in code rather than by a prompt; compute stays bounded by the queue the follow-up waits in; the discipline travels with a devkit install.
- Negative: Narrows the deliberate human gate on follow-ups (filed unowned so nothing starts) for one class only: depth-1 builds-on children, at most one per parent. Adds a dependency on the short CLI and a title prefix humans will see. A human edit to the description lines can make a child ineligible.
**Vision-fit:** n/a — internal tooling
**Researched:** Prior-art review (2026-10-21, verdict: genuine new work, narrowed) of tracker-driven coding-agent orchestrators and agent harnesses: follow-up relations live in the tracker and are enforced in orchestrator code; the agent decides while scripts perform the writes; spawn depth is a counter checked in code. A six-seat red-team review (6/6, verified) checked the design against devkit origin/main and the live frink-work Flow: 1540 recorded trigger payloads carry the story title and none carry labels, priority or custom fields.
**Rejected:** A devkit ledger under ~/.devkit (not readable from another machine); a PR-body block as the record (two follow-up paths have no PR); git trailers (unreadable from the triggering story); a Shortcut label, Priority or custom field as the marker (never present in update payloads); a workflow state as the marker (needs per-workspace setup); agent-started child runs (no depth bound); continuing the follow-up inside the parent run (bypasses the queue that bounds compute).
**Anchored-bet:** [BET]
**Revisit-when:** A Shortcut update webhook is shown to carry priority or a custom field; the owner's work tracker is not Shortcut; or auto-started follow-ups complete below the 13% baseline over 10 parents.
**Scope:** cli/lib/follow-up/**,cli/commands/follow-up/**
**Source:** collab · sc-7472
- 2026-10-21 — devkit follow-up file is the writer of the record lines and the relates-to link: it validates every item before writing, files each story unowned in the parent's team and its workflow's default state, links it to the parent, and archives a story whose link fails so a rerun cannot file it twice. Free text may not contain a record label, because the readers take the first match. start now treats an [auto-start] child as started when it is assigned or closed, so clearing the owner of a finished follow-up cannot let a sibling start.
- 2026-10-22 — devkit follow-up status is the reader behind a PR's Feature done line, so the Flow stops parsing record lines itself. It lists the story's open follow-ups that are not discovery, untyped ones included as type null, and when the story's own record names a parent it adds that parent's other open follow-ups. Sibling detection reads the record instead of taking a --self flag, so a caller cannot disagree with the record. builds-on follow-ups hold featureDone false, matching the Flow rule this command replaces.

## Target · 2026-10-22 — Follow-ups finish in the parent run; the record is a footer and titles carry no marker

**Context:** The 2026-10-21 Target made devkit follow-up start the only auto-start path, rejected continuing a follow-up inside the parent run because it bypassed the queue that bounds compute, and marked started children with an [auto-start] title prefix. Measured since then: devkit owner-wait p50 is 26.6h; 36-65% of children never ran after their parent merged; 17 of 20 parents were partial on main; 50% of sibling pairs share a file and 33% of concurrent devkit siblings conflict; 24% of new follow-ups sit at depth 3 or more (1% before auto-start), with chains to depth 6. The owner also judged title metadata confusing for other users of a shared Shortcut workspace.
**Ruling:** A feature finishes as one draft PR inside the parent run, as sequential lanes under Frink fan_out (one admission slot, maxIterations 4, engine-enforced). The record lines (**Project:**, **Follow-up of:** sc-N · <PR url>, **Follow-up type:**, **Stack on:**) stay byte-compatible with their readers, which take the first match anywhere in the description; devkit follow-up file writes them as a footer under the human-readable body, and free text still may not carry a record label. No title prefix is written or read. Depth is the parent carrying a **Follow-up of:** line. A Frink guard Flow auto-assigns the single depth-1 remainder. devkit follow-up start stays as the trial fallback until the trial passes: it assigns the lowest-id open builds-on child stacked on the parent PR, and starts nothing once any non-discovery follow-up of the parent is owned or completed, so a rerun or a guard-assigned sibling stops it; an archived child does not count.
**Consequences:**
- Positive: - Positive: Features land as one PR without waiting a day per hop for the owner; sibling conflicts disappear because lanes run serially in one worktree; titles stay human; the depth marker still bounds chains to one unattended hop per root.
- Negative: The parent run holds its slot longer; a trial must prove lanes land (5 parents, at least 4 as one PR, no stranded drafts); start keeps a second, interim start path alive until then; Frink's guard Flow is a second reader of the record schema.
- Negative: Longer parent runs and an interim second start path, in exchange for features that land whole and titles free of machine markers.
**Vision-fit:** n/a — internal tooling
**Researched:** Red-team review 2026-10-22 (4/4 agree, verifier-signed, owner-approved) over devkit and frink-work Shortcut and PR history: owner-wait, child start rate after merge, partial parents, sibling file overlap and conflict rate, and follow-up chain depth before and after auto-start.
**Rejected:** A title marker (confuses other workspace users, and a Shortcut label cannot replace it because update payloads carry no labels); parallel sibling stories (50% share a file); merge- or story-moved-triggered starts (owner-wait p50 26.6h); readers taking the last match (Frink's router and Stack on reader take the first, so the two would diverge).
**Anchored-bet:** [BET]
**Revisit-when:** The 5-parent trial fails (fewer than 4 land as one PR, or a draft is stranded or a lane Ship fails), or the fan_out iteration bound stops being engine-enforced.
**Scope:** cli/lib/follow-up/**,cli/commands/follow-up/**

Frink fan_out now keeps the run in one admission slot with an engine-enforced maxIterations of 4, so continuing in-run no longer bypasses the bound.
