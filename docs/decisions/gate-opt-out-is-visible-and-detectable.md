# gate-opt-out-is-visible-and-detectable

## Target · 2026-08-05 — a gate that opts out must SAY so, and a repo must be able to detect that the opt-out was an accident

**Context:** The co-occurrence matcher fails open when guard.config.json has no indexPath — correct by default (gate-engine/config.mts:179-182; most repos have no search-code index). But a repo shipped for weeks with a fully-built 46MB .search-code/index.db while semantic duplication detection never ran, because only the indexPath key had gone missing. Three independent silences made that possible: (1) nothing DETECTED the misconfiguration — devkit doctor never looked, though .search-code/index.db is devkit OWN canonical path (INDEX_PATH, install-search-code.mts:14) written by its own setIndexPath, so index-present + key-absent is provably devkit wiring lost, not a preference; (2) nothing REPORTED the skip — run.mts mapped rc=2 + failOpen2 to pure silence and emitted NO telemetry (emitGateEvent fired only inside the fails branch), so the skip rate was unmeasurable and the matcher own stderr scrolled past at the visual weight of a gate that passed; (3) nothing could FORCE the issue — AI gates have GUARD_AI_STRICT and coverage is fail-closed-by-opt-in, but deterministic gates had no strict axis at all, which is the exact negative already recorded in zero-consumer-tool-deps: gates are fail-open, so CI/contributors MUST install the pinned global devkit or the gates silently skip.
**Ruling:** Fail-open stays the default; the SILENCE around it does not. Three layers. (1) DETECT: a doctor check (cli/lib/doctor/guard-config-checks.mts) reports DRIFT when the resolved indexPath is null AND either .search-code/index.db is on disk OR .devkit/config.json recorded searchCode. It is gated on the dup guard specifically (the only gate that reads the index), skipped when guard.config.json is itself MISSING/unparseable (same root cause, one line), and treats an EXPLICIT null indexPath value as a declared opt-out — resolveGuardConfig collapses absent and explicit-null, so the raw file is the one place they differ, which yields an escape hatch with zero new config surface. SEARCH_CODE_DB is checked directly because it is matcher-only and never reaches resolveGuardConfig. The fixable flag is CONDITIONAL on the recorded selection, since selectionFlags emits --search-code only for a repo that already has it — a warning promising a repair init cannot perform would never clear. It is a CheckResult in default mode and an ADVISORY line in overlay/self-host, which short-circuit before collectResults; without that the check would be unreachable in the devkit repo itself. (2) REPORT: runDeterministic collects fail-open gates into a skipped list, names them on GREEN runs as loudly as red, and emits one gate_result with status could_not_run per skipped gate so the rate becomes measurable at all. (3) BLOCK: GUARD_DETERMINISTIC_STRICT=1 turns an opt-out into label(could-not-run) and exit 1. Strict does NOT flip failOpen2: that flag is a property of the GATE (exit 2 is an opt-out for this one), strict is a property of the RUN (what we do about an opt-out), which is what keeps an --extra command fatal exit 2 at (unexpected:2) instead of relabelling it as a chosen skip. prefixCacheScope salts on strict for the same anti-laundering reason the coverage salt exists — a non-strict all-green key would otherwise be HIT by a later strict run of the identical tree, skipping every gate.
**Consequences:**
- Positive: The duplication gate a repo believes it is running is now the duplication gate it is actually running: a silent opt-out is detected before the commit that needed it, named at the moment it happens, and blockable in CI. Skipped-gate telemetry exists for the first time, so the fail-open rate across adopted repos can be measured rather than guessed. Strict covers every deterministic gate (dup, clone, size, fanout, structure-lint), closing the negative recorded in zero-consumer-tool-deps, and the explicit-null escape hatch lets a deliberate opt-out stay silent forever without a new config key.
- Negative: Doctor can only read the env it was handed, so a consumer who exports GUARD_INDEX_PATH/SEARCH_CODE_DB ONLY in the hook environment sees DRIFT in a bare shell — accepted, with the remediation naming both vars, because the alternative is not detecting the real case at all. A repo with a hand-wired index (searchCode:false) gets a correct but unfixable DRIFT it must clear by hand or by declaring an explicit null; fixable stays honest rather than promising an init repair that selectionFlags cannot emit. Strict is opt-in and NOT exported by devkit ship, so repos that never turn it on gain detection and reporting but no enforcement — the road not taken is defaulting it on, which would break every consumer whose index or jscpd is absent. The skipped-gate block also adds output to every run where a gate legitimately opts out.

**Rejected:** (a) a matcher --strict flag, as originally proposed — REJECTED: the matcher does not decide fail-open, run.mts does; putting it in the runner is smaller AND covers every deterministic gate. (b) exit 3 for a strict could-not-run, mirroring GUARD_AI_STRICT — REJECTED: exit 3 exists so an AI OUTAGE is never rendered as a finding (glossary:36-40); a deterministic opt-out is a local, reproducible condition (no index, no jscpd) with no outage to distinguish, so it belongs on the ordinary exit-1 failure path. (c) flipping failOpen2 under strict — REJECTED: it relabels an --extra command fatal exit 2 as a chosen skip and downgrades its telemetry from fail to could_not_run. (d) a doctor-side direct write of indexPath into guard.config.json — REJECTED: --fix does not make bespoke edits to a consumer config; the repair routes through init own --search-code step. (e) reporting DRIFT purely on index-on-disk, per the original report — REJECTED as too narrow alone: it misses a repo that opted in but has not built the index yet, so the trigger is the union of both signals. (f) enabling strict by default under devkit ship — REJECTED for now: it would flip behaviour for every consumer whose index or jscpd is absent.

## Target · 2026-09-30 — in overlay mode a missing devkit runtime or an incomplete worktree projection fails closed; per-gate opt-outs stay visible fail-open

**Context:** The 2026-08-05 Ruling kept fail-open as the default and removed the silence around it, one gate at a time. In overlay mode the whole chain could opt out silently instead: the overlay gates find devkit through command -v and skip when it is absent, and the linked-worktree prelude printed 'gates skipped' and exited 0 when projection failed. Nothing a per-gate report, telemetry or strict flag covers ran at all, and frink #5, #68 and #108 shipped from overlay worktrees whose commits ran no gates.
**Ruling:** Unchanged for a single gate that cannot run (no index, no jscpd, a judge outage): it keeps the visible fail-open of the 2026-08-05 Target, named on green runs, counted as could_not_run and blockable with GUARD_DETERMINISTIC_STRICT or GUARD_AI_STRICT. Narrowed for the chain itself in overlay mode: when guard-deterministic is not on PATH, or a linked worktree's projection cannot be completed, the overlay pre-commit exits 1 with a one-line remedy, and there is no fail-open path for either. Standalone installs keep their documented contract that their gates fail open when the pinned global CLI is unavailable.
**Consequences:**
- Positive: An overlay repo can no longer commit ungated by accident. The only remaining opt-out is git commit --no-verify, which the user types and sees.
- Negative: An overlay user without the global CLI is blocked rather than warned, including on a machine that only wanted to commit docs. The per-gate command -v checks in the overlay gate body stay until the hook renderer is unified, though with devkit absent they are never reached, because the prelude has already exited.
**Vision-fit:** n/a — internal dev/CI tooling.
**Researched:** cli/lib/husky/husky-block.mts (the overlay gates' command -v guard-deterministic lines), cli/lib/husky/overlay/overlay-home.mts (the deleted 'gates skipped' branch), README.md (standalone fail-open contract), docs/decisions/overlay-self-heal.md (the 2026-09-30 re-target that makes the prelude fail closed).
**Rejected:** (a) Fail closed for standalone installs too: the owner kept standalone's documented fail-open contract, since standalone targets repos whose contributors may not install devkit. (b) Make every overlay gate fail closed individually: the prelude's one bin check covers the whole chain at once, and a per-gate outage still deserves the visible fail-open this axis rules.
