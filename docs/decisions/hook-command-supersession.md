# hook-command-supersession

## Target · 2026-09-04 — A changed hook command carries its ownership forward

**Context:** devkit records the exact command string of every agent hook it registers in an ownership ledger, and matches on that string byte-for-byte. That made every command a compatibility surface nobody had noticed: sc-2563 needed one searchSteering command corrected (it named a path that ships only under dist/, so both hooks died with MODULE_NOT_FOUND on every Bash tool call in every packaged consumer, silently disabling the guard). Landing that one-line correction alone would have been WORSE than the bug it fixed — partitionLedger routes the now-unrecognised ledger row to untrusted, sameOwnershipKey is unchanged by a command edit so the corrected registration is blocked, and installHookRegistrations throws. Every affected consumer would have gone from a dark hook to a devkit init and devkit upgrade that abort outright, and the affected population is exactly the one that reported the fault.
**Ruling:** A registration whose command string changes records its prior spelling in SUPERSEDED_HOOK_COMMANDS, in SOURCE form, beside the live command. Reconciliation runs once per provider per destination before scope transfer, removal and install, and does two things in the same publishPlan transaction: it carries devkit's own ledger row forward onto the current spelling, and it strips the prior spelling from the provider document. Provider spellings are derived by running each table row through the same nativeProjection a live install uses, never hand-transcribed, so codex and cursor are covered by construction. The document strip is gated on a ledger row for that exact registration and owner holding either the prior or the current spelling; the second arm recovers the crash window inside publishPlan's ledger-document-ledger write order. This is distinct from RETIRED_COMMANDS, which handles a registration that is GONE and accepts the literal itself as ownership proof because a pre-ledger config has no row to vouch for it.
**Consequences:**
- Positive: A consumer picks up a corrected hook command by running the upgrade they were going to run anyway: no hand-edited settings.json, no abort, and no window in which the agent harness is registering a hook that cannot run. Devkit can now correct a command it has already shipped, which it previously could not do at all without breaking installed consumers.
- Negative: Every future command-string edit must add a table row or it breaks the fleet, and the table accretes until someone can show no supported install still holds a given spelling — the since field records the shipping release so that call rests on evidence, but nothing forces the retirement. Reconciliation also projects the whole table on every provider pass of every install. And devkit now holds a power it did not have: rewriting rows in its own ledger. That is bounded to rows matching provider, destination, registrationId, owner, event and matcher, with the replacement produced by the trusted projection rather than by string editing, so a consumer-authored command that merely resembles a devkit one has no row and is never touched.
**Vision-fit:** n/a — internal developer tooling
**Researched:** sc-2563 evidence; the ledger decision core in cli/lib/install/hook-registration-ledger/lifecycle.mts traced state by state (partitionLedger, exactEntry, eventMatch, installProjectedHookRegistrations); the existing RETIRED_COMMANDS precedent and the sc-1321 pre-ledger reclaim it was built for.
**Rejected:** (a) Rewrite the ledger row and leave the document alone — BROKEN, not merely weaker: eventMatch searches for the NEW command, finds neither an exact nor a related match, and addRegistration appends it beside the prior spelling, which no ledger row now owns and nothing will ever remove. Strictly worse than the throw it was meant to avoid. (b) Extend RETIRED_COMMANDS with a ledger arm — WRONG KEY AND WRONG PROOF: it is keyed by componentId, but searchSteering owns two registrations with different commands, so it cannot name which row to repair; and its hand-written per-provider literals would silently stop matching the next time cursorCommand changes its reduction rules. (c) Reuse adoptExactLegacy — STRUCTURALLY CANNOT WORK: adopt() filters candidates by ownedKey, which the stale row already holds, so the corrected entry is dropped and the stale row survives to block the install. (d) Migrate at the ledger seed rather than per provider — breaks the invariant that ledger and document move together: migrating a codex row while targets is claude alone would declare .codex/hooks.json correct while it still holds the prior spelling.
**Anchored-bet:** [BET]
**Revisit-when:** The ledger stops keying ownership on exact command equality — e.g. a schemaVersion bump that records a stable target identity (scriptRel, or the registrationId alone) instead of the rendered string. At that point a command edit is no longer a compatibility break and this whole mechanism can be deleted.
**Scope:** cli/lib/install/hook-registration-ledger/**,cli/lib/install/install-hooks.mts
**Source:** shortcut · sc-2563
- 2026-09-04 — sc-2563 — the document strip is narrowed to the EVENT and MATCHER the ledger row names, not just its command string, and the first implementation got this wrong. Written command-keyed, it walked every event: a consumer command spelled identically to devkit's prior one but wired to an event devkit never registered — a Stop hook rather than PreToolUse:Bash — was deleted along with devkit's own, and where that emptied a scaffold-only group the whole event key went with it. That is a direct violation of non-devkit-asset-collision-preserve, committed by the mechanism whose entire justification is that a ledger row makes its ownership gate STRONGER than the retired-command arm's. The row names a location; not using it threw away the very thing that distinguishes the two arms. The asymmetry with RETIRED_COMMANDS is therefore deliberate and load-bearing rather than incidental: retirement accepts the command string as proof wherever it appears BECAUSE a pre-ledger config has no row saying where devkit put it (sc-1321), while supersession has that row and must stay inside it. Both arms now share one stripHandlers walk taking an (event, matcher, command) predicate, so the difference between them is exactly one function and cannot drift into a copied walk. Accepted consequence, the other side of the same choice: a consumer who RELOCATES devkit's command to another event keeps their relocated copy and gets a fresh canonical registration beside it, rather than having their edit silently reverted — the conservative direction for consumer-owned config, and no worse than the drift that edit already produced. Covered by three cases in legacy-commands.test.mts (wrong event, wrong matcher group, and the cursor flat-list shape where the nested walk never runs and event narrowing is the only guard).
- 2026-09-04 — sc-2563 — a registration can have shipped MORE THAN ONE prior spelling, and the first implementation silently assumed one. SELF_EXT made the emitted extension depend on how devkit was RUNNING, so search-steering has two prior spellings (.mjs from a packaged install, .mts from a source-context one) and therefore two table rows sharing a single current command. Reconciliation picked its match with .find(), so a ledger row already carrying the CURRENT command — the crash-window state, where publishPlan wrote the ledger and died before the document — matched the FIRST projection by its current-command arm and authorised stripping only the .mjs spelling. A consumer whose document still held .mts got the dead hook stranded and the current command installed beside it: precisely the duplicate-orphan failure the crash-window arm exists to prevent, reintroduced through the arm itself. The unit test missed it because it exercised the crash window with the .mjs spelling only, which is the one .find() happens to return. Ruling refined: a claimed row authorises stripping EVERY prior spelling of that registration at the location the row names, not just the spelling the row itself holds. Sound on ownership grounds because devkit is the sole writer of those strings and the location gate is unchanged, and necessary because a row carrying the current command carries no information about which prior spelling the document still has. Regression covered by an it.each over both extensions, so a future single-spelling assumption fails on the .mts leg. Found by commit-guard and correctness-reviewer independently at the ship gate, both escalation-confirmed.
