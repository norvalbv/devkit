# oxc-toolchain-migration

## Target · 2026-08-15 — Migrate quality tooling to Oxc one proven responsibility at a time

**Context:** Devkit and Frink split quality work across Biome, ESLint, and TypeScript, making every agent loop pay several processes and leaving anti-slop outside the standard ruleset. A one-off Devkit control measured type checking as the largest standalone lane at 2.185 s median wall time and 443.1 MiB median RSS, but the Frink compatibility study also found that an all-at-once Oxc swap would silently lose non-JavaScript topology coverage and would rely on experimental TypeScript-7-oriented type checking while Frink uses TypeScript 6.
**Ruling:** Adopt Oxc incrementally, one responsibility at a time, only after the candidate preserves that responsibility's diagnostics and scope on pinned Devkit and then Frink inputs. Target Oxfmt for formatting, native Oxlint for ordinary and compatible ESLint rules, and vendored anti-slop in the same Oxlint configuration. Keep the current Biome, ESLint topology path, and tsc ownership until their individual parity conditions are proven; replace filesystem topology with a dedicated policy runner rather than a partial source-only port.
**Consequences:**
- Positive: Agent feedback can become faster and less memory-intensive without trading away import walls, asset and empty-directory topology, formatter stability, or compiler diagnostics. Future contributors can tell which Oxc migrations are intended and which retained tools are deliberate temporary owners rather than forgotten duplication.
- Negative: The repository carries a mixed toolchain during migration and must run one-off paired parity experiments before each removal. This delays a single-command Oxc end state and temporarily duplicates configuration, but avoids a fast command that checks fewer files or reports fewer errors.
**Vision-fit:** Internal tooling: reduce CPU time and memory so autonomous agents reach trustworthy feedback faster.
**Researched:** Shortcut sc-1674; the [consolidated 2026-08-15 Devkit/Frink report](../benchmarks/experiments/2026-08-15-oxlint-js-plugin-frink/README.md); official Oxc Oxlint, JS-plugin, Oxfmt, and type-aware documentation; official Biome plugin documentation; anti-slop upstream.
**Rejected:** An immediate full Oxc replacement was rejected because Oxlint JS plugins cannot run the custom parser used for CSS, HTML, assets, and empty-directory topology, and its compiler-diagnostic path is experimental and targets TypeScript 7 semantics. Keeping the current stack indefinitely was rejected because the measured control identifies material CPU and memory targets and Oxc has compatible native rules plus the required anti-slop plugin model. Consolidating on Biome plugins was rejected because GritQL plugins are not ESLint-compatible JavaScript plugins and do not provide the required multi-file and semantic APIs.
**Anchored-bet:** [BET]
**Revisit-when:** Remove each incumbent only when a pinned paired experiment proves diagnostic and scope parity, plus a worthwhile wall-time or memory improvement, first in Devkit and then in Frink; reconsider the topology runner if Oxlint gains custom-parser and arbitrary-file coverage, and reconsider tsc when the candidate supports Frink's TypeScript semantics.
**Scope:** package.json,biome.jsonc,eslint.config.mjs,guard.config.json,gate-engine/structure/**,eslint/**,docs/benchmarks/**

## Target · 2026-09-03 — overlay installs anti-slop through a git-excluded ROOT entry config; the runtime-only clause is superseded

**Context:** sc-1964 declared overlay 'runtime-only so its local-only contract never writes tracked root configs', and sc-1675 before it declared 'overlay and self-host activation remain unsupported'. So devkit's strongest policy layer was unavailable in the one install mode built for a repo a team will not let you modify, and the refusal at anti-slop/lifecycle.mts named a cause that was not true: 'requires the tracked Oxc capability'. Both halves of that premise fail. The RUNTIME never needed the consumer — resolveOxcRuntime resolves oxlint and @oxlint/plugins through createRequire(import.meta.url) from devkit's own exact dependencies, so a global overlay install already carries them. The CONFIG chain needs a root-LOCATED file, not a tracked one, and overlay already ships that idiom twice (eslint -c eslint.config.devkit.mjs, biome check --config-path biome.devkit.jsonc). The cost was concrete: owners-web has no oxlint, no biome, and eslint 8 via .eslintrc.cjs, so writeEslintOverlay skips and the overlay eslint leg is permanently inert — anti-slop would be the only devkit lint layer that actually ran there.
**Ruling:** Overlay writes a git-excluded ROOT sibling entry config, oxlint.devkit.json, extending ./.devkit/oxc/oxlint.base.json — the same ours-extends-theirs shape as biome.devkit.jsonc — and every anti-slop oxlint spawn passes -c that file. The mode signal is SPLIT BY SITE. Readers (runner.mts, probeIntegration) resolve it from a new optional non-validating overlayEntryConfig stamp in .devkit/oxc/manifest.json, because a reader's cwd may be a mkdtemp extraction of the Git index where no repository marker exists, and the manifest travels there with the capability. The WRITER resolves explicit-flag then overlayInstall(cwd) then the stamp, and additionally REFUSES to create any discovery-named root config when overlayInstall(cwd) — because readManifest collapses missing/corrupt/wrong-version into null, which is exactly the state checkOxcCapability reports as MISSING and doctor --fix then repairs, so a stamp-only writer would lose the mode precisely when asked to repair and plant a visible root config. The staged gate injects the git-excluded capability plus the baseline into its snapshot on an EXPLICIT overlay branch, never unconditionally. .devkit/oxc, .devkit/anti-slop, oxlint.devkit.json and .anti-slop-baseline.json join GATE_PROJECTION_FIXED_CANDIDATES so ship and review reproduce the commit gate. The baseline is created once at install, create-if-absent and never --force, and a new scoped 'anti-slop adopt-activation' verb adopts a newly activated rule's inherited debt without re-snapshotting anything else. --base and adopt-renames are refused in overlay. Install refuses outright when git tracks any owned path, or when the repo owns its own Oxlint config. Every run prints the weaker overlay contract, green runs included. Package mode is unchanged.
**Consequences:**
- Positive: devkit's strongest policy layer becomes available in the mode built for repos devkit does not own, with zero committed footprint: verified end to end on a throwaway overlay fixture — install, git status --porcelain empty, a staged violation blocked by guard-anti-slop while the grandfathered one stayed forgiven, a zeroed baseline surviving a re-init, and --base refused. The invasive-write hazard is closed at the writer rather than per caller, so all eight syncOxcCapability call sites are covered by one guard. ship and review inherit the capability through the projection registry that already exists for git-ignored overlay inputs, so no new machinery. A newly activated rule no longer forces create --force, so the no-laundering guarantee is real rather than nominal.
- Negative: The overlay gate is materially weaker than package mode and says so instead of hiding it: baselineAtTree is always null there, so checkBaselineEnvelope short-circuits and the shrink-only ratchet, rename receipts and CI monotonicity never fire — it blocks new findings against a per-clone, git-ignored, unshareable baseline the holder can silently regenerate. requiresFullScan also never triggers on the untracked capability, so a plugin change does not force a re-scan. -c replaces discovery outright, so a consumer's own Oxlint config would stop being read; rather than override it silently the install REFUSES, which means composing with a consumer config is a real user-facing gap until extends-chaining is proven. One more optional manifest field, and a second mode-resolution rule to keep in step with the first.
**Vision-fit:** n/a — internal dev tooling; overlay runs guardrails on a shared repo a team would reject a PR for.
**Researched:** Measured on the pinned oxlint 1.78.0. -c fully replaces config discovery (oxc.rs nested-config docs, and apps/oxlint gates nested lookup on config.is_none()). Relative extends and jsPlugins[].specifier resolve from the file that DECLARES them, but overrides[].files globs resolve from the ENTRY config's directory: -c .devkit/oxc/oxlint.base.json reported 30 anti-slop findings inside .devkit/anti-slop/plugin where discovery reported 0, and tripped eslint(no-undef) on .devkit/anti-slop/probe.ts. A root sibling reproduced discovery byte for byte on both. CRUCIALLY the production integration probe would NOT have caught that: probeIntegration lints a mkdtemp file matched by the '**/devkit-anti-slop-integration-probe.ts' glob, whose '**/' prefix is base-INSENSITIVE, so it stays GREEN under the broken geometry — the fail-closed sentinel cannot detect this class of misconfiguration, which is why the root placement is pinned by an explicit test instead. No upstream fix is pending: maintainer leaysgur on oxc#24276 names --config-root/basePath as the right approach and says 'we won't implement this immediately', PR #18448 (--cwd, motivated verbatim by a tool caching its config outside cwd) and #18564 are closed unmerged, and 1.79-1.81 touch no config-discovery surface; the glob-base behaviour is also unreported upstream and contradicts oxc PR #24339's own stated model. owners-web sizing: 2,537 files scanned, 1,416 findings, 1.07s wall, 572 files (22.5%) carrying at least one finding, dominated by require-safety-comment-for-type-assertion (782) and no-module-mocking (206). That 22.5% is why overlay's existing staged-only-no-baseline idiom (husky-block.mts:248-252) does not transfer: the eslint/biome overlay configs EXTEND the repo's own, so the code already passes them, whereas anti-slop introduces 1,416 violations from zero and would block on roughly one file in four touched. **Rejected:** (a) pass -c .devkit/oxc/oxlint.base.json, which already extends the anti-slop config and declares the probe global — REJECTED on measurement: it shifts every overrides[].files glob base into .devkit/oxc/, voiding the agent-dir and vendored-plugin rule-offs (30 findings appear) and the probe-global override, and the runtime sentinel cannot see it. (b) write the discovery-named root .oxlintrc.json and rely on discovery — REJECTED: impossible where the consumer already tracks one, and it hijacks the consumer's own oxlint and IDE tooling in a repo devkit promised not to touch. (c) adopt the working-tree capability into EVERY staged snapshot rather than an overlay branch — REJECTED: in package mode the extraction already carries the capability from the index, and overwriting it leaves bytesOk passing (copied manifest digests match copied bytes) while activationEvidenceAtTree and baselineAtTree still read the index tree — a lint under one capability judged by another's evidence, with no detector. (d) chain the consumer's Oxlint config as a second extends entry — DEFERRED, not adopted: inter-extends precedence is not provable via --print-config (it under-reports jsPlugins and rules from extends) and must be established from lint output; the install refuses instead of guessing. (e) make the manifest stamp the writer's authoritative mode signal — REJECTED: the stamp is absent in exactly the repair state, so doctor --fix would plant a tracked-shaped root config on the path devkit itself advertises as the remedy.
**Anchored-bet:** [UNVALIDATED]
