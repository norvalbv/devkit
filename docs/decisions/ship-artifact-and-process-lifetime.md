# ship-artifact-and-process-lifetime

## Target · 2026-08-27 — devkit owns the lifetime of the process groups it detaches, and a ship records enough for a later run to reclaim what it left

**Context:** sc-2159: a backgrounded devkit ship was reported killed by the agent harness, but its child process tree kept running detached — pgrep showed 3 live processes and the log kept growing with fresh reviewer verdicts minutes after the kill notification. The surviving pipeline created its ephemeral devkit-ship-<branch>-<pid> worktree and local branch; nothing reclaimed them. Every later attempt then refused with 'branch already exists … cannot safely resume it', a message about commit topology for a problem that was a dead process leaving a lock behind — and the branch could not even be deleted by hand without first finding the worktree holding it. Observed twice in one session; each occurrence cost a wasted ship attempt plus manual worktree remove + branch -D + prune. The forcing question was whether the process-group half belongs to devkit at all, or to the harness that issued the kill.
**Ruling:** Both halves are devkit's. (1) devkit ship adopts runManagedPackagedScript, as devkit review already did: the script gets its OWN process group and signals are forwarded to that group, not to the wrapper alone. (2) Because SIGKILL is uncatchable, signal forwarding can never be sufficient, so every ephemeral ship worktree writes a run record — pid, start-time identity, gate supervisor pid, the base it was cut from, and whether this run created the branch — into the worktree's git ADMIN dir, where it outlives the worktree directory, is deleted for free by worktree remove/prune, and cannot reach a commit. A preflight reads that record before the branch is read and reclaims the worktree and branch ONLY when the record proves abandonment; otherwise it refuses naming the live pid, or reports and falls through. The governing invariant is no record, no destructive action: an unattributable worktree is never touched.
**Consequences:**
- Positive: Positive: a killed ship stops costing a manual cleanup and a wasted attempt. A signal aimed at ship now reaches ship's whole tree, and a SIGKILL that no signal handling can cover is survivable because the next run reclaims what the dead one left. Refusals name the blocking worktree and whether a process still holds it, so the failure is diagnosable rather than a commit-topology riddle. Negative: liveness rests on ps start-time identity, which is locale- and timezone-formatted, so writer and reader must share one pinned LC_ALL=C TZ=UTC command or a LIVE ship reads as dead and its worktree is force-removed mid-gate. devkit still cannot ask which process holds a directory as its cwd (no lsof/fuser/pgrep dependency), so pid-or-gate-pid liveness is an approximation. Orphans created before this shipped carry no record and are therefore reported, never reclaimed.
- Negative: Accepted a small durable on-disk record per ship, and an approximate liveness test, in exchange for removing a manual-recovery step from the failure path that agents hit most. Rejected filing the process-group half as harness-owned under devkit-gates-repo-not-harness: that axis governs an agent driving FOREIGN harness tooling, whereas gate-supervisor.mts spawns the surviving group itself with detached:true and ship.mts had simply not adopted the managed spawn review already used.
**Vision-fit:** n/a — internal tooling (devkit is dev infrastructure).
**Researched:** Traced the kill path end to end: cli/commands/ship.mts used runPackagedScript (spawnSync, no process group, no forwarding) while cli/commands/review.mts already used runManagedPackagedScript; gate-supervisor.mts spawns the gate child detached:true with its group id held only in a closure-local variable, never persisted. Verified on git 2.50.1 that worktree list --porcelain reports realpath-resolved paths and that the admin dir's gitdir file matches them byte-for-byte, and measured that ps -o lstart= differs across LC_ALL and TZ for one live process.
**Rejected:** (a) Keying orphans on the worktree PATH — REJECTED: ship mangles slashes to dashes in that name, so feat/x and feat-x collide, and macOS TMPDIR symlinks make a reconstructed path never match. (b) kill -0 as the liveness test — REJECTED: it answers 1 for EPERM as well as ESRCH and says nothing about pid reuse. (c) A refs/devkit/* run namespace — REJECTED: reconcile pins that namespace empty after a run, and a ref survives a SIGKILL with no natural GC. (d) The record inside the worktree — REJECTED: the gate chain runs arbitrary consumer tooling that may git add -A or git clean -fdx, and commit-scope assertions bound unbriefed deletions rather than additions, so a leaked record would ship silently.
**Anchored-bet:** Artifact reclamation is the backstop, not the signal handling: any future kill path devkit cannot intercept degrades to one advisory line and a retry rather than manual recovery.
**Revisit-when:** An orphan recurs WITH a record present (the preflight had the facts and still could not act), or a platform arrives where ps -o lstart= is unavailable and presence-only liveness starts refusing reclaimable orphans indefinitely.
**Scope:** cli/lib/ship/**,cli/commands/ship.mts,cli/commands/release.mts

- 2026-08-30 — sc-2261 — the preflight now attributes the branch's holder to the CALLER'S OWN worktree (compared by git admin dir, never by filesystem path) and prints the two commands that free it. Previously a linked worktree was told to force-remove the tree it was executing inside, and a main tree got 'switch it off' without naming what to switch to. Same 'reports and falls through' clause, no new destructive path. Paired with a PR-base preflight: the DEFAULT base (this checkout's branch) is now proven to be a branch ON ORIGIN before the worktree, the commit and the push, so shipping from a provisioned worktree's local-only scratch branch refuses early instead of pushing a branch whose PR then cannot open; and the post-push PR-create hint re-verifies the recorded base on origin: it KEEPS that base when the branch is still there, and also when the re-verify itself fails (only ls-remote exit 2 proves absence), because gh fails for causes unrelated to the base and swapping a deliberately chosen one would retarget the PR; it names a different base only when the recorded one has genuinely left origin, and says so.
- 2026-08-30 — sc-2273 — the record's authority stops at the artifact: it never licenses removing the worktree the preflight is EXECUTING IN. Reclamation begins by force-removing that directory, and git has no self-guard, so a caller standing in a leftover ship worktree with an abandoned record had its tree and everything staged in it destroyed, then wedged every later git -C "$PWD" into 'Unable to read current working directory' — surfacing downstream as a push refusal blaming ls-remote. Reachable because ship itself invites the operator in ('Worktree KEPT for diagnosis / Inspect:'), and from reship too, which shares the preflight. That entry now refuses and names a checkout to re-run from; the orphan is still reclaimed normally from any other cwd, so the Target's primary behaviour is unchanged. The three advisory arms were corrected in place rather than unified: the kept-worktree arm KEEPS its removal command (the only cleanup a kept tree ever gets) and gains 'run it from outside', the live arm keeps its already-process-gated command, and neither adopts sc-2261's rename remedy — renaming a branch a running ship holds checked out and will push -u is a worse harm than the advice being fixed.
- 2026-09-01 — sc-2471 — a same-branch competitor meets the ORPHAN PREFLIGHT, not the publish lock. A second reship for a branch whose publisher is parked in gh pr edit refuses at ship_reclaim_orphan_worktrees (reship.sh:490): the parked run's detached worktree and its devkit-ship-run record are established at :600/:604, long before the edit at :1010, so _ship_orphan_alive answers ALIVE and _ship_orphan_report_live refuses — the competitor never reaches rewrite_publish_lock_acquire at :544. The lock is not dead code either: a competitor whose preflight completes before the holder's worktree exists still genuinely blocks at :544. What was wrong was the test. reship.test.mts's concurrent-intent case synchronised on a fixed 250ms sleep, so on an unloaded box the recovery finished first and the case passed for the wrong reason, while on loaded CI it flaked two ways (ENOENT on the gate log, or a failure naming 'another ship ... is still running'). Its 5s pause-marker deadline was the second half: reaching gh pr edit means cutting a gate worktree and refreshing reviewer assets, which exceeds 5s here, so the escape hatch fired, released the pause, and let the recovery finish BEFORE the competitor was spawned — the setup proved nothing even when green. The case now awaits the competitor's own exit before releasing the pause and bounds the marker wait at 60s as a hang detector, which makes the preflight refusal the only reachable outcome; it asserts only the stable first refusal line, deliberately not the trailing 'git branch -D' remedy, which is mode-unaware and wrong for a detached reship worktree. rewrite_publish_lock_acquire also gained its first coverage, via a pre-seated lock whose holder pid cannot be proved live.
