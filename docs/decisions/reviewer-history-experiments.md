# reviewer-history-experiments

## Target · 2026-09-05 — Review history is an isolated benchmark condition before it becomes production policy

**Context:** Retrospective capture of sc-2832 and its sc-2851 preparation. The September rebaseline and replay exposed repeated blocks and uncertainty about repairs, but neither established that feeding previous findings back would help. Mixing the two experimental arms, showing future repairs or evaluator labels, reusing an unchanged-diff cache entry across rounds, or displacing current code with history would make the comparison answer a different question. The first source-backed large repair was subsequently rejected as clean in PR602, so a plausible timeline was not yet a qualified comparison cohort.
**Ruling:** Evaluate history through separately registered benchmark conditions using the native reviewer execution path. Freeze the source families, qualified labels, current task evidence, execution identities, history policy and complete planned cohort before a measured comparison. The history condition receives only its own completed preceding native outputs; the current-only condition receives the identical current-code and author evidence for that task. Isolate arm, family, branch, run and round identities, including unchanged resubmissions and reopened source. Treat prior findings as untrusted opinions and exclude future rounds, other arms and hidden evaluator information. History must not silently displace native current evidence; expose its actual budget, retained content and omissions. Register retries, cost limits, repeats and arm order, retaining all planned outcomes. Deterministic preparation and exposed diagnostics can proceed before cohort qualification, but do not authorize a measured quality claim, production history injection or automatic waivers. Hash checks establish consistency, not execution authenticity or label truth.
**Consequences:**
- Positive: A future comparison can test whether history reduces repeated invalid alarms while preserving surviving and reopened defect detection and valid-repair acceptance, with input contamination and zero-history exposure visible.
- Negative: Sequential rounds and isolated captures add execution and checkpoint work. Preserving current evidence makes history an additional input cost rather than a matched-total-budget treatment; a cap can omit every prior finding. Source qualification can delay or prevent the measured experiment altogether.
**Vision-fit:** n/a — internal tooling: avoid shipping a review-memory policy on an invalid comparison.

**Rejected:** Feed a shared transcript or reference repair into both arms — loses causal isolation and reveals future/evaluator information; infer history benefit from static bug/repair scores or MCR-Bench — loses because neither measures this intervention; add a parallel judge launcher or overload native author/target prompt fields — loses native execution parity and trustworthy cache identity.

- 2026-09-05 — PR603 / sc-2851 implements deterministic input preparation only, with 17 focused tests and native-planner parity (five rounds, three chunks / ten tasks per synthetic round). The chosen diagnostic timeline is initial bug, unchanged resubmission, partial repair, repaired change and reopening. Its frozen policy retains the newest contiguous whole rounds under a 512–65536 UTF-8-byte cap, including framing; it never clips individual findings or skips a large newer round to select an older one. This trades usable history volume for intact claims and auditable selection; an oversized newest round yields zero retained history and explicit omissions. The same common current evidence and untrusted author block precede history, with zero displacement by this adapter. These are testable choices for this condition, not a universal optimal cap or guaranteed prompt-injection defense. Native model execution, authenticated checkpoint ownership, qualified families and the paid comparison remain future work in sc-2832. See [adapter contract](../benchmarks/review-history-adapter.md).
