# published-version-tags-immutable

## Target · 2026-08-04 — published version tags are immutable; consumer lockfiles record the object they resolve to

**Context:** sc-1449: a consumer's bun install died with 'no commit matching "590bae24f77816d943fa7c4814c4ea833ef0aa33" found for "@norvalbv/devkit" (but repository exists)'. devkit's main was rewritten around 23-24 Jul (backup/main-before-slice-coauthor-fix on origin) and the four early LIGHTWEIGHT tags (v0.1.0, v0.2.0, v0.3.0, v0.8.1) were re-pointed onto the rewritten commits. That orphaned the object consumer lockfiles had already recorded: 590bae24 now resolves to nothing on the remote or in any local object DB, while v0.1.0 points at 3084b25. Blast radius is every environment lacking that object in a local cache — a fresh clone or CI — and it is silent until then, because a machine with warm caches keeps installing fine. Three frink branches still carry the dead pin. The failure names neither devkit's pin nor any repair, and it is self-sealing: once install aborts there is no node_modules/.bin/devkit left to run devkit doctor with.
**Ruling:** A published version tag is immutable and published history is never rewritten. This is a hard constraint, not a preference, because bun records in bun.lock the OBJECT a tag resolved to — the annotated tag object for a github: shorthand pin, the peeled commit for a git+ssh/git+https pin — never the tag name; re-pointing a tag therefore orphans every SHA already recorded downstream. Enforced in depth: devkit release refuses a tag that exists locally OR on origin (remoteTagExists, network failure = proceed so offline is not blocked), and devkit doctor's new 'devkit lock' check verifies the recorded object still resolves on the remote the consumer actually pinned, so a dead pin is found on a working machine instead of in someone else's CI.
**Consequences:**
- Positive: A consumer who runs devkit doctor learns their next fresh clone or CI install will fail, in devkit's own words, with a repair command that was verified to work — instead of meeting an opaque bun error in an environment where devkit can no longer run. The release path can no longer re-cut a version that exists on origin but was never fetched locally.
- Negative: doctor now makes one git ls-remote per run in package mode, so it needs the network to say anything (it reports OK/'not verified' when the remote is unreachable, never DRIFT — offline must stay clean). The check is a heuristic over a lockfile it cannot parse as JSON, so it buys its low false-positive rate with a long skip list (branch pins, stale requests, overrides, multiple disagreeing resolutions, non-fetch URL schemes); each skip is a case where a genuinely dead pin goes unreported. And the immutability rule itself is only as strong as the humans following it — no gate can stop a force-push from outside devkit's own release command.
**Vision-fit:** n/a — internal tooling (devkit release + consumer distribution)
**Researched:** Empirical, on bun 1.3.1, in two hermetic scratch repos (BUN_INSTALL_CACHE_DIR isolated) reproducing both recorded forms. The git+ssh form reproduces the ticket's error verbatim; the github: shorthand fails instead with 'GET https://codeload.github.com/norvalbv/devkit/legacy.tar.gz/590bae2 - 404'. Repair candidates measured, not assumed: bun update <dep> REPAIRS both forms (resolution returns to the live object, dep installs); deleting the lockfile entry or the whole lockfile also repairs; bun install --force does NOT (it re-extracts, it does not re-resolve); bun pm cache rm neither repairs nor is required, and it destroys the cached bare clone that may hold the only local copy of the orphaned object. devkit update is NOT a repair when the repo already pins the newest tag: it short-circuits as 'up to date' at update.mts:186-189.
**Rejected:** (a) Treat this as a consumer-side lockfile refresh and close it — LOSES ON RECURRENCE: it fixes one lockfile and leaves the next dead pin just as undiagnosable. (b) Skip the check whenever DEVKIT_REPO is set — LOSES ON COVERAGE: DEVKIT_REPO is documented as an ssh host alias for the SAME repo, and the ssh form is exactly the one that recorded the 40-char SHA that broke here, so the skip would blind the affected cohort; the check derives its remote from the consumer's own package.json ref instead. (c) Query ls-remote --tags only — LOSES ON PRECISION: a lockfile recording a branch commit from before a re-pin is healthy, so --tags alone false-DRIFTs it; the check reads --tags --heads and skips when the lockfile's recorded request disagrees with package.json. (d) Publish devkit to a registry and drop git-tag pins entirely — the real cure for the whole class, but a large change across release, init, update, doctor and every consumer; not taken now.
