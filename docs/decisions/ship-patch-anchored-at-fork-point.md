# ship-patch-anchored-at-fork-point

## Target · 2026-09-01 — ship's explicit-paths patch is anchored at the fork point and three-way merged

**Context:** An autonomous report (7f42f04c -> sc-2451, severity high) recorded a detached worktree cut at a4e71f69 while origin/main advanced to 77308735, which added the --dry-gates help to cli/commands/ship.mts. The caller staged unrelated additions to that same file. 'devkit ship --base main' refreshed BASE to 77308735 and applied the caller's patch, and the prepared commit REMOVED the newer --dry-gates usage/help/exit text. The mechanism: in explicit-paths mode ship-branch.sh diffed the REFRESHED base tree against the caller's WORKING TREE, so every byte the base landed after the fork read as a deletion. The resulting commit is a descendant of the new base carrying an explicit deletion, so GitHub merges the revert with no conflict and nothing objects. A reviewer caught it by luck; it cost two ship reviewer cycles and a rebuild in a fresh worktree.
**Ruling:** ship's explicit-paths staging patch is anchored at merge-base(BASE, HEAD) and applied with 'git apply --index --3way', not at the refreshed base tip. When the merge base IS the base -- the default arm, --from-branch, and every in-sync ship -- the old single BASE-anchored 'git apply --index' runs unchanged, so the mechanism is inert unless the base actually moved under the checkout. Binary, symlink and gitlink paths are carved out and keep BASE-anchored whole-file staging, classified from the UNION of both anchorings. Failure to merge aborts BEFORE the gate chain with two additive messages -- unmerged index entries name same-region conflicts, a recomputed D/T tree diff names base-side deletions -- and a post-staging empty-index check catches the patch that merges to a no-op.
**Consequences:**
- Positive: Work that landed on the base after a caller's worktree was cut is no longer silently reverted by a scoped ship. This is the failure mode with no detector anywhere in the chain: the gates judge the prepared commit, which is internally consistent, and GitHub merges it cleanly, so only a human reading the diff could catch it. It also restores the premise base-drift-surfaced-at-read-time relies on -- that record rejected a ship-time block because 'git merges these three-way, so a same-region overwrite already surfaces as a conflict at merge', which was untrue precisely because ship re-cuts caller content onto the refreshed base. Three-way at apply time makes it true, and the resulting abort is hunk-level, strictly narrower than the path-overlap block that record refused: a base edit at line 10 and a caller edit at line 1 of one file merge cleanly and never abort.
- Negative: Three costs are paid knowingly. (1) Binary, symlink and gitlink paths KEEP the old whole-file semantics and therefore keep the revert hazard, because --3way conflicts unconditionally on them and routing them through it would abort every legitimate concurrent edit of a shared asset -- the ignorable-signal failure base-drift-surfaced-at-read-time exists to prevent. An advisory names them instead of a block. (2) --resume now refuses whenever the base moved a briefed file, because the preserved commit holds a three-way merge while the caller's tree holds raw bytes and the recovery check compares them with 'git add -A'. The refusal is fail-closed and gains an explanatory hint rather than a re-derivation. (3) ship_size_preflight still previews against BASE while the commit carries the merged content, so it can under-count; it fails closed and stays advisory.
**Vision-fit:** n/a — internal devkit tooling (ship pipeline correctness), not a product surface. Stays inside devkit-gates-repo-not-harness: the subject is the consumer repository's own staged content, and no carve-out is consumed or widened.
**Researched:** Every claim verified against real git rather than reasoned about. 'git diff <newer-base> -- f.txt' from an older worktree emits a deletion of a line only the base added; the fork-point patch plus --3way preserves it. --3way conflicts unconditionally on binary AND symlink pairs (three unmerged stages, exit 1), which is what forces the carve-out. A path can be binary under one anchoring and text under the other in BOTH directions, which is why classification unions the two rather than trusting BASE. A base-DELETED briefed path does not conflict at all: git errors 'does not exist in index', falls back to direct application, fails the whole patch and leaves ls-files -u EMPTY -- so conflict reporting alone would name nothing. A caller edit identical to one already on the base yields a non-empty patch that applies cleanly and stages nothing. 'git apply' is atomic, so no failure stages anything partial. A feature-critique panel returned PROCEED_WITH_CHANGES and supplied the binary carve-out, the base-deleted shape and the empty-index check; a design pass then overturned the planned shallow-clone fallback.
**Rejected:** (a) Anchoring at BASE and merely WARNING on overlap — REJECTED: that is what base-drift-surfaced-at-read-time already ships, and the incident happened with that advisory available. The payload has to change, not the narration. (b) Routing binary/symlink/gitlink through --3way for uniformity — REJECTED: verified unconditional conflict, so it converts working ships into aborts and buys nothing, since whole-file replacement has no surviving base region to lose. (c) A pre-probe for shallow/partial clones that falls back to a BASE anchoring when fork-point blobs are missing — REJECTED on measurement: git already falls back to DIRECT application of the same fork-point patch, which stays correct because that patch carries no deletion hunk for base-only work; only merge tolerance is lost. Re-anchoring at BASE would instead re-introduce the silent revert on every ship in such a repo. Fail-open on a diagnostic is ship_size_preflight's rule; fail-open on the payload is the bug. One advisory line is printed instead. (d) Rebuilding the resume recovery tree through the same three-way staging so --resume keeps working — REJECTED for this change as disproportionate; it needs staging factored into a GIT_INDEX_FILE-targeted function. Recorded in Revisit-when. (e) Fixing reship.sh in the same change — REJECTED: see Consequences; scoped out deliberately, not overlooked.
**Revisit-when:** reship.sh's whole-file 'cp -Pp' over a freshly fetched base is reported to have reverted base work (it pins BASE the same way at reship.sh:353-359 and copies over it at :548-560, so it carries this hazard with a LARGER blast radius -- it discards 100% of base-side change to a briefed file, not only the overlapping hunks), OR --resume refusals on a moved base are measured as costing real retries, OR a consumer reports the binary/symlink carve-out silently discarding a base asset.
**Scope:** cli/lib/ship/patch-anchor.sh,cli/lib/ship/ship-branch.sh
**Category:** ship-pipeline
**Source:** shortcut · sc-2451

## Target · 2026-10-05 — a non-mergeable path changed on both sides refuses before the gates; the advisory is retired

**Context:** ship stages binary, symlink and gitlink paths whole-file because git apply --3way conflicts unconditionally on them. When BOTH the caller and origin/<base> changed such a path since the fork point, the caller's copy replaced the base's outright and the base's change was reverted with no detector in the chain: the gates judge an internally consistent commit and GitHub merges it cleanly. The 2026-09-01 Target printed an advisory for exactly that case, and in sc-3968 the advisory was printed, ignored, and the upstream fix to gate-engine/review/overrides.mts (then binary to git through literal NUL bytes) was reverted. Severity medium; blast radius any consumer with images, lockfiles or submodules touched by two lines of work.
**Ruling:** Unchanged from the 2026-09-01 Target: the explicit-paths patch is anchored at merge-base(BASE, HEAD) and applied with --3way, and binary, symlink and gitlink paths keep BASE-anchored whole-file staging, classified from the union of both anchorings. NEW: when the base moved, ship_refuse_whole_file_drift (patch-anchor.sh) refuses a whole-file path whose caller entry differs from the fork point AND from the base tip while the base tip also differs from the fork point. It runs before the text-arm trial, before any branch or worktree exists, names each path with up to three base commits, and remedies with 'rebase onto the base and redo the change on its copy'. It decides with staging's own entry readers (_ship_here_entry / _ship_tree_entry), so it refuses exactly what ship_stage_whole_file would replace. GUARD_SHIP_REPLACE_OK=1 is the one-run override and keeps the old warning. A preserved-commit retry (local branch exists) only warns, so the --resume recovery check stays authoritative.
**Consequences:**
- Positive: - Positive: The last silent-revert path in explicit-paths staging is closed. A both-sides binary, symlink or submodule change now stops the ship before any gate time is spent, the same way git merge, rebase and cherry-pick stop on a binary conflict, instead of relying on a reviewer to notice.
- Positive: The caller-equals-base case (both sides made the identical change) is skipped, which also removes a false advisory the old git-diff check printed for it.
- Negative: A legitimate deliberate replacement of a binary asset that the base also changed now needs GUARD_SHIP_REPLACE_OK=1 or a rebase, and a submodule bumped on both lines refuses too. Accepted because it is rare (both sides must change the same non-text path) and the alternative is a silent revert. Generated binaries such as lockfiles are refused rather than exempted. reship.sh's whole-file cp still carries the hazard.
**Vision-fit:** n/a — internal devkit tooling (ship pipeline correctness), not a product surface. Stays inside devkit-gates-repo-not-harness: the subject is the consumer repository's staged content.
**Researched:** git cherry-pick of a binary changed on both sides stops with 'warning: Cannot merge binary files' and a UU conflict (verified locally); git merge and rebase behave the same, and -X ours/theirs or merge=binary are explicit opt-ins. A prior-art pass found no stacked-PR tool documented as auto-taking a side (peer tools unconfirmed). A feature-critique pass supplied the caller-equals-base skip, the dedicated override, the staging-primitive reuse (git diff reads a dirty submodule as changed while staging compares only its HEAD) and the preserved-commit-retry guard.
**Rejected:** (a) Keep the advisory and make it louder — REJECTED: it already printed in the incident; the payload has to change, not the narration. (b) Reuse GUARD_SHIP_BASE_OK as the override — REJECTED: it answers a different question (base containment) and would become a broad bypass hiding what was overridden. (c) Exempt generated binaries such as lockfiles via the generated-paths registry — REJECTED: a whole-file lockfile replacement reverts the base's dependency changes while package.json merges three-way, shipping an inconsistent pair. (d) Decide with git diff --quiet as the advisory did — REJECTED: it disagrees with staging on dirty submodules and would false-block.
**Revisit-when:** Refusals are measured as firing on intended replacements often enough that GUARD_SHIP_REPLACE_OK becomes routine, OR reship.sh's whole-file cp is fixed and this check should move into a shared staging function.
**Scope:** cli/lib/ship/patch-anchor.sh,cli/lib/ship/ship-branch.sh
**Category:** ship-pipeline
**Source:** shortcut · sc-3968
**Evidence-change:** The both-sides advisory this Target booked as Negative (1) fired in a real ship and was ignored: an agent's stale copy of a file git classified as binary replaced origin/main's, reverting an upstream fix, and only an LLM reviewer caught it about 20 minutes later (sc-3968). The record's own Rejected (a) predicted this: a warning beside an unchanged payload does not prevent the revert.

## Target · 2026-10-05 — ship --pr merges what reached the PR branch instead of copying over it

**Context:** devkit ship --pr (reship.sh append mode) copied the caller's whole file over a worktree cut at the PR tip. Anything that changed the same file on the PR branch after the caller's copy was taken — a merge of the base via GitHub's Update branch, a reviewer's suggestion commit, another checkout's push — was reverted by the new commit with nothing naming it. A real run nearly reverted a just-merged feature this way (sc-4607); only an unrelated argument check in the pre-commit hook caught it. The 2026-08-30 Target on this axis scoped reship out deliberately and named this report as its Revisit-when.
**Ruling:** In append mode every briefed path is compared, before any copy, against an ANCHOR: the blob this checkout last shipped for that path on this branch, read from the reconcile manifest (an op:delete record anchors on absence). A path with no record anchors at merge-base(PR tip, caller HEAD); unrelated histories anchor on the tip itself, which is the old copy. Tip unmoved since the anchor, or tip already equal to the caller's copy: copy, byte-identical to before. Caller unchanged since the anchor: keep the tip. Both changed a regular file: git merge-file, staged when clean. A conflict, a binary, symlink or gitlink both changed, or a delete/modify pair refuses before gates, naming up to three commits on the tip since the anchor; GUARD_SHIP_REPLACE_OK=1 copies the caller's file instead, as for new ships. The manifest keeps recording the CALLER's blob for a merged path, never the merged one: recording the merge would make the next re-push see an unmoved tip and copy the still-stale file, the same revert one ship later. Rewrite mode (--pr --base) is unchanged.
**Consequences:**
- Positive: A follow-up push to an open PR can no longer silently undo what reached that PR branch meanwhile; the common iterate-and-reship loop on an unmoved tip stays byte-identical, and re-editing lines the caller already shipped never conflicts with the caller's own earlier commit.
- Negative: Three costs. (1) With no manifest record (another worktree shipped first, or the first manifest write failed) and a HEAD not on the PR branch, the fork-point fallback can refuse a re-edit of lines the caller shipped earlier; the refusal names the commits and the override. (2) A merged commit holds bytes the caller's checkout does not, until the caller pulls; one line says so. (3) Rewrite mode still copies whole files over the current PR base, the same revert class, and is left for a separate change.
**Vision-fit:** n/a — internal dev tooling (safe shared-checkout PR publication)
**Researched:** sc-4607 and its autonomous report; reship.sh header and copy loop; reconcile-manifest-write.mts classify (records hash-object of the committed worktree file); patch-anchor.sh refusal shape (#804); git merge-file; prior-art pass (no peer tool covers a checkout whose HEAD is off the PR branch; git push --force-with-lease is branch-level, not per-file)
**Rejected:** (a) Anchoring at merge-base(PR tip, caller HEAD) for every path, as the report proposed — REJECTED: in a shared checkout HEAD is not on the PR branch, so a shipped path's anchor predates the caller's own first ship and re-editing the same lines would conflict on every iteration. (b) Refusing whenever the PR tip carries commits devkit did not create — REJECTED: Update-branch merges are routine and usually touch other files, so it false-blocks. (c) Recording a per-branch last-shipped commit in the manifest to name foreign commits — NOT TAKEN: the commit is recovered by walking the path's log to the anchor blob, with no schema change. (d) Fixing rewrite mode in the same change — REJECTED as scope.
**Anchored-bet:** [BET]
**Revisit-when:** The fork-point fallback's refusal (no manifest record) is reported firing on a caller's own re-edit often enough that GUARD_SHIP_REPLACE_OK becomes routine, OR rewrite mode's whole-file copy is reported reverting base work.
**Scope:** cli/lib/ship/reship.sh,cli/lib/ship/reship/**,cli/lib/ship/reconcile-manifest-write.mts
**Source:** shortcut · sc-4607
**Evidence-change:** The Revisit-when trigger fired: reship.sh's whole-file copy was reported reverting work that reached a PR branch after the caller's copy was taken (sc-4607), so reship now needs its own anchor rather than the scope-out recorded in Rejected (e).
- 2026-10-06 — Manifest writes from reship are a per-path compare-and-swap: ship/reship/anchor.mts passes, through --anchors, the record each path was anchored on (op:blob, or - for none), and reconcile-manifest-write updates a path only while that record is unchanged, so a concurrent ship's newer anchor is never regressed. A no-delta append refreshes the record, and a path absent on both the tip and the caller is recorded as op:delete, so a stale anchor cannot cause a false refusal on the next re-push.
- 2026-10-06 — A manifest record whose blob is no longer in the object store anchors like no record (merge-base fallback): a merged path records the caller's blob, which no commit holds, so git gc can prune it while the PR is still open. Index writes normalise the briefed path, so a ./-spelled path stages as it did under git add.
