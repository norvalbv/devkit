# gate-verdict-attribution

## Target · 2026-07-27 — A gate verdict is only evidence if it names its inputs and its prompt version

**Context:** Reviewer telemetry recorded verdicts but never what produced them, so 1,324 ships of gate output could not answer the two questions needed to improve the agents. Measured on the live sink: a cached PASS emits cache_hit and NO review_result, so 249 of ~1,811 reviewer outcomes (~13%) leave no verdict row at all and read downstream as 'that reviewer was never selected' — indistinguishable from a reviewer that genuinely never ran, which mislabels an external finding as that reviewer's MISS. Separately, four of seven reviewers produced ZERO real findings across ~1,363 verdicts (backend-performance 0/567, frontend-performance 0/139; api-security's and frontend-security's lone 'fails' were foreign-worktree index artifacts) while the reviewer-fleet bench publishes strong block recall for the same reviewers — and nothing stored could distinguish correct calibration from blindness, because only the free-prose reason of a FAIL survived and only 1-4% of PASS transcripts happen to mention a considered-then-discarded finding. Cost: ~40 judge-hours of gate spend per 1,324 ships that cannot be evaluated, and a benchmark that cannot be checked against production.
**Ruling:** A verdict-producing gate emits its INPUTS and its non-runs, not only its outcomes. (1) Every SELECTED reviewer emits review_scope BEFORE the judge runs — files, diff_sha256, file count and hash, and cached — so a cache hit is attributable on the same footing as a live run. (2) Every reviewer that did NOT run emits review_skipped with the reason (gate_disabled, no_llm, GUARD_REVIEW_SKIP, not_selected), so non-selection is a row and never an absence. (3) Every verdict carries prompt_identity: the same hash formula as the review-mode packaged preflight, computed over the SYNCED consumer assets on the commit/ship path, so a production rate and a bench baseline are comparable when the bytes match. (4) The per-lens checklist vector rides on review_result INCLUDING the passes, with each failing lens attributed to what the gate did with it (blocking, waived, dropped_out_of_charter). Absent items means no artifact — a different fact from an artifact with zero failures.
**Consequences:**
- Positive: Per-lens fired-versus-clean rates become a GROUP BY over every run instead of a regex over prose that catches 2%, so the zero-yield reviewers can be diagnosed and their ~40 judge-hours per 1,324 ships either justified or reclaimed. A brief edit becomes measurable against production rather than only against the bench, because every verdict names the prompt version that produced it.
- Negative: Three more event types and a per-lens array on the hottest gate path. The item vector is capped at 40 entries with issue text truncated to 200 chars and non-passing items sorted first, and a wide scope spills its path list to a sidecar ref — both because gate-events.mts relies on sub-4KB single-append writes staying atomic under concurrent judges, so an uncapped payload would be a data-CORRUPTION bug rather than a large row. prompt_identity is null whenever any synced asset is unreadable, and permanently null for every ship predating this ruling, so early per-version rates are sparse and must not be read as regressions.
**Vision-fit:** n/a — internal tooling
**Researched:** Measured directly against the live sink and warehouse for 2026-07-10..27: 249 cache_hit vs 1,562 review_result; a sampled cache-hit ship confirmed zero commit_reviews rows for that reviewer; 193 correctness fails vs 0 for backend-performance across 567 verdicts; 230 distinct blocked fingerprints collapsing to 141 (branch, reviewer, lens) groups; 38 of 80 inconclusive rows are 'checklist artifact missing', concentrated in the same zero-yield reviewers. One backend-performance transcript showed the judge generating two findings and correctly overturning both as pre-existing, and a regex over ~2,700 PASS transcripts found that language in only 7-22 per reviewer, establishing prose as an unusable proxy.
**Rejected:** (a) Add the columns to the existing verdict row — REJECTED: the warehouse writes commit_reviews with INSERT OR IGNORE on UNIQUE(ship_id, reviewer), so a new column is never filled on re-ingest and can never be backfilled from replayed events. (b) Reuse preflightReviewAssets directly for prompt_identity — REJECTED: it is called only under reviewMode, hashes the PACKAGED asset root rather than the consumer's synced copies, and throws when the asset root is absent, so it would both mis-attribute and fail a gate over telemetry. (c) Emit one event per checklist item — REJECTED: it multiplies the hottest gate path by the item count and, with commit-guard keying on per-FILE items, breaks the sub-4KB atomic-append invariant a concurrent-judge sink depends on. (d) Carry a static per-reviewer lens vocabulary on the scope event — REJECTED: the per-run vector already distinguishes 'this lens never fired' from 'this reviewer has no such lens', so a duplicated ALL_ITEMS copy would only add a second source of truth the gate cannot import and would have to sync-test.
