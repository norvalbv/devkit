# ship-ci-wait-is-observation-not-intent

## Target · 2026-09-03 — A post-PR check wait is an OBSERVATION of the published PR, never a property of the shipped invocation

**Context:** sc-2394: devkit ship returns the instant gh pr create succeeds, while the gate check is still pending. An agent needing an end-to-end status had to discover the workflow run id separately and run gh run watch --exit-status, which redraws the entire job every 3 seconds; it burned many bounded polls and was finally Ctrl-C'd after ten minutes with the test step still running and the status ambiguous. No layer above devkit closes this: a sweep of frink, devkit's primary consumer, finds no gh pr checks, no gh run watch and no check-runs read anywhere in its source, so the harness does not already poll. Neither does gh: cli/cli trunk registers exactly five flags on pr checks (web, watch, fail-fast, interval, required) and none is a deadline, while neither timeout nor gtimeout exists on macOS 26.5.1, so timeout 900 gh pr checks --watch is not portable. The cost is one wrong-command episode per agent that needs a CI verdict, plus an ambiguous handoff at the end of it.
**Ruling:** devkit ship gains an opt-in --wait-ci (with --wait-ci-timeout, default 900s) that polls the PR's checks after every artifact is durable. Its governing property is that the wait OBSERVES a PR that already exists rather than describing what shipped, and five behaviours follow from that. (1) It is not recorded in the ship-intent record and is not replayed by --resume, exactly as --ready is not; it is accepted under --resume so a retry can re-request it. (2) devkit ship exits 0 whenever the PR opened; the verdict rides one machine-readable stderr line plus a ship_ci telemetry row, never the exit code, because ship's exit status already means 'did the PR open' and an agent reading non-zero would retry --resume against a record the push already deleted. (3) ALL checks are polled; --required is never the default. (4) A terminal tally must hold for a wall-clock settle grace, not merely for N polls. (5) gh's non-zero exits are DATA: exit 8 is pending and still carries the rows on stdout, exit 1 with 'no checks reported' is an empty set.
**Consequences:**
- Positive: An agent that ships can obtain a bounded, unambiguous CI verdict from the command it already ran, instead of discovering a run id and inventing its own polling bound. The wait cannot cost a ship: it runs after the push, the PR, the reconcile manifest, the intent release and the worktree cleanup are all durable, so a killed, timed-out or red wait leaves a fully published PR behind. Because the verdict never reaches the exit code, no caller can mistake a red PR for a failed ship.
- Negative: devkit takes on a poll loop with four independent failure modes (transient gh trouble, an empty check set that may be a race or a fact, a terminal set that may be incomplete, and a deadline) inside ship, its most safety-critical path. The settle grace adds ~30s to every green wait, deliberately, to buy the guarantee. Two gaps are accepted and not closed here: gh pr checks --json exposes no commit field, so a stale rollup from a previous head can only be outwaited rather than identified; and because ship unsets DEVKIT_MANAGED_SIGNAL_ROOT, a signal during the wait exits 130 on a PR that did open — documented in the Exits paragraph rather than fought. devkit also cannot dogfood the passing path: its own gate workflow concluded failure on 12 of the last 12 main commits (sc-1896), so the all-green outcome is covered only by a stubbed poller.
**Vision-fit:** n/a — internal tooling (devkit is dev infrastructure).
**Researched:** Read cli/cli trunk pkg/cmd/pr/checks/checks.go for the flag registration and grepped it for a timeout (zero hits); read release notes v2.97.0-v2.100.0, which add nothing to pr checks. cli/cli#7401, the post-create no-checks race, is CLOSED NOT_PLANNED with a maintainer citing API limitations, so the empty-set grace must be owned here. Measured on this repo that gh pr checks --required exits 1 with empty stdout while the unfiltered call reports gate at bucket:fail. Measured that neither timeout nor gtimeout is on PATH on macOS 26.5.1. Swept frink's source for post-ship check polling and found none.
**Rejected:** (a) Shelling gh pr checks --watch instead of polling — REJECTED: it has no deadline (the one thing genuinely absent upstream), no settle confirmation, and renders a redrawing TTY table that is unreadable under an agent pipe, which is the exact complaint sc-2394 reports. (b) Recording the flag in the ship-intent record so --resume replays it — REJECTED: emitFields writes a positional NUL stream whose nlinks index is hard-coded in two bash readers with no test asserting writer and readers agree, so a missed edit silently ships the wrong path set; the flag's silent loss on a resume is loud and losslessly re-requested, which is not worth that risk. (c) A non-zero exit for a red CI result — REJECTED as the default: exits 3 and 4 already mean an AI-judge outage and a usage error in this pipeline, and ship's exit 1 is documented as 'the PR did not open'. (d) --required as the default — REJECTED: measured to render a red PR green on any repo without branch protection, including devkit's own. (e) Adopting one of the three gh extensions (gh-pr-await, gh-watch, gh-observer) — REJECTED: 3-10 stars each, and a toolkit installing into repositories it does not own cannot require a third-party gh extension.
**Anchored-bet:** [BET]
**Revisit-when:** gh ships a deadline or exit-condition flag on pr checks (cli/cli#11921 is open), OR gh pr checks --json gains a commit/head field, which would let a stale rollup be identified rather than outwaited, OR a --wait-ci run is observed reporting a terminal verdict that a later check contradicts.
**Scope:** cli/lib/ship/wait-ci.mts

- 2026-10-12 — sc-4708 — a failed verdict now carries attribution: the PR run's per-file test summary is compared with the run on the first parent of the PR's merge commit (the base CI actually tested, never main's newest run), plus failed job › step sets. inherited-only is claimed only when no file is new or unsure, no step is new and no failing check is outside the workflow; a both-failed file whose name lists are missing, truncated or empty is unsure. - 2026-10-14 — sc-5537 — gh trouble during --wait-ci is now split by whether waiting can fix it. A network or GitHub-side fault (killed per-poll exec, dial tcp / i/o timeout, connection reset, HTTP 5xx, rate limit, GraphQL 'something went wrong') is the caller-only reason gh-unreachable and is bounded only by the absolute deadline, with the interval doubling to a 6x cap and never sleeping more than one interval past the deadline; a 3-strike counter had ended a 3600s wait 22 minutes in on a two-minute outage. gh-failed stays the catch-all for unknown flags, unknown JSON fields, bad repos and auth text, and keeps the 3-strike cap, so a misclassification costs the old behaviour rather than a two-hour spin. At the deadline the wait ends unavailable only if no poll ever succeeded or the failure streak reached the budget; one blip on the last poll keeps the pending snapshot as timed-out. The classifier moved to wait-ci/classify.mts for the 500-line cap. Re-entering a wait for an already-open PR stays with sc-5520.

## Target · 2026-10-19 — A post-PR check wait observes the published PR; its verdict reaches ship's exit code only through the --wait-ci-strict opt-in

**Context:** A caller that wants 'ship, then merge only on green CI' has to parse the ship: ci-outcome= stderr line, because ruling (2) of the first Target kept the verdict out of the exit code. A grep is easy to get subtly wrong: matching only failed misses timed-out, and timed-out is 20% of observed waits (37 of 186), so a hand-rolled check merges while CI is still running. Overloading exit 1 would have been worse: 1 means the PR did not open, and an agent reading it retries --resume against an intent record the push already deleted.
**Ruling:** devkit ship gains an opt-in --wait-ci (with --wait-ci-timeout, default 900s) that polls the PR's checks after every artifact is durable, and the wait OBSERVES a PR that already exists rather than describing what shipped. (1) It is not recorded in the ship-intent record and is not replayed by --resume, exactly as --ready is not; it is accepted under --resume so a retry can re-request it. (2) By default devkit ship exits 0 whenever the PR opened and the verdict rides one stderr line plus a ship_ci telemetry row. The opt-in --wait-ci-strict (requires --wait-ci) is the ONLY way the verdict reaches the exit code: ship exits 5 unless the outcome is passed, failing closed for failed, cancelled, no-checks, timed-out, unavailable, every not-run and a wait that crashed or was killed, because 1 must keep meaning the PR did not open. An existing exit 1 still wins over 5, then a 130/143 signal; the wait records its status and the scripts exit with it only at their success exits, so no post-wait step is skipped. 5 is never a cue to --resume. (3) ALL checks are polled; --required is never the default. (4) A terminal tally must hold for a wall-clock settle grace, not merely for N polls. (5) gh's non-zero exits are DATA: exit 8 is pending and still carries the rows on stdout, exit 1 with 'no checks reported' is an empty set.
**Consequences:**
- Positive: Positive: a script can write devkit ship ... --wait-ci --wait-ci-strict && <merge> and get merge-only-on-green with no text parsing, and an unknown verdict can never pass as green. Without the flag nothing changes: a red PR is still not a failed ship for any caller that did not ask.
- Negative: Negative: ship's exit contract grows a fourth meaning (0 PR open, 1 PR not open, 5 PR open but CI not known green, 130/143 signal) that every caller and doc must keep straight. Fail-closed means a CI-less repo, an outage of gh, or a 900s budget shorter than the CI run all exit 5 under strict, so a strict caller must size --wait-ci-timeout to its CI. A status of 5 hides which non-green outcome occurred; the stderr line remains the only place that says which.
**Vision-fit:** n/a — internal tooling (devkit is dev infrastructure).
**Researched:** Read the first Target's Rejected (c) (default only) and the sc-2675 --wait-ci-required opt-in precedent; local ship_ci telemetry rows for the outcome mix; PR #1051 (devkit ci-verdict) exit contract, which returns 0 for every verdict and 2 for no verdict; cli/cli trunk pkg/cmd/pr/checks/checks.go, whose exit 1 conflates a failed check with any runtime error and whose cancelled checks exit 0; run-packaged-script.mts and queueThenRun, which pass the bash status through verbatim, and the codebase, where no gate or ship path exits 5.
**Rejected:** (a) Exit-coding the standalone devkit ci-verdict instead of ship — REJECTED here: #1051 deliberately exits 0 for any verdict, it is not merged, and a caller who ships and waits in one command would still need a second command and a second wait. (b) Exit 5 only for failed and cancelled, as first proposed — REJECTED: timed-out, no-checks and unavailable are not green, and timed-out alone is 20% of real waits. (c) Reusing exit 1 for a red verdict — REJECTED: 1 means the PR did not open and invites a --resume against a deleted record. (d) Making the non-zero exit the default — REJECTED, as in the first Target: a red PR is not a failed ship for callers that never asked.
**Anchored-bet:** [BET]
**Revisit-when:** gh ships a deadline or exit-condition flag on pr checks (cli/cli#11921), OR gh pr checks --json gains a commit/head field, OR a --wait-ci run reports a terminal verdict that a later check contradicts, OR strict callers report needing to tell timed-out from failed by exit code alone.
**Scope:** cli/lib/ship/wait-ci/**
**Source:** shortcut · sc-2674
**Evidence-change:** sc-2674: the first Target rejected a non-zero red exit only as the DEFAULT (Rejected c) and left the opt-in open. Since then 186 local --wait-ci runs (139 passed, 37 timed-out, 7 failed, 3 unavailable) show the line is consumed, every script that branches on it has to grep stderr, and the standalone devkit ci-verdict (sc-5520, PR #1051) also exits 0 for any verdict, so no devkit command exposes the verdict as a status.
- 2026-10-24 — sc-4330 — the narrowed wait no longer ends in no-checks or passes on a partially reported set, retiring that clause of the 2026-10-02 note (the 2026-09-03 Revisit-when, a terminal verdict a later check contradicts, is that partial-set pass). Under --wait-ci-required the wait reads the base's required contexts once per wait, the union of gh api --paginate rules/branches/{base} (active rulesets only) and branches/{base} .protection.required_status_checks.contexts, both readable without admin, and appends a pending EXPECTED row for each context gh --required has not listed. --required stays on the checks call so GitHub's per-app isRequired stays authoritative: a same-named check from another app stays pending rather than reading green. The set is cached only after a successful read, and a failed read is classified like any gh failure (5xx waits out the deadline, 403/404 ends unavailable, except the 403 GitHub returns for rulesets on a private free-plan repo, which is read as no ruleset contexts since none can apply), never taken as nothing-required; ruling (5) of the first Target, where gh pr checks exit 1 with no checks reported is an empty set, applies to that checks call only, and the same text from the set read is no answer. The verdict line and ship_ci row carry required-contexts / required_contexts, 0 meaning the base requires nothing. A set holding any failed check is now terminal even while other checks, synthetic EXPECTED rows included, are pending, since a red check cannot turn green within the attempt; such a red reports attribution=unknown reason=run-in-progress rather than comparing an unfinished run. Without that, the EXPECTED rows would turn a known red into timed-out. The rule also applies to the all-checks wait, where the cost is that a red with another check still running now ends early with attribution unknown instead of waiting for the full run's attribution; a red check decides the verdict either way. Known gaps: workflows and code_scanning rule types stay invisible before they report (sc-7034), and a mid-wait base retarget is not seen.
