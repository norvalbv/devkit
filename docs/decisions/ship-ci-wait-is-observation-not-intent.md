# ship-ci-wait-is-observation-not-intent

## Target · 2026-09-03 — A post-PR check wait is an OBSERVATION of the published PR, never a property of the shipped invocation

**Context:** sc-2394: devkit ship returns the instant gh pr create succeeds, while the gate check is still pending. An agent needing an end-to-end status had to discover the workflow run id separately and run gh run watch --exit-status, which redraws the entire job every 3 seconds; it burned many bounded polls and was finally Ctrl-C'd after ten minutes with the test step still running and the status ambiguous. No layer above devkit closes this: a sweep of frink, devkit's primary consumer, finds no gh pr checks, no gh run watch and no check-runs read anywhere in its source, so the harness does not already poll. Neither does gh: cli/cli trunk registers exactly five flags on pr checks (web, watch, fail-fast, interval, required) and none is a deadline, while neither timeout nor gtimeout exists on macOS 26.5.1, so timeout 900 gh pr checks --watch is not portable. The cost is one wrong-command episode per agent that needs a CI verdict, plus an ambiguous handoff at the end of it.
**Ruling:** devkit ship gains an opt-in --wait-ci (with --wait-ci-timeout, default 900s) that polls the PR's checks after every artifact is durable. Its governing property is that the wait OBSERVES a PR that already exists rather than describing what shipped, and five behaviours follow from that. (1) It is not recorded in the ship-intent record and is not replayed by --resume, exactly as --ready is not; it is accepted under --resume so a retry can re-request it. (2) devkit ship exits 0 whenever the PR opened; the verdict rides one machine-readable stderr line plus a ship_ci telemetry row, never the exit code, because ship's exit status already means 'did the PR open' and an agent reading non-zero would retry --resume against a record the push already deleted. (3) ALL checks are polled; --required is never the default. (4) A terminal tally must hold for a wall-clock settle grace, not merely for N polls. (5) gh's non-zero exits are DATA: exit 8 is pending and still carries the rows on stdout, exit 1 with 'no checks reported' is an empty set.
**Consequences:**
- Positive: An agent that ships can obtain a bounded, unambiguous CI verdict from the command it already ran, instead of discovering a run id and inventing its own polling bound. The wait cannot cost a ship: it runs after the push, the PR, the reconcile manifest, the intent release and the worktree cleanup are all durable, so a killed, timed-out or red wait leaves a fully published PR behind. Because the verdict never reaches the exit code, no caller can mistake a red PR for a failed ship.
- Negative: devkit takes on a poll loop with four independent failure modes (transient gh trouble, an empty check set that may be a race or a fact, a terminal set that may be incomplete, and a deadline) inside ship, its most safety-critical path. The settle grace adds ~30s to every green wait, deliberately, to buy the guarantee. Two gaps are accepted and not closed here: gh pr checks --json exposes no commit field, so a stale rollup from a previous head can only be outwaited rather than identified; and because ship unsets DEVKIT_MANAGED_SIGNAL_ROOT, a signal during the wait exits 130 on a PR that did open — documented in the Exits paragraph rather than fought. devkit also cannot dogfood the passing path: its own gate workflow concluded failure on 12 of the last 12 main commits (sc-1896), so the all-green outcome is covered only by a stubbed poller.
**Vision-fit:** n/a — internal tooling (devkit is dev infrastructure).
**Researched:** Read cli/cli trunk pkg/cmd/pr/checks/checks.go for the flag registration and grepped it for a timeout (zero hits); read release notes v2.97.0-v2.100.0, which add nothing to pr checks. cli/cli#7401, the post-create no-checks race, is CLOSED NOT_PLANNED with a maintainer citing API limitations, so the empty-set grace must be owned here. Measured on this repo that gh pr checks --required exits 1 with empty stdout while the unfiltered call reports gate at bucket:fail. Measured that neither timeout nor gtimeout is on PATH on macOS 26.5.1. Swept frink's source for post-ship check polling and found none.
**Rejected:** (a) Shelling gh pr checks --watch instead of polling — REJECTED: it has no deadline (the one thing genuinely absent upstream), no settle confirmation, and renders a redrawing TTY table that is unreadable under an agent pipe, which is the exact complaint sc-2394 reports. (b) Recording the flag in the ship-intent record so --resume replays it — REJECTED: emitFields writes a positional NUL stream whose nlinks index is hard-coded in two bash readers with no test asserting writer and readers agree, so a missed edit silently ships the wrong path set; the flag's silent loss on a resume is loud and losslessly re-requested, which is not worth that risk. (c) A non-zero exit for a red CI result — REJECTED as the default: exits 3 and 4 already mean an AI-judge outage and a usage error in this pipeline, and ship's exit 1 is documented as 'the PR did not open'. (d) --required as the default — REJECTED: measured to render a red PR green on any repo without branch protection, including devkit's own. (e) Adopting one of the three gh extensions (gh-pr-await, gh-watch, gh-observer) — REJECTED: 3-10 stars each, and a toolkit installing into repositories it does not own cannot require a third-party gh extension.
**Anchored-bet:** [BET]
**Revisit-when:** gh ships a deadline or exit-condition flag on pr checks (cli/cli#11921 is open), OR gh pr checks --json gains a commit/head field, which would let a stale rollup be identified rather than outwaited, OR a --wait-ci run is observed reporting a terminal verdict that a later check contradicts.
