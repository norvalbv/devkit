# devkit-gates-repo-not-harness

## Target · 2026-08-04 — devkit gates the consumer repository, not the agent use of harness tooling

**Context:** An autonomous report (ce50bb00 -> sc-1368, severity blocking) asked devkit to fix "the orchestration script that generates subagent dispatch prompts" after every dispatched agent was told to cd "undefined". No such script exists in devkit: the prompts came from ad-hoc Claude Code Workflow scripts a session authored inline. Root cause was args passed to the Workflow tool as a JSON-encoded string, so args.wt read a property off a primitive and yielded undefined. Measured at the caller across all sessions on this machine: 13 of 13 Workflow launches that passed args passed it in string form, and zero object-form calls have ever been made. Because object-form failure is SILENT (an array would throw on .map), the damage compounded unseen: 37 of 43 subagent dispatches in one bench session carried the literal text undefined, four of five runs still reported status completed, and two writes escaped the assigned worktree into the shared main checkout at gate-engine/review/overrides.mts. The forcing question was whether devkit should grow a gate that prevents this class.
**Ruling:** devkit gates govern the CONSUMER REPOSITORY - its diffs, structure, staged set, decision records, commits. They do not police how an agent drives its own harness tooling. A PreToolUse hook on the Claude Code Workflow tool validating the shape of its args argument is rejected, notwithstanding that devkit has every mechanism to ship one (agents-hooks auto-discovery, the hook-registration ledger, and OPTIONAL_COMPONENTS to keep it opt-in). Defects in how an agent authors a throwaway script are corrected in the authoring layer - session memory plus a normalise-then-assert script preamble - never by shipping enforcement into repositories devkit does not own.
**Consequences:**
- Positive: A repository that installs devkit gets gates that judge only that repository. devkit never blocks a consumer tool call on a third-party contract it cannot version, so an upstream schema change can never turn devkit into a false blocker inside someone else node_modules. A future autonomous report of this class resolves against this record in one query instead of re-running a multi-agent investigation.
- Negative: The footgun stays live and uncontrolled by any mechanism devkit owns. It has a 13-of-13 historical rate, no feedback signal, and its only controls are advisory (a session memory and an authoring idiom). A recurrence costs roughly 37 wasted dispatches and risks another worktree-isolation escape into a shared checkout - the exact pathology that already burned this repo. We accept that recurring cost rather than take a fail-closed dependency on a foreign argument schema.
**Vision-fit:** Serves the same promise as zero-consumer-tool-deps: installing devkit adds gates over YOUR repository and zero obligations to anything else. A guard on a harness tool argument shape would be the first devkit gate whose subject is not the consumer repository at all.
**Researched:** Read the raw session transcripts rather than the derived run records (which resume silently overwrites): 92 Workflow tool_use calls across all projects, 43 dispatch transcripts in session 0b4e61fa, and the persisted workflow scripts. Confirmed the Workflow args parameter carries no type constraint and its description explicitly requires actual JSON values rather than a JSON-encoded string, so the string form was non-conformant with a documented contract. A feature-critique panel argued the opposing case at full strength and overturned three of the four reasons originally given for declining.
**Rejected:** (a) A PreToolUse workflow-args-guard hook in agents-hooks - REJECTED: it would make a package running inside other people node_modules fail CLOSED against the argument schema of a tool devkit neither owns nor versions; one upstream schema change turns it into a false block in every consumer repo. (b) The advisory variant (additionalContext, no permissionDecision) following the decision-scope-brief precedent - REJECTED: it could not have prevented any of the 13 calls, because the warning it would emit already exists verbatim in the Workflow tool description and has never once produced a correct call. (c) A repo-local CLAUDE.md or AGENTS.md line as the primary control - REJECTED: it reaches only agents working inside devkit, while 8 of the 13 malformed calls were made in frink.
**Anchored-bet:** [BET]
**Revisit-when:** A second independent harness-misuse incident that is NOT self-recovering (the run fails or corrupts state rather than agents improvising back to the correct path), OR one originating from a checked-in devkit script rather than an ad-hoc session script.
