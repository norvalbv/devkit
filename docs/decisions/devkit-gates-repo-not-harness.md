# devkit-gates-repo-not-harness

## Target · 2026-08-04 — devkit gates the consumer repository, not the agent use of harness tooling

**Context:** An autonomous report (ce50bb00 -> sc-1368, severity blocking) asked devkit to fix "the orchestration script that generates subagent dispatch prompts" after every dispatched agent was told to cd "undefined". No such script exists in devkit: the prompts came from ad-hoc Claude Code Workflow scripts a session authored inline. Root cause was args passed to the Workflow tool as a JSON-encoded string, so args.wt read a property off a primitive and yielded undefined. Measured at the caller across all sessions on this machine: 13 of 13 Workflow launches that passed args passed it in string form, and zero object-form calls have ever been made. Because object-form failure is SILENT (an array would throw on .map), the damage compounded unseen: 37 of 43 subagent dispatches in one bench session carried the literal text undefined, four of five runs still reported status completed, and two writes escaped the assigned worktree into the shared main checkout at gate-engine/review/overrides.mts. The forcing question was whether devkit should grow a gate that prevents this class.
**Ruling:** devkit gates govern the CONSUMER REPOSITORY - its diffs, structure, staged set, decision records, commits. They do not police how an agent drives its own harness tooling. A PreToolUse hook on the Claude Code Workflow tool validating the shape of its args argument is rejected, notwithstanding that devkit has every mechanism to ship one (agents-hooks auto-discovery, the hook-registration ledger, and OPTIONAL_COMPONENTS to keep it opt-in). Defects in how an agent authors a throwaway script are corrected in the authoring layer - session memory plus a normalise-then-assert script preamble - never by shipping enforcement into repositories devkit does not own.
**Consequences:**
- Positive: A repository that installs devkit gets gates that judge only that repository. devkit never blocks a consumer tool call on a third-party contract it cannot version, so an upstream schema change can never turn devkit into a false blocker inside someone else node_modules. A future autonomous report of this class resolves against this record in one query instead of re-running a multi-agent investigation.
- Negative: The footgun stays live and uncontrolled by any mechanism devkit owns. It has a 13-of-13 historical rate, no feedback signal, and its only controls are advisory (a session memory and an authoring idiom). A recurrence costs roughly 37 wasted dispatches and risks another worktree-isolation escape into a shared checkout - the exact pathology that already burned this repo. We accept that recurring cost rather than take a fail-closed dependency on a foreign argument schema.
**Vision-fit:** Serves the same promise as zero-consumer-tool-deps: installing devkit adds gates over YOUR repository and zero obligations to anything else. A guard on a harness tool argument shape would be the first devkit gate whose subject is not the consumer repository at all.
**Researched:** Read the raw session transcripts rather than the derived run records (which resume silently overwrites): 92 Workflow tool_use calls across all projects, 43 dispatch transcripts in session 0b4e61fa, and the persisted workflow scripts. Confirmed the Workflow args parameter carries no type constraint and its description explicitly requires actual JSON values rather than a JSON-encoded string, so the string form was non-conformant with a documented contract. A feature-critique panel argued the opposing case at full strength and overturned three of the four reasons originally given for declining.
**Rejected:** (a) A PreToolUse workflow-args-guard hook in agents-hooks - REJECTED: it would make a package running inside other people node_modules fail CLOSED against the argument schema of a tool devkit neither owns nor versions; one upstream schema change turns it into a false block in every consumer repo. (b) The advisory variant (additionalContext, no permissionDecision) following the decision-scope-brief precedent - REJECTED: it could not have prevented any of the 13 calls, because the warning it would emit already exists verbatim in the Workflow tool description and has never once produced a correct call. (c) A repo-local CLAUDE.md or AGENTS.md line as the primary control - REJECTED: it reaches only agents working inside devkit, while 8 of the 13 malformed calls were made in frink.
**Anchored-bet:** [BET]
**Revisit-when:** A second independent harness-misuse incident that is NOT self-recovering (the run fails or corrupts state rather than agents improvising back to the correct path), OR one originating from a checked-in devkit script rather than an ad-hoc session script.
**Scope:** agents-hooks/**,cli/lib/install/hook-registration-ledger/**
**Source:** shortcut · sc-1368

## Target · 2026-08-09 — Narrow carve-out: hooks may order devkit's own shipped workflow stages

**Context:** prior-art ordering ships as prose in the brainstorming skill; sessions in this repo and consumer repos exit plans and invoke feature-critique without ever dispatching prior-art unless the user intervenes each time. The owner asked for a mechanical guarantee. The prior ruling rejected PreToolUse hooks on harness tools because devkit cannot version a third-party argument schema and must not fail closed against it.
**Ruling:** PreToolUse hooks validating third-party argument SHAPES remain rejected. A narrow carve-out is granted for ordering devkit's OWN shipped workflow stages: a hook may deny a harness tool call when the denial enforces sequencing that devkit's own skills mandate (prior-art before feature-critique/ExitPlanMode), provided it reads only tool_name and tool_input.subagent_type, denies at most once per session (snooze marker), fails open on every error, and ships as an opt-in component.
**Consequences:**
- Positive: Positive: the step-0 ordering devkit ships finally has one mechanical enforcement point; a schema drift upstream degrades to the gate never firing (fail-open), never a false block. Negative: this is the first devkit hook whose subject is a harness tool call rather than the consumer repository; the boundary now requires the reads-only-tool-identity + deny-once + fail-open + opt-in fence to stay principled.
- Negative: Accepted one bounded exception to the gates-repo-not-harness line in exchange for closing a recurring, non-self-recovering workflow failure; rejected staying prose-only (measurably unfollowed) and rejected hard fail-closed denial (would block legitimate skips and inherit the foreign-schema fragility the original ruling feared).
**Vision-fit:** Still serves the promise that installing devkit adds obligations only devkit owns: the gate enforces devkit's own published workflow, reads no foreign schema beyond tool identity, and is opt-in — a consumer that never selects priorArtGate is untouched.
**Revisit-when:** The deny-once gate produces a false block in practice (a denial where neither running prior-art nor stating a skip was appropriate), or upstream renames Task/subagent_type so the gate silently never fires for a full release.
**Scope:** agents-hooks/**,cli/lib/install/hook-registration-ledger/**
**Source:** brainstorm
**Evidence-change:** The revisit trigger fired: a second harness-misuse class that is not self-recovering — agents repeatedly skip the step-0 prior-art stage that devkit's own checked-in brainstorming skill mandates, and no agent improvises back to the correct path without the user manually prompting. Unlike the Workflow-args case, the failing contract is devkit-owned prose (skills/brainstorming/SKILL.md), not a foreign argument schema.

## Target · 2026-08-10 — The carve-out widens one precise notch: the priorArtGate hook may additionally substring-match devki

**Context:** The priorArtGate carve-out (this axis, previous Target) let a devkit hook order devkit own workflow stages reading ONLY tool identity + tool_input.subagent_type. In practice that shape cannot tell a session that consciously skipped step-0 per the brainstorming skill predicate (and wrote the mandated one-line skip note) from a session that forgot entirely — both eat the one deny, so the gate taxes exactly the behavior it exists to produce.
**Ruling:** The carve-out widens one precise notch: the priorArtGate hook may additionally substring-match devkit OWN prescribed acknowledgment token (a `Prior-art:` line) in the gated call text — ExitPlanMode tool_input.plan and the feature-critique Task tool_input.prompt. A gated call carrying the token passes silently and marks the session acknowledged; one without it is denied once as before. This is recognition of a devkit workflow token, not validation of a foreign tool argument shape: no schema checks, no length or content heuristics, no judgment of foreign args. Everything outside that token match stays rejected exactly as this axis has always ruled.
**Consequences:**
- Positive: Compliant sessions (ran step-0, or wrote the skip note) never see a deny. Forgetful sessions still get the one teaching deny. The hook now depends on two upstream field names (plan, prompt) instead of zero; both degrade fail-open to the previous deny-once behavior if renamed. Gaming (pasting the token thoughtlessly) is possible and accepted — the gate wants a conscious acknowledgment, the same trust level as retry-after-deny.
- Negative: Rejected keeping tool-identity-only purity: it structurally cannot distinguish compliance from omission, and the cost of that purity is taxing every trivial plan. Rejected real content heuristics (plan length, file counts, diff presence): no diff exists at plan time and those ARE foreign-arg-shape validation. Token recognition is the narrowest read that separates the two populations.
**Vision-fit:** Devkit gates devkit workflow discipline mechanically while judgment stays in the model: the skill states the predicate, the model applies it, the hook verifies only that the application was recorded. Harness-tool argument validation remains out of scope.
**Revisit-when:** The `Prior-art:` line format changes in the brainstorming skill; a harness renames ExitPlanMode plan or Task prompt fields; token-pasting-without-thought shows up in review telemetry as skipped step-0 on problem-shaped work.
**Scope:** agents-hooks/**,cli/lib/install/hook-registration-ledger/**
**Source:** brainstorm
**Evidence-change:** Deny-once taxed the compliant path: a plan already carrying the skill-mandated `Prior-art:` acknowledgment line (verdict or skip note) was still denied once per session. Recognizing devkit own prescribed token requires reading the gated call plan/prompt text, one notch past the tool-identity-only carve-out.
