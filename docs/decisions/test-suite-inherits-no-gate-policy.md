# test-suite-inherits-no-gate-policy

## Target · 2026-09-04 — devkit own test suite inherits no gate policy from whatever launched it

**Context:** devkit ship exports its gate policy into the entire gate process tree (run-gates-with-capture.sh sets DEVKIT_SHIP=1 GUARD_AI_STRICT=1; ship-branch.sh sets DEVKIT_RUN_MODE=ship), and further down that same tree pre-push-validation.sh runs bun run test:run. devkit own suite therefore executes inside devkit own ship environment, so any test asserting a gate exit code silently answers to its launcher rather than to the code: a judge outage that fail-opens at 2 returns 3 under strict. Report b6376f26 (sc-2259) cost a full ~12-minute ship attempt to surface plus a further cycle to diagnose, because the red looked like a defect in the diff. The inverse is worse and silent - a test asserting the strict 3 passes under ship and fails in CI. The status quo was not neutral but actively eroding: vitest.setup.mjs had already been appended to four times, each after a different class of ambient env burned someone, and six test files had independently hand-rolled their own GUARD_AI_STRICT denylists with duplicated prose comments naming the same cause.
**Ruling:** devkit own test processes inherit NO run authority from whatever launched them. vitest.setup.mjs deletes an explicit, named list of ship/review authority variables before any test module loads (setupFiles runs per worker ahead of the first import, so even a top-level process.env capture sees the cleaned env), and both vitest configs share that one file. The list is the same vocabulary cli/lib/ship/review-target.sh unsets, bound to it by a parity test so the two can never drift; membership is reused, the reason is not (that script prevents inheriting a FOREIGN run authority). Deliberate invocation knobs are never scrubbed: SHIP_COMMIT_TIMEOUT and DEVKIT_PREFLIGHT_TIMEOUT are inputs a caller chose. A test that needs a policy var sets it explicitly. The guarantee is about INHERITANCE, not visibility - a per-worker setup file cannot undo a test that sets a var mid-file and never restores it.
**Consequences:**
- Positive: A gate test returns the same exit code whether it was launched from a clean shell, from a pre-push hook, or from inside a devkit ship, so a red test is attributable to the diff that produced it. The class of failure this removes is the expensive one: a result that is green locally and red in a sandbox with nothing in the diff to explain either.
- Negative: The list is literal and hand-maintained, so it fails OPEN on a newly introduced policy variable: a new GUARD_ gate knob leaks into the suite until someone appends it, and the symptom is the same silent exit-code flip this record exists to end. That was chosen deliberately over a prefix rule, which fails CLOSED and is strictly harder to debug.
**Vision-fit:** n/a - internal tooling. devkit own harness, not a surface any consumer installs.
**Researched:** prior-art and feature-critique passes over the whole env path: gateJudgeEnv and withStagedFiles in gate-engine/review/runtime.mts, withoutGitEnv at gate-engine/judge/run-judge.mts, the reviewer tool grants in gate-engine/review/reviewers.mts, cli/commands/review.mts prefix strip, and both vitest configs. Upstream: vitest setupFiles and env documentation, and vitest issue 10525 (stubEnv with undefined stopped unsetting in vitest 4).
**Rejected:** (a) A judge-side withoutShipPolicyEnv composed at gate-engine/judge/run-judge.mts - BREAKS EXISTING BEHAVIOUR: that sink is downstream of gateJudgeEnv and withStagedFiles, which deliberately inject DEVKIT_CHECKLIST_KEEP and DEVKIT_REVIEW_STAGED_FILES into the same object, so scrubbing the DEVKIT_REVIEW_ namespace there deletes what was just added and re-opens sc-1438, sc-1439 and sc-2494. Its premise is also false: the broadest judge grant is BASE_TOOLS plus one Bash prefix scoped to the reviewer own checklist script, so no judge can spawn vitest. (b) A GUARD_ / DEVKIT_ prefix rule with a keep-set - FAILS CLOSED on a new knob: there are 180+ live such names, mostly knobs and path pointers, and review-target.sh already documents renaming DEVKIT_PREFLIGHT_TIMEOUT to dodge the one prefix strip devkit has. (c) env -u at pre-push-validation.sh - TOO NARROW: it closes the hook door only, missing a developer own exported shell and the devkit review chain. (d) vitest test.env - CANNOT UNSET: documented as a setter, so children see the variable present-but-empty, which is wrong for any reader that checks presence. (e) vi.stubEnv with undefined, per test - BROKEN UPSTREAM on the pinned vitest 4 (issue 10525), and per-test defence is what produced the six duplicated denylists in the first place.
**Anchored-bet:** [BET]
**Revisit-when:** A codex-family judge is shown to execute commands outside its --allowedTools grant, which would make a judge-side scrub necessary after all; OR a newly added policy variable leaks into the suite twice because the literal list was not updated, which would buy the prefix rule its cost.
**Scope:** vitest.setup.mjs,vitest.config.mjs,cli/__tests__/vitest-setup-env-scrub.test.mts

- 2026-09-04 — sc-2259 follow-up — the Target's ruling said the scrub list IS review-target.sh's vocabulary; edge-case testing showed that list is not a superset of what a ship actually exports, so the first implementation was a partial fix. ship-branch.sh additionally exports DEVKIT_SHIP_BRANCH, DEVKIT_SHIP_DRY_GATES, DEVKIT_SHIP_FROM_BRANCH, DEVKIT_SHIP_INTENT_RECORDED, DEVKIT_SHIP_PATHS, DEVKIT_SHIP_REPO, DEVKIT_SHIP_RESUMED and DEVKIT_SHIP_ROOT, none of which review-target.sh unsets because it guards a review ENTRYPOINT rather than the downstream tree. Four of those are read at runtime and are not inert: qavis-advisory shipMode() branches on DEVKIT_SHIP_ROOT and then runs git -C against that path, and review completeness verdictBranch() scopes a sticky verdict to DEVKIT_SHIP_BRANCH, so an inherited pair makes a test answer for the OUTER ship's repository. The scrub now carries three provenance lists - INHERITED_RUN_ENV (review-target.sh parity), SHIP_EXPORTED_ENV (the ship-script delta) and TEST_ONLY_ADDITIONS (the FRINK_AI_STRICT alias) - with SCRUBBED_ENV as their union. The binding test no longer trusts a hand-written list: it parses the export left-hand sides out of ship-branch.sh and run-gates-with-capture.sh and requires every DEVKIT_/GUARD_ name found there to be scrubbed, so a future ship export is caught at the source rather than after it flips a gate test. Also pinned: vitest.e2e.config.mjs shares the same setupFiles, which was assumed rather than asserted.
