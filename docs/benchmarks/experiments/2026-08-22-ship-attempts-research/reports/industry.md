## Industry practice: large-PR handling and re-review — cited findings

### CodeRabbit
Source: `docs.coderabbit.ai/reference/review-commands`, `coderabbit.ai/blog/coderabbit-deep-dive`
- **Large PRs**: no chunk-size number published. Blog states a two-tier model approach — a cheap/fast model ("simpler models," implied GPT-3.5-class) does per-file **triage/summarization** to decide which changes need deep review; GPT-4-class model does the actual detailed review only on flagged files. Custom diff formatting ("closer to how humans understand changes" vs raw unified diff) plus "layers of sanity checks to fix or hide inaccuracies." Path Filters (`!dist/**`) and Path Instructions (glob-scoped custom rules) narrow scope but are user-configured, not automatic chunking.
- **Re-review**: `@coderabbitai review` = "incremental review of new changes only" (new commits since last review); `@coderabbitai full review` = complete re-review from scratch. Both consume the same review quota. No documented dedup mechanism for repeated findings on unchanged code.
- **No published FP-rate or cost numbers** in any fetched source.

### Qodo/Codium PR-Agent (open source — verified from actual source, not docs)
Repo: `github.com/qodo-ai/pr-agent` (recently renamed `The-PR-Agent/pr-agent`)
- `pr_agent/settings/configuration.toml`: `max_model_tokens=32000`, `patch_extra_lines_before=5`, `patch_extra_lines_after=1` (hunk context extension), `large_patch_policy="clip"` (options: `clip`/`skip`), `num_code_suggestions_per_chunk=3`, `max_number_of_calls=3` (max chunks for `/improve --extended`), `parallel_calls=true`.
- `pr_agent/algo/pr_processing.py`: `get_pr_diff()` — if total tokens fit under `get_max_tokens(model) - 1500` soft threshold, sends the whole extended diff in one call. Otherwise calls `pr_generate_compressed_diff()`, which sorts files by token count descending and greedily packs a single patch (`generate_full_patch`) until `max_tokens_model - 1000` hard threshold; files that don't fit are listed by name only ("Additional modified files (insufficient token budget to process)"). If `large_pr_handling=true` and files remain, it fans out into **additional sequential/parallel patches** — capped at `pr_description.max_ai_calls - 1` (default 4-1=3) iterations — each processed by a separate model call (`asyncio.gather` when `parallel_calls=true`, `pr_code_suggestions.py:804-810`). So the effective chunk unit is **whole files packed into token-budget buckets**, not fixed-size hunks, capped at 3 parallel model calls per PR by default.
- **Re-review**: `/review -i` (incremental) is a first-class mode (`pr_reviewer.py:63-65,534-573`). It calls `git_provider.get_incremental_commits()` to scope the diff to only new commits since the prior review, gated by `minimal_commits_for_incremental_review` and `minimal_minutes_for_incremental_review` thresholds (`require_all_thresholds_for_incremental_review` picks `any`/`all` semantics). If the git provider doesn't support incremental commits, or `commits_range is None`, it **falls back to a full review** (`pr_reviewer.py:543-552`). Persistent review comment is skipped for incremental runs (`persistent_comment and not incremental.is_incremental`, line 201).
- **Dedup on re-push**: `pr_agent/algo/inline_comment_dedup.py` — opt-in via `config.persistent_inline_comments` (default `false`). Computes two SHA-256 fingerprints per inline comment (body fingerprint over file+line+normalized first-80-chars of prose; code fingerprint over file+line+normalized suggested-code block), embeds them as an HTML comment marker in the posted body, and on later runs scans existing comment bodies for markers to rebuild the seen-set — skipping any comment whose either fingerprint already exists (OR-match, to catch "same prose different code" and vice versa). This is a purpose-built fix for GitHub issue #2037 ("re-posts identical inline suggestions on every run").
- `github_app.push_trigger_wait_for_initial_review`, `push_trigger_pending_tasks_backlog`, `push_trigger_pending_tasks_ttl=300` — debounces/queues push-triggered re-reviews.

### Cursor Bugbot
Source: `cursor.com/docs/bugbot`, `cursor.com/blog/may-2026-bugbot-changes`
- Reviews the **full PR diff on every push by default** (docs are explicit about this — "so an iterative branch bills several times over"). A newer commit **cancels** an in-flight review.
- Optional "Incremental Review" toggle in Bugbot Automations: reviews only the delta since the previous Bugbot run, not the whole PR — described as the difference between "paying for one diff repeatedly and paying for it once."
- 8 parallel analysis passes per PR with randomized diff ordering per pass, majority voting + a validator model to decide which findings survive; claimed 70%+ resolution rate; ~$1.00–$1.50 average cost per run. (These numbers came from third-party summary pages, not Cursor's own docs — treat as unverified/marketing-adjacent.)

### Graphite (Diamond / now "Graphite Agent")
Source: `graphite.com/guides/ai-code-review-context-full-repo-vs-diff`, `graphite.com/blog/introducing-graphite-agent-and-pricing`
- Positions itself as "codebase-aware" (diff + surrounding code + other modules) rather than full-repo-indexed, explicitly framed as a middle ground to avoid the cost of indexing entire large repos.
- Its actual answer to "PRs too big to review" is organizational, not architectural: **stacked PRs** (Graphite's core product) — split the change into a chain of small reviewable PRs rather than chunking one large diff internally.
- No chunk-size numbers, no documented incremental-re-review mechanism found in public sources.

### Greptile
Source: `greptile.com/what-is-ai-code-review`, `greptile.com/docs/introduction`
- Indexes the whole repo: tree-sitter AST parse → per-node natural-language docstrings → embeddings, kept live-updated as code changes. Retrieval = vector + keyword search plus an **agentic step** that evaluates relevance and follows references/call graph across files ("multi-hop investigation"), plus git history.
- This is a full-context-retrieval strategy rather than a diff-chunking strategy — it doesn't need to chunk the PR because it isn't trying to fit the whole repo in one prompt; it fetches only the relevant slices per finding.
- No public source disclosed a chunk size, token cap, or explicit incremental-vs-full re-review policy.

### GitHub Copilot code review
Source: `github.blog/changelog/2025-07-02-copilot-code-review-better-handling-of-large-pull-requests`, `docs.github.com/copilot/using-github-copilot/code-review/using-copilot-code-review`
- July 2025 changelog: removed prior "system limits that prevented reviews on larger or more complex files" — motivated by the stat that **~30% of GitHub PRs have >20 files**. No chunk unit/size or model disclosed.
- Auto re-review is opt-in per repo ("Run on each push"); manual re-review via the Reviewers menu otherwise.
- **Documented known gap** (their own docs, verbatim): *"When re-reviewing a pull request, Copilot may repeat the same comments again, even if they have been dismissed with the 'Resolve conversation' button or downvoted."* — i.e., GitHub does **not** claim to solve the "repeat finding on unchanged code" problem; it's an acknowledged limitation, not a solved feature.

### Ellipsis
Source: ZenML LLMOps case study (`zenml.io/llmops-database/building-and-deploying-production-llm-code-review-agents...`)
- Uses Turbopuffer vector store with **incremental indexing keyed by content-hash chunk IDs**: on each commit, diff new vs. existing chunk IDs in the namespace, delete obsolete ones, embed/upsert only new ones — most commits touch a small % of chunks so re-sync takes "a couple of seconds." This solves *index* freshness on push, not directly PR-diff chunking for the LLM call itself.
- Multiple specialized LLM "comment generator" agents run in parallel with a filtering pipeline (architecture described only at a high level; no chunk-size/token-cap numbers published).

### Sourcery
Source: `docs.sourcery.ai/Code-Review/...`
- "Sourcery reviews a pull request as soon as it opens, and again when you push new commits" — re-review is automatic on every push. `@sourcery-ai review` command explicitly **"resets the per-pull-request re-review counter and runs a fresh full review"** — implying re-reviews are normally throttled/counted (mechanism not detailed in the fetched pages) and that a full (not incremental) review is what actually runs. Detailed anatomy-of-a-review page (with the dedup mechanics) exists per their own internal links but its content wasn't retrievable via fetch in this session — flag this as **not independently confirmed**, only referenced.

### cubic.dev
Source: `cubic.dev/blog/the-false-positive-problem-why-most-ai-code-reviewers-fail-and-how-cubic-solved-it`, `cubic.dev/blog/scaling-code-review-for-ai-generated-code-without-scaling-the-team`
- Published numbers: claims **11% false-positive rate** after "three major architecture revisions," a **51% FP reduction** from their baseline "without sacrificing recall," and claims to surface "50% more unique issues than CodeRabbit" on repos running both (self-reported, not independently verified).
- States "above 500 lines, returns diminish sharply — large diffs overwhelm context windows, causing models to fall back on surface-level pattern matching," and that "chunking large PRs is a prerequisite, not an optimization" — but the blog does **not** disclose their actual chunk unit/size or model tiering; that's marketing copy, not a spec.

### Anthropic — Claude Code Review (own product, primary source: `code.claude.com/docs/en/code-review`)
This is the most technically detailed public spec found in this research:
- **Architecture**: "multiple agents analyze the diff and surrounding code in parallel on Anthropic infrastructure. Each agent looks for a different class of issue, then a verification step checks candidates against actual code behavior to filter out false positives. The results are deduplicated, ranked by severity, and posted as inline comments." No chunk-size number disclosed (diff is scoped per-PR, not per-file necessarily — agents work by *issue class*, not by file shard).
- **Severity taxonomy** includes a **🟣 "Pre-existing" tier** — bugs that exist in the codebase but weren't introduced by this PR — a structural answer to "don't blame the diff for unrelated existing code," distinct from suppressing findings outright.
- **Re-review modes** (repo-level config, chosen by an Owner): *Once after PR creation* (single review, no re-review), *After every push* (full new review on every push, and it **auto-resolves previously-opened threads when the flagged issue is fixed**), *Manual* (`@claude review` / `@claude review always`). There is **no incremental-diff-only mode** — "After every push" re-examines the diff and surrounding code again each time, it just auto-resolves matched threads rather than re-posting them.
- **Anti-churn mechanism is prompt-level, not code-level**: `REVIEW.md` supports an explicit "Re-review convergence" instruction pattern — e.g. *"after the first review, suppress new nits and post Important findings only"* — to stop "a one-line fix from reaching round seven on style alone." This is a documented, named pattern in their own docs, i.e., Anthropic treats re-review churn as a prompting/policy problem, solved by repo-level instructions, not by a fingerprint/hash dedup mechanism (unlike PR-Agent's `persistent_inline_comments`).
- **Feedback loop**: 👍/👎 on every inline comment; reactions are collected post-merge to tune the reviewer, but explicitly **do not trigger a re-review or change the PR live**.
- **Cost/latency (published)**: "$15-25" average cost per review, "completing in 20 minutes on average," billed via usage credits separate from plan usage; cost scales with PR size/complexity and multiplies by push count under "After every push."
- **Local `/code-review` (not the GitHub-App product)**: effort levels `low/medium/high/max` trade "fewer, high-confidence findings" vs "broader coverage, may include uncertain findings" — this is the model-tiering-by-confidence lever, not per-chunk model selection. `ultra` escalates to the same cloud multi-agent pipeline as the GitHub App, run against local branch/PR scope.
- Anthropic's separate `anthropics/claude-code-security-review` GitHub Action (different product) exposes a `run-every-commit` flag whose own doc string warns: *"Warning: May increase false positives on PRs with many commits"* — implying its default behavior is some form of per-commit caching/skip, and enabling full re-scan on every commit is known to increase noise. Also advertises "diff-aware scanning" (changed files only) and a `findings_filter.py` FP filter, but no chunk-size/token numbers disclosed.

## Standard-practice summary
Per-PR-scoped fan-out is standard, but true **per-file/per-hunk parallel fan-out with a fixed chunk size** is only confirmed, from primary sources, in one place: **Qodo PR-Agent**, whose open-source code packs files into token-budget buckets and runs up to 3 parallel model calls per PR (`parallel_calls=true`, `max_number_of_calls=3`). Every other vendor either (a) discloses no numeric chunk unit at all (CodeRabbit, Greptile, Graphite, cubic, GitHub Copilot, Anthropic) or (b) sidesteps chunking via full-repo context retrieval (Greptile: AST+embeddings+agentic multi-hop) rather than diff-splitting, or (c) sidesteps it organizationally by asking humans to keep PRs small (Graphite's stacked-PR pitch). Incremental re-review (new-commits-only) as a distinct, user-selectable mode is standard among the diff-only tools — CodeRabbit (`@coderabbitai review` vs `full review`), PR-Agent (`/review -i`, gated by commit-count/time thresholds with automatic fallback to full review), Cursor Bugbot (opt-in toggle, full-diff is actually the *default*), Sourcery (full review is what actually runs on every push per their own command description, despite reviewing "again when you push"). Anthropic's own Code Review product is the outlier: it deliberately does **not** offer incremental-diff-only re-review — its cheapest mode is "once," its continuous mode ("after every push") re-examines the whole diff+context every time, and it handles repeat-noise as a prompt-engineering problem (REVIEW.md "re-review convergence" instructions, a "Pre-existing bug" severity tier, and thread auto-resolution keyed to whether the flagged line changed) rather than a fingerprint/cache dedup problem. The one purpose-built code-level dedup mechanism found anywhere in this research is PR-Agent's `persistent_inline_comments` fingerprint store (`inline_comment_dedup.py`) — everyone else either doesn't publish a mechanism, relies on "resolve conversation" being manual (GitHub Copilot, which explicitly documents this as unsolved), or relies on the LLM prompt to self-suppress repeats. Cross-file bugs in chunked mode are handled by exactly two documented strategies: full-repo context retrieval before/instead of chunking (Greptile's graph+agentic hop, Anthropic's "surrounding code" context per agent) or a second whole-PR pass (CodeRabbit's cheap-model triage-then-deep-review two-stage funnel; PR-Agent's separate `/describe` PR-level summary call distinct from per-chunk `/improve` suggestion calls). No vendor examined publishes a rigorous, methodology-disclosed false-positive rate; the only numbers found are self-reported and unverified (cubic: 11% FP / 51% reduction; Bugbot: "70%+ resolution rate," ~$1–1.50/run — both from third-party marketing-adjacent pages, not the vendor's own technical docs) plus one unrelated static-analysis academic number (90% FP, Google Ads/Marketing dataset, not an LLM reviewer). What is **not known publicly** for any vendor: the actual token/line chunk-size threshold used in production (except PR-Agent's configurable `max_model_tokens=32000` default and `large_patch_policy=clip`), which specific model is assigned to which chunk/pass beyond CodeRabbit's cheap-triage/expensive-review split and Anthropic's effort-level confidence dial, any rigorous eval-set-based false-positive/precision number from a first party, and how Google's or Meta's internal LLM-based review tooling (if it exists in the form implied by the task) actually works — nothing from either company is public.
